# 03 — 控制面板

控制面板是宿主提供的**一扇窗口**（另有通知表面与每个插件一扇的详情窗口，
见 §1.4 与 §9），承载七页内容。

它同时是**面板表面**的唯一引用来源 —— 打开它就创建那一份 imgui 上下文与
渲染后端，关闭它就全部销毁（见 [01-架构总览 §8](01-架构总览.md)）。
因此本篇的每个交互都要回答一个问题：**它会不会打开或关闭面板表面？**

---

## 1. 窗口与生命周期

### 1.1 窗口

- 一扇 **GLFW 窗口** + 它自己的渲染后端（DX11 优先，没有硬件 D3D11 时回退
  OpenGL，见 [01-架构总览 §8.3](01-架构总览.md)），标题为 `SimpleMessage 0.1.0`。
- 默认尺寸 900×600，最小 640×400。
- **窗口活一整个进程**：关闭面板只是把它藏起来，下次打开不用重建（[02-宿主设计 §11.4](02-宿主设计.md)）。
- 位置与尺寸、上次打开的页、各页的过滤条件，保存在
  `<数据目录>/host/ui_state.toml`。
- 浮层**不在**这扇窗口里 —— 它有自己的窗口，见 §1.4 与 [02-宿主设计 §11.6](02-宿主设计.md)。

> **为什么不写 imgui 的 `imgui.ini`**：那会在 exe 目录或工作目录里多出一个
> 用户不知道从哪来的文件，而它的内容又和 `ui_state.toml` 高度重叠。
> 把 `io.IniFilename` 设为 `nullptr`，宿主自己管这一份小状态。

### 1.2 打开与关闭

| 动作 | 效果 |
|---|---|
| 点托盘图标 / 菜单"打开控制面板" | 打开窗口。**面板表面的引用 +1** |
| 点窗口的 × | **关闭面板，不退出程序**。面板表面的引用 −1 |
| 按 `Esc` | 同上 |
| 托盘菜单"退出" / 面板里的"退出"按钮 | 走 [01-架构总览 §12.2](01-架构总览.md) 的关停顺序 |

> **× 只是关面板，不是退出程序。** 这与"点 × 关掉了一个应用"的直觉不同，
> 所以**必须**处理这个预期差：
>
> - 首次关闭面板时，用一次**托盘气泡**提示"SimpleMessage 仍在后台运行"；
> - 之后不再提示（状态记在 `ui_state.toml`）。
>
> 不这样做的话，用户会以为程序退出了，然后发现它还在托盘里 ——
> 或者更糟，以为程序退出了，实际上它还在消耗资源。

### 1.3 关闭时的引用归还

关闭面板**只**归还"面板"这一个引用（[01-架构总览 §8.2](01-架构总览.md)）。
面板自己关掉之后，窗口立即藏起来、面板表面销毁 —— 没有任何插件能把它钉住。

**详情视图不算数。** 插件打开的详情视图有自己的窗口（§9），既不依赖面板，
也不会因为面板关闭而消失；反过来，关掉详情窗口也不会打开或关掉面板。

| 此刻还开着的东西 | 面板会怎样 |
|---|---|
| 什么都没开 | 窗口藏起来（引用归零 → 面板表面销毁） |
| 插件开着详情视图 | **照常关**（详情在它自己的窗口里继续显示） |
| 还有浮层（§1.4） | **照常关**（浮层在自己的通知表面里继续显示） |

这正是把"通知、详情和主界面挤在同一扇窗口"拆开之后的直接结果 ——
三件事的行踪互不牵连。

### 1.4 通知表面（浮层画在哪）

浮层不画在控制面板的窗口里，而是画在一扇**独立的通知表面**上：
无边框、不进任务栏、不抢焦点、置顶，尺寸由内容决定（[02-宿主设计 §11.6](02-宿主设计.md)）。

| 事 | 归谁 |
|---|---|
| 摆在哪块屏幕的哪个角 | 宿主：`[notify_window]`（[03-配置格式 §3.4](插件开发/03-配置格式.md)），改了立刻生效；**面板的通知页顶部可以改**（§4.6） |
| 窗口多大 | 内容：一帧画完之后按内容量；**内容**的宽度区间是插件的设置（`notifier.imgui` 的 `toast_width_min/max`） |
| 画什么、什么时候消失 | 插件：`draw_ui()` + `request_ui_surface()` |
| 闲着 30 秒 | 停止出帧（休眠），下一条通知到达时唤醒（[02-宿主设计 §11.7](02-宿主设计.md)） |

**面板与浮层互不牵连**：浮层出现不会打开面板，面板关掉也不会让浮层消失。
通知页（§4）列的是落在**历史**里的通知，与浮层本身有没有显示在同一点上无关 ——
浮层到期了，那条记录还在通知页里。

### 1.5 页面结构

```
┌────────────────────────────────────────────────────────────┐
│ 概览 │ 插件 │ 通知 │ 规则 │ 路由 │ 日志 │ 关于 │ ⟵ 七页，Tab 切换 │
├────────────────────────────────────────────────────────────┤
│  [ 可能出现的安全模式横幅 ]                                  │
│  [ 可能出现的"配置未保存"提示 ]                              │
│                                                            │
│                       当前页内容                            │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

插件详情**不在这扇窗口里**：每个插件一扇独立窗口，见 §9。

- 每帧**只绘制当前页**。其余页面的构建逻辑不执行（不是"隐藏"）——
  日志页与通知页都要遍历几百条数据，全画一遍会明显拖慢帧率。
- **顶部横幅区**由宿主在任意页之上插入，共两种：
  - 安全模式提示（[02-宿主设计 §16](02-宿主设计.md)）；
  - "配置未能保存"提示（[03-配置格式 §6.5](插件开发/03-配置格式.md)），带"重试"按钮。
  两者可以同时出现，且**不遮挡**内容（内容区下移）。

## 2. 概览

一屏回答"现在什么情况"。

| 区块 | 内容 |
|---|---|
| **版本** | 宿主版本 + API 版本（`0.1.0` / API 3） |
| **运行状态** | 已运行时长；单实例是否为所有者；调度是否被"暂停调度"暂停 |
| **插件统计** | 已加载 / 已启用 / 已禁用（自动）/ 被拒绝，四类计数 |
| **通知统计** | 本次运行收到总数；当前队列长度；已被丢弃条数；未被投递条数 |
| **错误汇总** | 最近一次崩溃、最近一次初始化失败（若有），各一行，可点击跳到插件页对应项 |

**已被丢弃条数**是必须显示的一项（[02-宿主设计 §7.2](02-宿主设计.md)）：
队列满时丢弃最旧的通知，如果用户在界面上看不到这件事，
"我刚才明明收到过那条通知"就会变成一个无解之谜。

**没有图表。** 一个跑在资源受限设备上的托盘工具不需要画折线图 ——
它需要的是"我该做什么"。

## 3. 插件

### 3.1 列表

**每行是一个插件实例**，不是一个 DLL。一个 Source 类型可以有多行
（`source.email`、`source.email@2`），它们共享同一个已加载的 DLL，
但各有独立的设置、调度槽与统计。

页面顶部是一排操作：**“添加实例”**、**“重新扫描插件目录”**、
**“全部启用”**、**“全部禁用”**。“添加实例”在只读模式或安全模式下禁用并
显示原因；重新扫描与两个批量按钮在安全模式下禁用。批量操作只作用于真实实例，
跳过类型行、被拒绝的实例与宿主内建来源。

**“重新扫描插件目录”** 用于在宿主运行中补充插件，不必重启：

- 扫描 `plugins/` 下的 `.dll`（跳过 `sm_imgui.dll` / `sm_curl.dll` 这类共享依赖）。
- 新出现的 DLL 先走**与启动时相同**的校验（元信息、ABI、导出符号等），
  **校验失败的直接跳过**，在列表里以“已拒绝加载（原因）”占一行，
  不影响其他插件。
- 之前被拒绝的类型会重试一次 —— 用户可能已经修好并替换了文件。
- 已通过校验的类型与正在运行的实例保持不变；重扫只登记新类型、创建新实例。
- 完成后在页面顶部显示结果（扫描数、新增 / 通过 / 拒绝、恢复数、新加载实例数）；
  没有新插件时提示“没有发现新插件”。

替换**正在使用**的 DLL 仍然做不到（文件被占用）：先在列表里禁用该插件，
或退出宿主后再替换。

| 列 | 说明 |
|---|---|
| 启用 | 复选框。改动**立即生效**（该实例的加载/卸载），并进防抖写回队列 |
| 名称 | 实例显示名：自定义名 → 类型名 → `类型名 #N` |
| id | 实例 id（`source.email`、`source.email@2`），等宽字体 |
| 类型 | 调度子项 / 通知器（`Source` / `Notifier`） |
| 版本 | `PluginMeta::version`（同类型各行相同） |
| 状态 | 见下表 |
| 最近活动 | 最近一次 `start()` / `on_notify()` 的时刻与结果 |

**类型没有实例时也占一行**：显示“尚无实例”和“添加实例”按钮
（预选该类型）。这样“我装了插件但它不在列表里”不会发生 ——
被用户删空的类型仍然看得见，也随时能加回来。

**“添加实例”只列出 Source 类型。**Notifier 每种类型只有一个实例，
表中没有它的增删入口（[03-配置格式 §3.2](插件开发/03-配置格式.md)）。

**状态列的取值必须能区分"我关的"与"它坏了"**：

| 显示 | 状态 | 颜色 |
|---|---|---|
| 运行中 | Running | 正常 |
| 已停止 | Stopped（用户禁用） | 灰 |
| **已禁用（原因）** | Disabled（自动） | **黄** |
| 初始化失败（原因） | InitializeFailed | **黄** |
| **已拒绝加载（原因）** | Rejected | **红** |
| 未加载 | Discovered（安全模式 / 未启用） | 灰 |

### 3.2 添加 / 删除 / 改名实例

**添加**（只对 Source）：

1. 顶部“添加实例”按钮打开弹窗。
2. 弹窗列出所有 `kind == Source` 且未满 16 个实例的类型，每项显示
   类型名、类型 id 与“现有 N 个实例”。
3. 可填显示名（留空 = 自动命名，即类型名，第二个起为 `类型名 #2`）。
4. 确定后宿主生成实例 id（首个是类型 id，之后是 `@2`、`@3`……），
   写配置并立即加载；设置文件按默认值生成。
5. 成功则展开新实例那一行并滚动到它；失败（类型重载失败等）在弹窗内
   显示原因，且配置不会留下半条实例。

**改名**：只改显示名，**永远不改实例 id** —— id 是配置键、设置文件名、
日志来源与规则目标的身份，改它等于把实例变成另一个实例。空名字恢复自动命名。

**删除**（只对 Source，带确认弹窗）：

- 确认弹窗显示实例名、实例 id 与将被删除的设置文件路径，并说明
  **“历史通知不受影响；设置文件会被删除且不可恢复”**。
- 确认后该行立即从列表消失（调度线程若正卡在 `start()` 里，宿主等它
  返回后再销毁对象），配置立即落盘，随后删除
  `plugins/<实例id>.toml` 与 `.bak`。
- 被删的是该类型的最后一个实例时，宿主写 `[removed_types]` 墓碑，
  下次启动**不会**自动把它重建出来（[03-配置格式 §3.2](插件开发/03-配置格式.md)）。
- 删除的是 `@2` 时 canonical 实例继续运行；其他实例的设置文件不受影响。
- 列表里的**通知历史仍按原实例 id 显示**（历史是记录，不是插件状态）。

**只读模式 / 安全模式**：这三个入口全部禁用，并在页面上说明原因；
即便绕过界面直接调用管理器 API，也会被拒绝。

### 3.3 展开详情

点击一行展开：

- **描述**（`PluginMeta::description`）
- **插件类型**：类型名与类型 id（同一 DLL 的所有实例相同）
- **实例 id**（只读，等宽字体）、**序号 / 总数**（`第 2 个，共 3 个`）
- **实例名称**：可编辑的输入框（Source 实例；空 = 自动命名，见 §3.2）
- **作者**、**要求的宿主版本范围**（`host_range`）与它是否满足
- 若 `Rejected`：**拒绝原因**（来自 [01-入门 §2.2](插件开发/01-入门.md) 的
  12 条检查中的哪一条，附具体值，例如"插件 id `source.mail` 与已加载的
  `source.mail` 重复"；手写的 `notifier.x@2` 会提示“Notifier 每种类型只能有
  一个实例，请从 config.toml 的 `[[instances]]` 删掉这一行”）
- 若 `Disabled`：**禁用原因**（崩溃的异常码 / 连续超时次数 / `Abort`）+ 
  **"重新启用"按钮**
- 若 `InitializeFailed`：错误文本（来自 `set_error()`）+ "重试"按钮
- **设置表单**（见 §3.4）。类型被拒绝或该类型尚无实例时不显示
- 一行小字：`配置：<own_config_path>`（即 `plugins/<实例id>.toml`）
  与"重置为默认值"按钮
- Source 实例底部有 **"删除实例"** 按钮（见 §3.2）。类型被拒绝、Notifier
  实例与宿主内部来源 `sm.host` 都不显示它

**"重新启用"与"重试"是必须存在的**（[02-宿主设计 §4.5](02-宿主设计.md)）：
自动禁用是宿主的保护动作，而撤销它的路径必须就在用户看到原因的地方 ——
不能要求用户去手工编辑配置文件。

### 3.4 设置表单的自动生成

宿主按 `PluginMeta::settings` 生成表单，**插件不参与任何 UI 代码**。

| `SettingType` | 控件 |
|---|---|
| `Bool` | 复选框 |
| `Int` | 拖动条（SliderInt）+ 同行输入框；范围取 `[min_int, max_int]` |
| `Double` | 拖动条（SliderDouble）+ 同行输入框；范围取 `[min_double, max_double]` |
| `String` | 单行输入框（`InputText`），`max_length = max_string_bytes` |
| `Enum` | 下拉框（`BeginCombo`），选项来自 `options` |
| `Sound` | 单行输入框 + **“浏览…”**（系统打开对话框，列出 `*.wav;*.mp3`）+ **“试听”**（立即播放当前值） |

生成规则：

- `label` 为空时用 `name`；`description` 非空时作为 **tooltip**（鼠标悬停显示）。
- `requires_restart == true` 时在标签后加 `（重启后生效）`。
- 控件宽度按最长标签对齐，避免一列参差不齐的输入框。
- **`String` 类型的值不回显成"路径选择器"** —— 通用路径选择器是刻意不支持的
  类型（[02-SDK接口参考 §7.3](插件开发/02-SDK接口参考.md)）；需要选目录的插件，
  让用户在设置里粘贴路径。
- **`Sound` 是唯一的例外，而且只针对声音**：值是 WAV / MP3 文件路径，相对路径
  相对宿主的配置目录解析 —— 这条约定由 SDK 固定，宿主才能安全地提供"浏览…"与
  "试听"。试听失败时弹窗说明原因；试听与 `notifier.sound` 用同一个 miniaudio
  解码器，但走宿主自己的播放路径，不读插件的音量设置。
- **改动立即写进内存**（下一次 `setting_*()` 就返回新值），
  并进防抖写回队列（[03-配置格式 §6.2](插件开发/03-配置格式.md)）。
- **非法值不可能通过界面产生**：滑块受范围约束，输入框受长度约束，
  下拉框只能选已有项。因此界面上的值永远是合法的 ——
  校验逻辑只服务于"手工编辑的配置文件"。

> **为什么没有"应用"按钮**：改动立即生效是本设计的核心承诺
> （[02-SDK接口参考 §6.3](插件开发/02-SDK接口参考.md)）。加一个"应用"按钮，就等于把
> "我改了设置为什么没生效"变成一个必然会被问到的问题。

### 3.5 实例的启用/禁用

```
勾上：
    （该类型的 DLL 若已卸载）LoadLibrary → 12 条校验
    sm_create_plugin → initialize()
    成功 → 该实例加入调度器（Source）或路由表（Notifier）
    失败 → 状态置 InitializeFailed，并显示原因

取消勾选：
    从调度器/路由表摘除该实例
    若 Running → stop()
    exit() → sm_destroy_plugin()
    状态置 Stopped，并持久化到 [[instances]]
    该类型没有其它活动实例时才 FreeLibrary
```

**这条路径与启动时的加载路径必须是同一份代码** —— 两份代码意味着
"启动时能加载的插件在界面上开不了"这类不一致。

**DLL 的卸载是按类型计数的**：关掉 `source.email@2` 不该让
`source.email` 跟着停摆。只有该类型的**所有**实例都不再存在
（注意：禁用不算删除，实例仍占着类型）时模块才会卸载；重新启用时
重新加载并重新校验。

## 4. 通知

### 4.1 列表

显示**未过滤的完整内存历史**（最近在前）。

| 列 | 说明 |
|---|---|
| 时间 | `HH:MM:SS`（当天）或 `MM-DD HH:MM`（更早） |
| 级别 | 文字 + 颜色（Debug 灰 / Info 蓝 / Warning 黄 / Error 橙 / Critical 红） |
| 来源 | `source_plugin` |
| topic | 等宽字体 |
| 标题 | `title` |
| 摘要 | `summary`（即通知卡片上会显示的那一行） |

**用 `ImGuiListClipper` 只绘制可见行。** 历史有 200 条，
每条的内容渲染都要做文本布局，全画一遍是纯粹的浪费。

### 4.2 过滤

一组控件，作用于列表（以及"导出"）：

| 控件 | 说明 |
|---|---|
| 级别 | 多选（Debug/Info/Warning/Error/Critical） |
| 来源 | 下拉（全部 / 各**实例 id** / `sm.host`）。两个 `source.webhook` 实例是两个独立选项 |
| topic | 文本前缀匹配（不是正则） |
| 文本 | 在 title/content/summary 中做**子串**匹配 |

过滤是**纯客户端的、每帧重算的** —— 200 条数据的子串匹配在微秒级，
不值得为它做缓存与失效逻辑。

### 4.3 详情

点击一行展开（或右侧显示详情面板，取决于窗口宽度）：

- 完整 `content`（只读、可滚动，可**选中并 Ctrl+C 复制**；`content` 上限 64 KiB）
- `id` / `url` / `time_unix_ms`（含人类可读格式）
- `importance`（非 0 时显示）
- **Action 按钮**：点击 → 宿主按 [01-架构总览 §10.2](01-架构总览.md) 的路径
  调用**该通知来源插件**的 `on_action`？

  **不。** 关键决定：**通知卡片上的 Action 由接收该通知的 Notifier 处理，
  不是由产生它的 Source 处理。**

  理由：Action 的语义是"用户对这个通知想做什么"（打开详情、静音、
  标记已读），而"怎么呈现与响应"是 Notifier 的职责。Source 只负责采集数据，
  让它去处理"用户点了静音"会迫使每个 Source 都实现一套 UI 交互逻辑。

  实现上：控制面板画的通知卡片，其 Action 点击走
  **每一个订阅了该通知的 Notifier 的 `on_action`**（与 `on_notify`
  的路由结果完全一致）。因此插件在 `on_action` 里写一次逻辑，
  无论是在浮层上点还是在控制面板的列表里点，都会走到它。

- `seq`（等宽字体，排在最后）—— 排障时它是唯一稳定的身份标识

**点任意一个 Action 都会把这条通知标为已读**（[02-宿主设计 §8.5](02-宿主设计.md)）：
宿主在主线程把动作分发出去时（**在路由之前**）就标 —— 用户确实点了他屏幕上那张卡片，
托盘图标理应对此有反应，哪怕这个 topic 一个 Notifier 都没订阅。反过来，
若等分发成功再标，"没人订阅"的那一类点击就永远清不掉未读。
面板与插件浮层两条点击路径因此都自动带上已读语义，插件不必自己维护状态。

### 4.4 保存到文件

控制面板提供**不依赖任何插件**的导出能力：

| 按钮 | 行为 |
|---|---|
| **导出当前筛选结果…** | 弹出保存对话框，写出 `.jsonl`（JSON Lines，一行一条通知，UTF-8） |
| **导出全部历史…** | 同上，忽略筛选 |

导出的字段：`seq` / `time_unix_ms` / `level` / `importance` / `source_plugin` / `topic` /
`id` / `title` / `summary` / `content` / `url` / `actions`（数组，含 `id`
与 `label`）。**不含**任何宿主内部状态。

> **为什么格式是 JSON Lines 而不是 TOML**：TOML 表达"一个数组，其中每个
> 元素是一个异构记录"很别扭，而 JSONL 天然就是"一行一条记录"，
> 且可以被 `grep`、被 `jq`、被 Excel/BI 工具直接吃进去。

> **自动保存由插件负责。** 需求里"允许对通知进行保存（到文件中）"有两个
> 层面：**立即导出**（任何用户都要能用，所以做进宿主）与
> **自动归档**（要不要存、存哪、按什么切分，都是策略问题，所以应该是
> 一个 Notifier 插件）。`config.toml` 的示例里出现的 `notifier.archive`
> 就是后者的占位 —— 它**不在本仓库交付的示例插件里**。

### 4.5 清空

"清空历史"按钮，带确认。清空的是**内存历史**，不影响已导出的文件，
也不影响之后新到的通知。`seq` **不重置**（重置会让旧导出文件与新通知的
`seq` 撞车，破坏"进程内唯一"这条保证）。

### 4.6 通知表面

页面**最顶部**的一节（在过滤控件之上），改的是 `[notify_window]` 的两个键
（[03-配置格式 §3.4](插件开发/03-配置格式.md)）—— 浮层所在的那扇窗口贴在哪块屏幕的哪个角。

| 控件 | 内容 |
|---|---|
| **显示器** | 下拉。第一项是"主屏（primary）"，之后每块枚举到的显示器一项，文字是 `设备名（工作区 x,y 宽x高）`；配置里的设备名当前不在系统里时，额外列一项"（已断开）<名>" |
| **位置** | 四选一的单选：左上 / 右上 / 左下 / 右下 |

- **改完立即生效，不需要重启**：宿主每帧现读这份配置，工作区按设备名缓存，
  换块屏下一帧就重新解析。写回走的是与其它设置同一条防抖路径
  （[03-配置格式 §6.2](插件开发/03-配置格式.md)）。
- **枚举显示器一秒一问**（面板开着时这一页以 60fps 重画，而枚举要问系统）。
  插拔显示器的观感延迟最多 1 秒。枚举结果里当然**没有**"（已断开）"那一项 ——
  它由画的地方按配置补上，因为那其实是配置里那个名字，不是系统里的一块显示器。
- 选项里显示的是**工作区**而不是整块屏幕：浮层贴的是工作区的角（不会被任务栏
  压住），工作区就是用户真正看得见的那个矩形。
- 名称写错**不在这里拦**：那块屏幕可能只是此刻没接。运行时的行为是回退主屏
  并记 Warn（[03-配置格式 §3.4](插件开发/03-配置格式.md)），面板在这一节下面补一句提示，
  把"为什么它跑到主屏上去了"直接说出来。
- 显示器那一行**不带"（重启后生效）"之类的后缀** —— 它真的立即生效，而
  `requires_restart` 那条提示（§3.4）用在这里会变成假话。

> **为什么放在通知页而不是"关于"页**：这两个键描述的是"通知长什么样、
> 出现在哪" —— 用户想改它的时候，人就在通知页上。

### 4.7 规则保存开关

通知表面下面有一节"规则保存"，只有一个复选框：**允许规则保存通知内容**。
它读写 `config.toml` 的 `[app] allow_rule_save`
（[03-配置格式 §3.1](插件开发/03-配置格式.md)），默认关闭。

- 关闭时，`rules.toml` 里所有 `[rules.save]` 都不生效；打开后**无视通知来源**，
  匹配且启用了保存的规则会把通知追加写入文件。
- **切换立即生效**，不需要重启；写回走与其它设置相同的防抖路径。
- 保存能力本身由规则决定：这里只是总许可。规则页选中一条规则时，详情会
  显示它的保存状态、路径模板；如果全局开关没开，会额外提示"当前不会写入"。
- 配置只读、`schema_version` 过新或安全模式下复选框禁用 —— 安全模式承诺本次
  运行不落盘，即使配置里写着 `true` 也不会保存。

> **为什么许可不放在每条通知上**：来源趟规则在通知刚进入管线时就执行，那时
> 还没有任何界面交互，也不存在"这条通知的弹窗"。把许可做成全局开关，既能让
> 用户随时关掉写文件这件事，又保持"命中即保存"的语义。

## 5. 规则

规则是通知源与浮层之间的中间层（[03-配置格式 §9](插件开发/03-配置格式.md)）：
用正则匹配标题 / 内容 / 简介 / topic，可以改写标题、内容、简介、级别，
也可以直接丢弃。规则分两趟执行：

| 阶段 | 什么时候 | 影响范围 |
|---|---|---|
| **来源**（source） | 通知进入管线时（`Admit`） | 入库的那一份数据；历史、路由、所有 Notifier 都看到改写后的结果 |
| **投递**（delivery） | 某条通知要交给某个 Notifier 时 | 只影响这一次 `on_notify`；历史与其它 Notifier 不受影响 |

**这个页面只读，唯一的例外是启用开关。** 规则本身只能在 `rules.toml`
里写（[03-配置格式 §9](插件开发/03-配置格式.md)），面板不生成、不改写这个
文件；启用状态反过来存在 `config.toml` 的 `[rules]` 表里
（[03-配置格式 §3.5](插件开发/03-配置格式.md)），由面板写回。

> **为什么启用状态不放在 `rules.toml`**：那个文件是用户手写的，格式、
> 注释、顺序都属于用户。面板写回它就必须整体重写，用户精心排的注释会
> 消失 —— 这与 `[[instances]]` 的处理是同一个理由。把"哪些开着"这个纯状态
> 放进宿主管理的 `config.toml`，两份文件的归属就清楚了。

### 5.1 列表

| 列 | 说明 |
|---|---|
| 启用 | 复选框，**页面上唯一可交互的东西**。改动立即生效并进防抖写回 |
| # | 规则在文件里的顺序，从 1 开始。顺序就是执行顺序 |
| 名称 | 点击选中，下方出现详情 |
| 命中 / 拦截 | 本进程内这条规则的匹配次数 / 丢弃次数。**重新加载后归零**（新规则集实例） |
| 状态 | 启用 / 已停用 |

列表上方显示规则总数与"跳过了 N 条"（解析失败被逐条跳过的规则数），
再上方显示 `rules.toml` 的完整路径 —— 用户不需要去翻配置目录。

被跳过的规则**不占列表位置**：它们没有进入运行时，但"跳过了 N 条"必须
可见，否则用户会以为规则文件里那一行被静默忽略了。具体哪一条、为什么，
在日志页（来源 `host`）。

### 5.2 选中详情

只读展示这一条规则的全部有效配置：id 与名称、类型（`match` /
`auto_summary`）、阶段（来源 / 投递）、来源与 Notifier 目标（不写目标时
显示"全局（所有来源）"）、匹配表达式、`case_insensitive` / `drop` /
`handle`、六类重写项（标题 / 内容 / 简介 / 级别 / 重要等级 / 时间模板）；
`auto_summary` 规则
显示 `from` / `max_codepoints` / `only_if_empty`。

`match` 规则还会显示保存设置：`保存：已启用` / `保存：未启用`，以及路径
模板（空路径显示默认的 `notify/{ruleid}.txt`）。启用保存但通知页的总开关
没开时，这里会补一句"通知页尚未允许规则保存，当前不会写入"。

显示的是**解析后的配置**（模板原文，不是替换结果）—— 这条规则命中时
会改写成什么取决于捕获组，没法在这里预先算出来。

### 5.3 重新加载

"重新加载规则"按钮重新读 `rules.toml`，成功后替换运行中的规则集，并把
"已加载 N 条规则"显示在按钮旁边；失败时保留**上一份**规则集，页面显示
失败提示，具体原因在日志页。

重新加载同时会：

- 清零所有命中 / 拦截计数（新规则集实例）；
- 重新应用 `config.toml [rules]` 里的启用覆盖；
- 让**此后进入**的通知用新规则。已经在队列里的通知不会回滚 —— 来源阶段
  的改写 / 丢弃在入队时就已经发生。

### 5.4 安全模式

安全模式下规则页仍然显示规则内容，但**启用开关被禁用**：安全模式下不写
任何配置文件（[02-宿主设计 §16](02-宿主设计.md)）。如果 `rules.toml`
缺失，安全模式只在内存里使用默认模板，不落盘。

## 6. 路由

**只读页。**

| 区块 | 内容 |
|---|---|
| **表一：Notifier × 有效订阅** | 每个 Notifier 一行；显示它当前的订阅模式列表，并标注每一项来自**元信息**还是**配置覆盖**；订阅为空时显示"（订阅全部）" |
| **表二：最近的 topic** | 最近出现过的 topic（去重，按最近一次出现排序），每个 topic 后面列出**当前会收到它的 Notifier** |
| 底部提示 | `路由由 config.toml 的 [routing] 与插件的元信息共同决定。要修改请编辑：<路径>` |

**表二是这个页面真正的价值**：用户遇到"这条通知没弹出来"时，
打开这一页看一眼 topic 后面跟的 Notifier 列表是不是空的，
答案立即就出来了 —— 不需要重新读一遍订阅匹配规则。

> **为什么只读**：这个页面显示的是**合并结果**（元信息 + 配置覆盖）。
> 让它可写就必然要回答"我在这里删掉一个模式，是删配置里的，还是变成了
> 一条空的覆盖？"—— 两种答案都有道理，而无论选哪种，用户下次打开
> `config.toml` 时都会看到一个自己不认识的、由界面生成的内容。
>
> 所以这里的正确做法是**把决定放在唯一的地方**（配置文件），
> 界面只负责让人看懂它。底部那行路径提示是页面的一部分，不是装饰。

## 7. 日志

### 7.1 数据来源与代价

日志的权威存储是**日志子系统的环形缓冲 + 磁盘文件**
（[02-宿主设计 §12](02-宿主设计.md)）。日志页显示的是环形缓冲的最近内容。

```
每帧最多做一次"快照"：加锁，把最近 min(缓冲长度, 256) 条记录
复制进面板自己的缓冲，解锁。
```

- **加锁时间以微秒计**（一次 memcpy），不会拖慢写线程。
- 每帧最多复制 256 条，因此缓冲里积压 1000 条时，需要几帧才能全部显示。
  这不是问题：看到"还在追"比"某一帧卡 50 ms"好。
- 面板只持有**副本**，因此不阻塞、也不会读到写线程正在写的记录。

### 7.2 控件

| 控件 | 说明 |
|---|---|
| 级别过滤 | 多选，默认 `info` 及以上 |
| 来源过滤 | 下拉（全部 / 各**实例 id** / `host`）。日志的 `source` 字段就是 `plugin_id()`，所以实例天然分开 |
| 文本搜索 | 子串匹配（不是正则） |
| **跟随最新** | 勾选时自动滚动到底部；用户手动向上滚动时**自动取消勾选** |
| 暂停 | 停止取新快照（缓冲里后面来的记录仍会写盘） |
| 打开日志文件 | 用系统默认程序打开当前日志文件 |
| 打开日志目录 | 打开资源管理器 |

"跟随最新"在用户向上滚动时自动取消 —— 这是终端与日志查看器的
通行做法，用户不需要先找到那个勾选框才能往回看。

### 7.3 显示

- 等宽字体（`Consolas` / 回退 `Courier New`）。
- 单行、不换行、横向可滚动（日志行本来就该是一行）。
- 级别用颜色区分，与通知页同一套色板。
- **不提供"清空日志文件"** —— 日志的价值恰恰在出问题之后，
  而"清空"按钮是一个只会被误点的危险操作。要清就删文件，
  让它变成一个需要走出程序的动作。

## 9. 插件详情窗口

插件调用 `set_view_title()` 之后，宿主为它新建一扇**独立窗口**。窗口里只
画这个插件的 `draw_view()`，不出现控制面板的七页，也不需要先打开面板
（[02-宿主设计 §11.5](02-宿主设计.md)）。

| 行为 | 说明 |
|---|---|
| 打开 | 自动新建（或复用）该插件的详情窗口，**不打开控制面板** |
| 标题 | `set_view_title()` 给的值；为空时用插件名 |
| 内容 | 该插件的 `draw_view()` 每帧绘制 |
| 关闭 | 窗口标题栏的 ×，或插件自己调 `close_view()` |
| 多个插件 | 每个插件各自一扇，互不影响 |
| 会话引用 | 每个打开着的视图各持有**自己那扇详情窗口** 1 个引用（`duration <= 0` 的那个），直到被关闭 |

**窗口的关闭按钮由宿主提供** —— 插件的 `draw_view()` 里可以画自己的
"关闭"按钮（`notifier.imgui` 就画了一个），但宿主不能依赖它（插件可能忘了画，
或崩溃了）。标题栏的 × 是最后的安全出口；点它等价于 `close_view()`。

**同一插件只有一扇详情窗口。** 插件在已有视图时再次调 `set_view_title()`
是**改标题并换内容**（例如在浮层上点了另一条通知的「详情」），不是开第二扇。
不同插件之间互不影响。

## 10. 字体与字号

字体加载链见 [02-宿主设计 §13](02-宿主设计.md)。控制面板特有的两点：

### 10.1 字号

界面字号取自 `[app] ui_font_size`（默认 16）。**有效字号 = 字号 × 所在表面的
内容缩放系数**（DPI），两个量都是逐张表面的（[02-宿主设计 §13](02-宿主设计.md)）。

**改动字号时**：`io.Fonts->ClearFonts()` 后按新字号重新装字体
（见 [02-宿主设计 §13](02-宿主设计.md)），**不销毁 imgui 上下文**。
图集的构建与纹理上传都由 imgui 在下一帧自动完成（imgui 1.93 没有
`ImGui_ImplDX11_CreateFontsTexture()` 这个公开函数，见 [02-宿主设计 §11.2](02-宿主设计.md)）。
重建期间会有一帧的停顿（一个 16px 的常用简体字集，实测 6–8 ms）。

### 10.2 面板的字号与插件的字号

宿主的**每张表面各有一份字体图集**（各有自己的上下文，[02-宿主设计 §13](02-宿主设计.md)）：
面板一份、通知表面一份、每个打开着的详情窗口各一份。字号是**同一份配置**
（`[app] ui_font_size`），插件不能各选各的。

> **为什么不让插件各自选字号**：imgui 的字体是上下文级资源，每个插件加载一份
> 自己的字体会让显存占用与插件数量成正比 —— 在资源受限的目标上不可接受。
> 需要更大字号的插件应当自己在自己的窗口内做缩放（`ImGui::SetWindowFontScale`）。
>
> **"每张表面各一份图集"为什么不违反这条**：表面数量是"面板 1 + 通知表面 1 +
> 当前打开着的详情窗口数"，与**已安装**插件数量无关，而且详情窗口一关就销毁
> 它那一份（图集与上下文一起）。换来的收益是每张表面可以各自跟自己的显示器
> DPI（[02-宿主设计 §13](02-宿主设计.md)）。

## 11. 交互与可用性约定

| 约定 | 理由 |
|---|---|
| 所有列表支持键盘上下 + Enter 展开 | 面板可能被用在无鼠标场景（远程、脚本） |
| 破坏性操作（清空历史、重置插件设置）都要确认 | 两者都会丢掉用户看得见的数据 |
| 危险操作（重置插件设置）的确认框里说明"会影响什么" | 不是笼统的"确定吗？" |
| 每个可点击的路径都在 tooltip 里显示完整路径 | 界面窄，路径长 |
| 界面上**不显示**任何百分比、进度条、"正在优化…" | 没有后台任务需要汇报；画它们只会让人以为程序在忙 |
| 界面语言恒为简体中文，字符串集中在 `src/host/strings.h` | 见 [01-架构总览](01-架构总览.md) 的“明确不做的事”：不做 i18n 框架，但**不把中文字面量散落各处** —— 集中在头文件里，将来要加语言时改一处即可 |
