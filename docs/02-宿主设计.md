# 02 — 宿主设计

本篇是宿主的实现蓝图。它不重复 [01](01-架构总览.md) 已经讲清楚的
调度循环、UI 会话与生命周期（只引用），而是补齐**模块划分、子系统行为、
数值参数与失败路径**。

## 1. 模块划分

`src/host/` 下的文件划分，与 `src/host/CMakeLists.txt` 的源文件列表一一对应。
每个文件只做一件事：一个子系统一进一出都是值，谁也不认识谁的内部状态。

| 文件 | 职责 |
|---|---|
| `main.cpp` | 宿主主函数的登记（真正的进程入口符号由平台层的 `entry.h` 提供）、命令行解析、子系统初始化与关停的**显式顺序** |
| `app.cpp/.h` | 应用外壳：托盘、单实例、消息循环、退出流程 |
| `util.cpp/.h` | 路径与文件系统、时间格式化、线程标识（不含业务；编码转换在 `platform/utf8.h`） |
| `log.cpp/.h` | 有界环形缓冲 + 后台写线程；日志文件与启动清理 |
| `config.cpp/.h` | TOML 读写、schema 校验、迁移、原子写与备份（见 [插件开发/03-配置格式.md](插件开发/03-配置格式.md)） |
| `seh_guard.cpp/.h` | 跨插件调用的 SEH 屏障与错误上报 |
| `plugin_host.cpp/.h` | `IHostContext` 的实现：插件跨边界调用的**唯一**入口 |
| `plugin_manager.cpp/.h` | 插件发现、加载校验、类型/实例管理、启停、禁用、模块卸载 |
| `plugin_id.h` | 实例 id 的纯函数：校验、`@N` 生成与解析、类型归属（header-only） |
| `instances.cpp/.h` | `[[instances]]` / `[removed_types]` 的解析与写回、v1 → v2 迁移（可单测） |
| `scheduler.cpp/.h` | 调度器：最小堆、调度线程、唤醒、看门狗统计 |
| `notification_pipeline.cpp/.h` | 入队、深拷贝、去重、背压、历史 |
| `rules.cpp/.h` | 规则中间层：表达式解析、捕获组重写、两种目标、两趟执行（见 §7.6） |
| `placeholders.cpp/.h` | 通用 `{name}` 占位符展开与路径清洗（纯标准库，见 §7.6） |
| `rule_save.cpp/.h` | 规则命中后的通知落盘：路径解析、追加写入、有界失败告警（见 §7.6） |

| `internal_source.cpp/.h` | 宿主自身通知源（`sm.host.*`）、日志→通知桥与限流 |
| `notify_scope.h` | 日志→通知桥的递归中断（`thread_local` 深度计数） |
| `ui_session.cpp/.h` | UI 会话引用计数、imgui 上下文与后端的按需创建/销毁（每张表面各一份，见 §11.5–§11.6） |
| `ui_fonts.cpp/.h` | 中文字体加载（系统字体目录与首选字体列表由平台层给出） |
| `ui_root.cpp/.h` | 面板窗口的 imgui 根节点：铺满客户区、不参与拖动与缩放 |
| `monitor.cpp/.h` | 显示器名字解析（枚举本身在平台层的 `window.h`） |
| `render_backend.h` | 渲染后端的接口与枚举（`IRenderBackend` / `RendererKind`） |
| `render_opengl.cpp` | OpenGL 回退后端（DX11 后端的实现在 `platform/win32/render_dx11_win32.cpp`） |
| `render_probe.cpp` | 后端选择策略：探测、`--renderer` 覆盖与"拿不到上下文"时的折算 |
| `ui_state.cpp/.h` | 面板状态的持久化（`ui_state.toml`） |

| `text_input.cpp/.h` | imgui `InputText` 与 `std::string` 之间的胶水 |
| `strings.h` | 全部界面文案（唯一来源） |

平台相关的一切在 `src/platform/` 之下，**业务代码不得直接调用任何平台 API**，
也不得包含 `<windows.h>` 或在宿主里写 `#ifdef _WIN32`。接口按职责拆成几个头：

| 头文件 | 职责 |
|---|---|
| `platform.h` | 动态库加载、崩溃屏障、可中断等待、单调时钟、调试输出、单实例锁 |
| `utf8.h` | UTF-8 与宽字符互转（与平台无关，实现在 `utf8.cpp`） |
| `fs.h` | UTF-8 路径上的文件打开、目录创建、删除/改名、列目录、绝对路径判定 |
| `system.h` | 可执行文件目录、命令行、`shell_open`、系统字体目录/首选字体、本地时间、架构名、配置根目录 |
| `console.h` | 控制台附加与写入 |
| `message_window.h` | 隐藏的宿主消息窗口（单实例唤起、会话结束） |
| `dialog.h` | 系统"打开"/"另存为"文件对话框 |
| `sound.h` | 提示音试听（miniaudio 解码 WAV / MP3，设置表单的"试听"按钮） |
| `image.h` | 图像解码（RGBA） |
| `tray.h` | 托盘图标、右键菜单与图标等级 |
| `window.h` | 窗口、消息泵、工作区、显示器枚举 |
| `entry.h` | 宿主主函数的登记；各平台提供 `entry_<平台>.cpp` 里的真正入口符号 |

窗口系统是单独的一层：接口 `src/platform/window.h`，实现
`src/platform/win32/window_win32.cpp`（GLFW 3.5.1，见 §11.6）。文件落在
`win32/` 目录下是因为它只在这一个平台上有实现，里面装的是 **GLFW 的封装**，
不是 Win32 调用。**所有可见窗口（控制面板、通知表面、各详情窗口）都是 GLFW
窗口**，它们的窗口过程归 GLFW，宿主要的那几个通知（关闭请求、内容缩放）由
窗口层的回调给出（`window.h` 的 `WindowCallbacks`）；宿主消息窗口与托盘窗口
的 Win32 窗口过程也分别收在 `win32/message_window_win32.cpp` 与
`win32/tray_win32.cpp` 里，因为 GLFW 对"一个不画东西的隐藏消息窗口"没有帮助。

## 2. 单实例

```
名字：Local\SimpleMessage.Instance.<配置目录路径的哈希>
      （Local\ 前缀 = 每用户会话一个；不用 Global\ 是因为不同用户的
        两份实例本来就该允许，它们的配置目录通常也不同）
```

流程：

```
CreateMutexW(nullptr, TRUE, name)
├─ GetLastError() == ERROR_ALREADY_EXISTS
│    → 找到已存在实例的隐藏窗口（FindWindowW 用固定的窗口类名）
│    → PostMessage(hwnd, WM_SM_WAKE, 0, 0)      ← "唤醒并打开面板"
│    → 退出，退出码 0
└─ 否则
     → 本实例成为所有者，把 <hwnd> 记下来供后来者投递消息
```

**安全性**：`WM_SM_WAKE` 只做一件事 —— 打开控制面板。
它**不携带任何数据**，因此一个恶意进程最多能让面板弹出来一次，
不能让它加载插件、改配置或执行命令。

**关掉单实例（`single_instance = false`）时**：仍然创建互斥体，
但不因"已存在"而退出。理由是这样才能两个实例同时跑时**至少互相知道**
对方的配置目录（日志里记一条 Warn：检测到另一个实例正在使用同一配置目录，
配置写回可能互相覆盖）。用户关掉的是一个保护，不是一个提示。

## 3. 托盘外壳

托盘菜单：**打开控制面板**、**暂停调度**（勾选项，暂停时调度线程不再触发任何 `start()`，已有注册全部保留）、**打开配置目录**、**打开日志目录**、**关于**、**退出**（走 [01-架构总览.md](01-架构总览.md) §12 的关停顺序）。

单击托盘图标 = 打开控制面板（不是"切换显示"——面板打开时再单击只是把它置前）。托盘图标随最高未读级别变化（Info/Warning/Error/Critical 四套图标），没有未读时用基础图标。

"未读"指内存历史里 `read == false` 的条目中级别最高的那一个（`read` 是**宿主独占**字段，不在 `Notification` 里、不进导出的 `.jsonl`）。"暂停调度"值得有独立菜单项，因为它是一个临时动作：用户想要的是"先别打扰我，一会儿再恢复"，而不是去插件页里挨个禁用 —— 做成一次点击 + 一个勾选状态，恢复时也不会漏掉某个插件。

## 4. 插件管理器

### 4.1 目录扫描

```
枚举 <插件目录>/*.dll（不递归）
按文件名排序              ← 保证加载顺序确定，便于复现问题
跳过共享库：sm_imgui.dll     ← 它是宿主的依赖，不是插件
            sm_curl.dll      ← 它是插件共享的依赖，不是插件
```

加载顺序**必须确定**。不确定的顺序会让"两个插件抢同一个 id"
变成"有时这个赢有时那个赢"，而这类问题几乎无法从用户报告里复现。

### 4.1.1 插件类型与插件实例

管理器把两层身份分开：

| 层 | 数量 | 携带的东西 |
|---|---|---|
| **类型**（`PluginType`） | 每个 DLL 一个 | 模块句柄、`PluginMeta` 指针、`create`/`destroy` 函数、kind、声明的设置 schema 与订阅、校验结果、实例计数 |
| **实例**（`Record`） | 每个 `[[instances]]` 行一个 | 实例 id、所属类型、自定义名、状态、`sm_create_plugin` 对象、`PluginSettings*`、调度槽、统计、`pending_removal` |

发现阶段只为每个 DLL 建一条类型；随后 `SynchronizeInstances` 按
`config.toml` 的 `[[instances]]` 建实例。已校验通过、**零实例且无墓碑**
的类型会得到一条 canonical 实例（`id = 类型 id`）—— 这是"插件放进目录
就可用"的延续；`[removed_types]` 墓碑阻止用户删空的类型被自动复活。

`MakeHostSetup` 填给插件的 `plugin_id` 与 `own_config_path` 都是**实例 id**，
因此日志来源、设置文件、调度槽、规则目标天然按实例隔离，SDK 与 ABI 不变。

**模块的生命周期按类型引用计数**：只有当该类型不再有任何实例记录时才
`FreeLibrary`；卸载时把指向 DLL 内存的 `meta`、函数指针与订阅 span 全部
置空（显示用的字符串在发现阶段已复制，安全模式与拒绝原因仍可展示）。
重新添加实例时若模块已卸载，会重新 `LoadLibrary` 并**重新走 12 条校验**；
失败则回滚刚写入的配置条目。

**删除实例是延迟的**：调度线程可能正卡在该实例的 `start()` 里。
`RemoveInstance` 先把配置落盘、把实例标记为 `pending_removal` 并从调度器
摘除，然后每帧检查 `scheduler->IsExecuting(id)`；为假时才
`stop → exit → destroy → 删设置文件 → 从记录表删除`。期间该行不出现在
快照里，管理 API 也拒绝再改它。

### 4.2 加载校验

逐条执行 [插件开发/01-入门.md](插件开发/01-入门.md) §2.2 的 12 条检查。
**任一失败都要做到【日志 + 控制面板可见 + 计入统计】三件事。**

### 4.3 DLL 搜索路径

**必须**使用受限搜索：

```cpp
// Win8+ / Win7+KB2533623
SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_DEFAULT_DIRS);
AddDllDirectory(exe_dir);
AddDllDirectory(plugin_dir);
LoadLibraryExW(path, nullptr, LOAD_LIBRARY_SEARCH_DEFAULT_DIRS);
```

`sm_imgui.dll` 在 exe 目录下，插件目录里也可能有插件自带的其他依赖 DLL，
因此**两个目录都必须加入搜索路径**。否则 `notifier.imgui.dll` 会以
`ERROR_MOD_NOT_FOUND (126)` 失败（见 [插件开发/01-入门.md](插件开发/01-入门.md) §7.2）。

**降级路径**：若 `SetDefaultDllDirectories` / `AddDllDirectory` 不可用
（Win7 未打 KB2533623），退化为 `SetDllDirectoryW(exe_dir)` 并记一条 Warn
说明当前搜索路径未被完全收紧。**加载失败时必须把 `GetLastError()` 的
数值与文本一并写进日志** —— 否则 126 号错误看起来和"文件不存在"
一模一样，而真相往往是缺少某个依赖 DLL。

### 4.4 插件状态

| 状态 | 含义 |
|---|---|
| `Discovered` | 已发现且元信息校验通过，未加载 |
| `Rejected` | 元信息校验失败，附拒绝原因 |
| `Loaded` | DLL 已加载，实例已创建 |
| `Initialized` | `initialize()` 已成功 |
| `InitializeFailed` | `initialize()` 返回 false，附错误 |
| `Running` | 已被调度 / 已接收通知 |
| `Stopped` | 被用户禁用 |
| `Disabled` | 因崩溃 / 连续超时 / `Abort` 被自动禁用（持久化） |
| `Unloaded` | `exit()` 已调用、`FreeLibrary` 已完成 |

状态与转换见 [01-架构总览.md](01-架构总览.md) §9。

**`Disabled` 与 `Stopped` 在界面上必须能区分**：前者是"它出问题了，我帮你
关了"，后者是"我主动关的"。混在一起会让用户以为软件自己乱动设置。

### 4.5 禁用必须持久化（并且要能恢复）

崩溃 / 连续超时 / `Abort` 导致的禁用会写进 `config.toml` 对应
`[[instances]]` 行的 `enabled = false`（只影响出问题的那个实例），
并在日志里记 Error。

但**持久化必须能撤销**，且撤销路径要在用户看得见的地方：
控制面板的插件页上，被自动禁用的插件旁边显示"重新启用"按钮与
**禁用原因**。用户修好问题（改了设置、换了版本）后一键恢复。

**自动恢复尝试**：被自动禁用的插件在**下一次启动**时**不**自动重试加载。
理由是把"重试"变成一个显式动作，比让用户面对一个反复自崩的程序好。

## 5. 异常隔离

### 5.1 崩溃屏障

每一次跨边界的插件调用（`initialize` / `start` / `stop` / `exit` /
`on_notify` / `on_action` / `draw_ui` / `draw_view` / 主线程任务函数）
**都**包一层 SEH 屏障：

```cpp
// seh_guard.cpp —— 这个文件是【唯一】允许使用 __try/__except 的地方
bool guarded_call(void (*fn)(void*), void* user, std::uint32_t* out_code);
```

**实现约束（很容易踩，必须照做）**：

1. `guarded_call` **自身不得包含需要栈展开的 C++ 对象**（不能有带析构的
   局部变量、不能有 `std::string` 之类的临时量）。MSVC 会以
   `C2712`（不能在要求对象展开的函数中使用 `__try`）直接拒绝编译。
   所有需要在屏障外侧做的事，都放到另一个函数里。
2. 该文件应当用 **`/EHa`** 单独编译（或整个项目用 `/EHa`），
   以便把"被当作 SEH 抛出的 C++ 异常"也一并捕获。
3. 捕获后把异常码（`GetExceptionCode()`）写进 `out_code`，
   **不要**尝试继续执行插件的其他代码 —— 直接进入禁用流程。
4. **绝不在屏障内做恢复。** 屏障的产物只有两个：一个布尔值和一个错误码。

### 5.2 崩溃后做什么

```
1. 记 Error 日志：插件 id + 异常码（含异常码的文本解释）+ 触发的方法名
2. 强制 flush 日志（见 §12.5）—— 崩溃之后写出的每一行都极其宝贵
3. 结构性事件通知（不受 notify_log_level 控制）
4. 若插件已 Running：标记为 Disabled，持久化到配置
5. 从调度器/路由表中摘除该插件
6. 走 §4.4 的卸载路径：exit() → FreeLibrary
```

**卸载（`FreeLibrary`）是必须的**：崩溃过的插件**进程内状态不可信**，
继续调用它等于赌运气。卸载的代价是这个插件本次运行彻底不可用 ——
这正是我们想要的：一个崩溃的插件不该有机会再崩第二次。

### 5.3 看门狗（标记，不杀）

一次 `start()` 超过阈值（默认 **30 秒**）即认定为"无响应"：

```
if (start_end - start_begin) > 30s:
    记 Warn：插件 id + 耗时
    该插件的连续超时计数 += 1
    if 连续超时计数 >= 3:  标记为 Disabled 并持久化
    （本次产出若有数据仍然正常入队）
```

**连续超时计数在任一次正常返回时清零**（被看门狗打断的那一次不算"正常返回"）。

**宿主不杀线程、不杀进程。** 理由已在 [01-架构总览.md](01-架构总览.md) 说明。
宿主能做的是两件事：

1. **请求协作取消**：`is_cancelled()` 返回 `true`，插件应当在自己的耗时
   循环里检查它并尽快返回（见 [插件开发/02-SDK接口参考.md](插件开发/02-SDK接口参考.md) §6.3）。
2. **标记并隔离**：把状态显示在界面上，让用户知道该关掉哪个插件。

### 5.4 谁来看门狗

调度线程正卡在插件代码里，**它自己发现不了超时**。因此需要第三方观察，
选**主线程**（它是唯一在等待中、可以被定时唤醒的线程）：

- 调度线程在每次调用 `start()` 前把 `(插件id, 开始时刻)` 写进一个
  原子可见的"在执行标记"，返回后清空。
- 主线程的消息等待超时设为 **1000 ms**，每次醒来检查该标记。

> **代价**：空闲时主线程每秒被唤醒一次（实测 CPU 占用仍为 0%，一次唤醒是
> 微秒级）；替代方案（专门的看门狗线程）要多一条线程与一份栈，更不划算。

## 6. 调度器

调度循环、最小堆、退避规则、arena 上限见 [01-架构总览.md](01-架构总览.md) §7。
这里补充实现细节。

### 6.1 接口

```cpp
class Scheduler {
 public:
  void start();                              // 启动调度线程
  void request_stop();                       // 置关停标志 + signal
  void join();                               // join，带宽限期
  void wake();                               // 打断等待（新注册/取消调度/关停）
  void set_paused(bool paused);              // 托盘"暂停调度"

  // 由 IHostContext 的 schedule_next / schedule_at 调用（调度线程内）
  void schedule_next(Plugin&, std::int64_t delay_ms);
  void schedule_at(Plugin&, std::int64_t unix_ms);

  // 由插件管理器调用（主线程）
  void add(Plugin&);                         // 插件进入可调度集合
  void remove(Plugin&);                       // 插件被禁用/卸载
};
```

**`wake()` 是必需的**：`schedule_next(50)` 在等待是 10 分钟的情况下，
如果不打断等待，这个"50 毫秒后"就会变成"10 分钟后"。任何修改堆的操作
都必须 `wake()`。这是个容易漏的地方 —— 漏了的症状是"调度有时候晚很久"。

### 6.2 数据结构

```
min-heap: vector<Entry{due_monotonic_ms, Plugin*}>
每插件一个 schedule slot（不在堆里，在 Plugin 上）：
    next_due_monotonic_ms   （是否在堆中由 in_heap 标志区分）
    consecutive_failures
    consecutive_timeouts
    base_delay_ms           （插件注册的间隔，退避乘数的基数）
```

- 堆里**最多一个** `Plugin*` 条目。`schedule_next` 在同一个 `start()` 里
  被调用两次时，只需更新 `next_due_monotonic_ms` 后做一次
  `sift_down`（或"标记脏 + 重新入堆"）。
- **插件被禁用/卸载时必须从堆里摘除。** 不做这一步的话，堆里会留下指向
  已释放内存的指针。建议做法：堆元素带一个"代际号"，
  弹出时校验代际号是否仍匹配，不匹配就丢弃。

### 6.3 时间基准

- **堆排序与等待用单调时钟**（`platform::monotonic_ms()`）。
- **`schedule_at(unix_ms)` 在入堆时换算一次**成单调时刻（记下换算时的
  墙钟偏移）。因此用户在插件注册之后修改系统时间**不会**影响已注册的
  绝对调度 —— 这是刻意的：用户改时钟时往往在调时区或校时，
  让一批"每天 9 点"的任务因此提前/推迟触发，是纯粹的意外。
- **过期保护**：一个任务的 `due` 时刻若已过去超过一个宽限期
  （建议 60 秒，例如机器休眠了 3 小时后唤醒），宿主记一条 Debug 日志
  然后**跳过本次执行、按插件的常规间隔重新注册**。
  不补跑：3 小时里欠下的 12 次执行一次性补上，只会产生 12 条重复通知。

### 6.4 并发与实现约束

- 三条并发铁律：`heap_` / `slots_` / `executing_` 受 mutex 保护，且**插件
  代码一律在锁外运行**；任何改堆之后必须 `wake()`；调度线程绝不把 `Slot*`
  带出锁外（只带 plugin id）。
- 空闲等待是 60 秒：某条路径忘了 `wake()` 的后果是"晚最多 1 分钟"，
  不是"从此不动"。
- 对不可调度插件（已禁用 / Notifier）的注册一律忽略 —— 凭空建槽位等于让
  禁用的插件复活。
- 过期任务**不补跑**（见 §6.3）：3 小时欠下十几次执行，补上只会产生十几条
  重复通知。
- 连续超时计数**只在本次没被看门狗打断时**清零（否则每轮卡 40 秒的插件
  永远凑不满 3 次）。
- 退出时两个 waiter **故意不销毁**（线程还活着会用到）：几百字节泄漏换
  "退出途中不踩已释放的事件对象"。
- `slot.last_error`（面板错误汇总）必须由调度器落定：等待时长与连续次数
  只有调度器知道。

## 7. 通知管线

### 7.1 入队

```
被 Source 返回的一条 Notification：
  1. 填入 source_plugin（= 该 Source 的【实例 id】，例如 source.email@2）
  2. 长度截断（title/content/url/icon/topic/id/actions），超限记 Warn
  3. summary 有值 → 归一化空白；没有就留空，交给 auto_summary 规则
  4. 跑【来源阶段】规则（目标包含该来源的 auto_summary 与 match 规则）：
     丢弃 → filtered_source++，结束；有改写 → 写回字段
  5. 规则改写过 → 按 SDK 上限再截断一次，summary 重新归一化
  6. 校验必填项（title / content / topic 非空）——缺失则丢弃并记 Warn
  7. 若 id 非空且队列里已有【同一来源实例 + 同 id】→ 原地更新（保留原 seq，不动位置），结束
  8. 否则分配 seq（自增，从 1 开始），入队
  9. 入队后按需丢弃最旧的（见 7.2）
```

**去重键是 `(source_plugin, id)` 而不是 `id` 单独**：两个邮箱实例可能同时
报告消息号 `42`，两个 Gotify 服务也可能都从 `1` 开始编号。只看 `id` 会让
一个实例的通知覆盖另一个实例的 —— 而且症状是"某条通知偶尔不出现"，极难排查。

**来源规则跑在必填校验之前**：这条顺序让规则可以**补上**缺失的 title /
content（例如从 topic 生成标题），而不是只能看着它被丢掉。

**第 6 步的"丢弃"是校验里唯一会丢数据的一处**，且只针对"连标题都没有"的
通知 —— 这种数据没有任何 Notifier 能合理呈现。规则丢弃是用户显式配置的
行为，单独计入 `filtered_source`，与这里的 `rejected` 分开。

**第 5 步的"原地更新"**：更新之后**不重新分配 seq**，也不移动它在队列中的
位置。更新的是内容，不是"用户又没看过" —— 因此 `seq` 与 `read`（已读）**一起保留**。
Notifier 用 `seq` 判断"是不是新到的"，如果更新也换 `seq`，
那么每条刷新式通知都会被当成新通知弹出浮层 —— "未读邮件数"就会变成刷屏器。

**动作数组的截断**：超过 `kMaxActionsPerNotification` 的尾部被丢弃并记 Warn。
保留前几个而不是随机几个，因为插件通常按重要性排序声明动作。

### 7.2 背压

队列容量 `kNotificationQueueCapacity`（1000）。

**满时的策略是"丢弃最旧的"，不是"拒绝最新的"。**

> **为什么不拒绝最新的**：队列满说明消费端（UI 或某个慢 Notifier）跟不上，
> 而最新的一条通常最重要（最新的错误、最新的告警）。代价是**旧通知会消失**，
> 因此丢弃时**必须计数**（见下），并在控制面板的"概览"页显示"已丢弃 N 条"。

```
丢弃计数：dropped_count
每次丢弃 +1，并记一条 Debug 日志
当 dropped_count 从 0 变为非 0，且距上次报告超过 10 秒：
    记一条 Warn："通知队列已满，已丢弃 N 条最旧的通知"
    并把 dropped_count 归零
```

### 7.3 历史

内存历史保留最近 `min(notification_history_size, kNotificationHistoryCapacity)`
条，**只增不删**（除了被容量挤掉）。

- `draw_ui(history)` 传给每个 Notifier 的是**按它的订阅过滤后**的视图。
- 控制面板的"通知"页显示的是**未过滤**的完整历史。
- 历史中的通知由宿主拥有，**跨帧稳定**（这正是"插件不得缓存投递的
  `Notification&`"这条规则的另一半：宿主给你的引用只在回调期间有效，
  但 `seq` 在历史的生命周期内稳定，用它做索引）。

### 7.4 消费顺序

每帧按 [01-架构总览.md](01-架构总览.md) §8.4 的五步顺序。补一点实现细节：

- **消费是批量的**：一帧内最多消费 `min(队列长度, 64)` 条。
  不设上限的话，一次积压 1000 条会让这一帧的 UI 卡住几秒钟。
  剩下的下一帧继续 —— 界面保持响应比"尽快清空队列"重要。
- 队列**被清空**（而不是"每帧清空"）后，UI 会话引用计数才有机会变化
  （Notifier 在此过程中调用 `request_ui_surface`）。
- **路由之后、`on_notify` 之前跑投递阶段规则**（见 §7.6）。投递规则丢弃
  只让这一个 Notifier 收不到，历史与其它 Notifier 不受影响；因此它单独
  计入 `filtered_delivery`，**不算**"未被投递"。

### 7.5 图标

`Notification::icon` 只描述"图在哪"，**投递路径不做网络 I/O** —— 否则一个慢
URL 会卡住整条通知管线。Notifier 在绘制时通过 `IHostContext::icon_texture()`
取纹理，宿主按下面的路径处理：

1. 按来源字符串在进程级的 `ImageCache` 里查；成功与失败都缓存。
2. 未命中则起一条 detached 工作线程：http(s) 走 libcurl（最多跟随 3 次重定向，
   连接 5 秒、总计 15 秒，响应 8 MiB 上限，**只允许 http 与 https**）；
   `file://` 与本地路径直接读文件（相对路径按 `data_dir()` 解析，同样 8 MiB）。
3. 用系统 WIC 解码（PNG / JPEG / BMP / ICO），源图超过 4096×4096 判定失败，
   解码后最长边缩到 256 px。
4. 主线程再次调用时把 RGBA 上传成**当前表面渲染上下文**的纹理，并按来源在
   该 UI 运行时内复用；运行时销毁时统一释放。

**失败被缓存**（`out_failed = true`），所以一个坏 URL 不会每帧重试；缓存按
"超过 10 分钟未被请求"与 128 条上限淘汰。**纹理按表面缓存**：DX11 设备是进程
共享的，但 GL 上下文不是 —— 同一条通知的图标在通知表面与详情窗口里是两张
纹理，这是正确的。

### 7.6 规则中间层

`rules.cpp` 是宿主里唯一同时被**调度线程**（来源阶段，在 `Admit` 里）与
**主线程**（投递阶段，在 `PumpMainThread` 里）执行的业务模块。它不认识插件，
只接收一份字段视图与两个 id：来源 id、Notifier id。

```
来源阶段（Admit，调度线程）：
  深拷贝字段 → summary 归一化 → 跑目标包含该来源的 auto_summary / match 规则
      → 启用 save 的命中：取该规则 rewrite 之后的字段快照并落盘
      → 丢弃？ filtered_source++，结束
      → 有改写？写回 owned，按 SDK 上限再截断，summary 重新归一化

投递阶段（PumpMainThread，主线程，每个匹配的 Notifier 之前）：
  对历史里的字段建一份临时视图 → 跑目标包含该 Notifier 的 match 规则
      → 启用 save 的命中：同一条规则对同一条通知只落盘一次
      → 丢弃？ filtered_delivery++，这个 Notifier 收不到（历史不变）
      → 有改写？用临时字符串搭一个 Notification 视图传给 on_notify
```

**来源目标匹配有类型回退。** 规则的 `target.source` 先按完整实例 id
（`source.email@2`）做 `regex_match`；没命中且实例带 `@N` 时，再用类型 id
（`source.email`）试一次。因此 `'^source\.email$'` 命中该类型的全部实例，
而 `'^source\.email@2$'` 只命中第二个。`target.notifier` 不回退 —— Notifier
每种类型只有一个实例，id 恒等于类型 id。

**每条规则的保存快照在它自己的 `rewrite` 之后取得。** `ApplySource` /
`ApplyDelivery` 在命中一条 `save.enabled` 的规则时，把规则下标与**此时**的
title / content / summary / level 推入 `RuleSaveHits`。管线在 `drop` /
`handle` 的提前返回之前消费这些快照，因此：

- 同时写了 `rewrite` 与 `save` 的规则，落盘的是重写后的值；
- 同趟后续规则的改写不会污染前一条规则的快照；
- 来源趟即使随后丢弃通知，也已经写出这一条。

`rules.cpp` 只负责产生快照，不碰文件系统；`rule_save.cpp` 负责路径解析
（`placeholders.cpp` 展开占位符）、追加写入与有界告警。是否真正写文件由
`NotificationPipeline` 的全局开关（`[app] allow_rule_save`）决定，安全模式
强制关闭。保存失败只在锁外记一条 Warn，不影响投递，也不会经日志→通知桥
递归刷屏（保存调用包在 `NotifyScope` 里）。

**规则集是 `std::shared_ptr<RuleSet>`，整体替换。** `SetRules` /
`RulesSnapshot` 用一把小锁换一份快照，然后立刻释放锁；正在处理的通知继续
持有旧实例直到本次调用结束。因此重载 `rules.toml` 不需要暂停调度线程，也
不会让 `Admit` 与 `PumpMainThread` 竞争同一份可变状态。

**启用状态与命中计数**都在 `RuleSet` 内部（原子量）。启用状态只是
`config.toml [rules]` 的运行时副本；命中 / 拦截计数属于当前实例，重载后
新实例从零开始（见 [03-控制面板.md](03-控制面板.md) §5.1）。

规则的完整 TOML 语法、表达式与重写模板见
[插件开发/03-配置格式.md](插件开发/03-配置格式.md) §9。

## 8. 路由

```
对每条通知：
    对每个已加载且启用的 Notifier：
        取它的有效订阅模式集合
            = config.toml 的 [routing] 里显式列出的（完全覆盖）
            = 否则用 PluginMeta::subscriptions
        若集合为空（元信息里也没声明）        → 匹配（收到全部）
        若存在任一模式能匹配 notification.topic → 匹配
```

### 8.1 模式匹配规则

| 模式 | 匹配 |
|---|---|
| `"mail.inbox"` | 仅 `mail.inbox`（精确） |
| `"mail.*"` | `mail` 及其下任意层级：`mail.inbox`、`mail.inbox.spam` |
| `"sm.host.*"` | `sm.host.log`、`sm.host.plugin`… |

**实现要点**：`"mail.*"` 匹配的是"`mail.` 前缀"，**不匹配 `mail` 本身**
（那样会让 `"mail.*"` 隐含地等价于 `"mail"` + 子级，容易造成意外）。
需要两者都收就写两个模式。

**路由本身不支持正则。** 正则会让"这个插件收不到通知"变成一个需要动脑子
的推理题；需要正则的过滤/改写交给 §7.6 的规则层（那是一个显式的、用户
逐条写下的中间层，不是路由语义的一部分）。

### 8.2 多条匹配是特性

一条通知**可以**命中多个 Notifier（既弹浮层又归档）。
**不存在"最长前缀优先所以只选一个"这回事** —— 路由是广播，不是单播。

广播 + 订阅过滤比"只发给最匹配的那个"更简单也更强 —— 后者会让"归档 + 弹窗"
这种完全正常的组合无法表达，用户得发明一种"多播"的额外语法。

### 8.3 路由表缓存

路由表在以下时机重建（不是每帧重建）：

- 插件集合变化（加载 / 卸载 / 启用 / 禁用）；
- `[routing]` 配置变化；
- 插件的订阅在元信息里变化（只可能在加载时发生）。

> **重复注册同一插件 id 的多个实例**：加载校验的第 12 条拒绝了重复的
> `PluginMeta::id`（[插件开发/01-入门.md](插件开发/01-入门.md) §2.2），
> 且 Notifier 每种类型只允许一个实例（实例 id 恒等于类型 id），
> 因此路由表的键（Notifier 实例 id）天然唯一。
>
> Source 的多个实例不会进这张表 —— 它们各自往管线投递，`source_plugin`
> 是实例 id，来源侧不需要"注册"。

### 8.4 不匹配的通知

一条通知**没有任何** Notifier 接收时：

- **不丢弃**（它仍然进历史、仍然在控制面板的"通知"页可见）；
- 记一条 **Debug** 日志（不是 Warn —— 用户可能就是要让某类通知只进历史）；
- 计入概览页的"未被投递"统计。

**投递阶段规则丢弃的不算这一类**：那是用户显式配置的"这个 Notifier 不要
收"，通知本身仍可能被别的 Notifier 接收、也仍在历史里。两者分开计数
（`filtered_delivery` 与 `undelivered`），否则"规则把某个 Notifier 挡掉了"
会被误读成"没有 Notifier 订阅这个 topic"。

> 记 Debug 而非 Warn："通知没弹出来"常因"没有 Notifier 订阅这个 topic"，
> 但每条都记 Warn 会让日志对"就想让它只进历史"的用户失去意义。

### 8.5 动作分发与"已读"

分发一个 Action 时，**在路由之前**就把该条通知标为已读 —— "用户点了他
屏幕上那张卡片"与"哪个 Notifier 响应这个动作"是两件事；放在路由之后会让
"没人订阅这个 topic"的点击永远清不掉未读。通知类事件（入队、路由、投递）
只写 `Trace` / `Debug`，不进 `Info`（见 §12.7）。

## 9. 宿主自身的通知源（`sm.host`）

宿主也是一个通知来源，走**同一条**管线 —— 一个内建的虚拟 Source：`id = "sm.host"`（保留命名空间，插件不得使用），在插件列表里显示为"宿主"且**不可禁用、不可卸载**，不进 `[[instances]]` 配置表（它不是实例，也没有设置文件）。它**不通过 `start()` 产生数据**，而是**事件驱动**：事件发生的那一刻，宿主直接往管线里投递一条。

四个 topic：`sm.host.log`（由日志转成的通知，见 §10）、`sm.host.plugin`（加载被拒绝 / 初始化失败 / 崩溃 / 被自动禁用 / 超时）、`sm.host.config`（解析失败 / 迁移 / 写回失败 / `schema_version` 过高）、`sm.host.lifecycle`（宿主启停）。

**结构性事件**（插件加载被拒绝 / `initialize()` 失败 / 崩溃 / 连续超时被禁用 / `Abort`、配置解析失败 / `schema_version` 过高 / 写回失败、宿主启动与退出）**始终**产生通知，**不受** `[app] notify_log_level` 控制。理由：用户调低阈值想要的是"别拿日常消息烦我"，而不是"别告诉我东西坏了"。

## 10. 日志 → 通知 桥

### 10.1 映射与阈值

| `LogLevel` | → `Level` |
|---|---|
| `Error` | `Error` |
| `Warn` | `Warning` |
| `Info` | `Info` |
| `Debug` / `Trace` | **永不转换** |

阈值来自 `[app] notify_log_level`（默认 `"error"`）：

| 值 | 转换的日志级别 |
|---|---|
| `off` | 无（结构性事件仍然通知） |
| `error` | `Error` |
| `warn` | `Error` + `Warn` |
| `info` | `Error` + `Warn` + `Info` |

**`Debug` / `Trace` 永远不转换**，无论阈值设成什么。它们的存在意义是
"写进日志文件"，而不是"通知用户"。

### 10.2 通知的内容

| 字段 | 取值 |
|---|---|
| `title` | 级别名 + 插件 id，如 `"错误 · source.mail"` |
| `content` | 日志消息体（不含前缀） |
| `topic` | `sm.host.log` |
| `level` | 按上表映射 |
| `id` | **为空**（日志是流式事件，不做去重） |
| `time_unix_ms` | 该条日志的时间 |

### 10.3 防递归：不可绕过的来源标记

**最危险的一件事**：通知的产生与投递本身会写日志
（例如"投递失败"、"未匹配到任何 Notifier"）。如果这些日志又能变成通知，
就是一个自我维持的环 —— 一条日志变成通知，通知处理时又写日志，
那条日志又变成通知……

**破解方式**：给"正在处理通知"这件事打上一个**插件无法影响**的标记。

```cpp
// 线程局部。宿主在【开始处理任何通知相关的工作】时进入，
// 处理完毕时退出。处理期间产生的所有日志都不会被桥接成通知。
thread_local int tls_notify_depth = 0;

struct NotifyScope { NotifyScope()  { ++tls_notify_depth; }
                     ~NotifyScope() { --tls_notify_depth; } };

bool should_bridge(const LogRecord& r) {
  if (tls_notify_depth > 0) return false;   // ← 递归中断，第一条防线
  ...
}
```

**为什么说"不可绕过"**：这个标记不是插件能设置的东西 —— 它由宿主在
进入通知处理路径时设置，插件既看不到也改不了。插件能做的最坏的事是
"在自己的 `on_notify` 里写日志"，而那些日志在 `tls_notify_depth > 0`
的作用域内产生，天然不会被桥接。

### 10.4 限速：`sm.host.log` 的合并计数

```
每 10 秒一个窗口。
窗口内 sm.host.log 的通知数 > 5 时：
    前 5 条正常投递。
    其余的不投递，已合并计数 merged += 1。
窗口结束时若 merged > 0：
    投递一条汇总通知：
        title   = "还有 N 条类似日志"
        content = "（同类日志已合并）最近一条：<被合并中的最后一条消息>"
        id      = "sm.host.log.merged"    ← 用同一个 id 保证同一窗口只留一条
```

**结构性事件（`sm.host.plugin` / `sm.host.config` / `sm.host.lifecycle`）
不受本限速影响** —— 它们本来就不该高频。

> 用"合并计数"而非"静默丢弃"：静默丢弃会让用户以为"只有 5 条错误"，
> 而实际有 200 条；合并计数传递真实信息量，也不会把界面变成无法阅读的列表。

## 11. UI 会话管理

引用计数模型、创建/销毁时机、渲染循环形态、每帧顺序约束见
[01-架构总览.md](01-架构总览.md) §8。这里补齐实现细节。

### 11.1 会话对象

```cpp
class UiSession {
  // 三个引用来源，各自独立统计；面板与通知表面由本类直接管，
  // 详情表面每个插件一扇，窗口与运行时由 App 按 views 列表同步
  bool panel_open = false;                // [面板] 控制面板是否打开（0 或 1）
  struct SurfaceRef { std::string plugin_id; std::int64_t expires_ms; };
  std::vector<SurfaceRef> surfaces;       // [浮层] request_ui_surface(duration > 0)
  struct ViewRef { std::string plugin_id; std::string title; };
  std::vector<ViewRef>    views;          // [视图] set_view_title 且未 close_view

  bool panel_alive()  const;   // panel_open          → 面板窗口
  bool notify_alive() const;   // !surfaces.empty()   → 通知表面
  bool detail_alive() const;   // !views.empty()      → 一台或多台详情窗口（App 管）
};
```

- **`request_ui_surface(duration_ms > 0)`**：找本插件已有的项，
  把 `expires` 设为 `max(现有, now + duration)`；没有就新增。
- **`request_ui_surface(duration_ms <= 0)`**：插入一个
  `expires = INT64_MAX` 的项（永不到期），只能由 `close_view()` 归还。
- **`close_view()`**：移除本插件的 `INT64_MAX` 项，并清掉 `views` 里
  本插件的项。**只影响本插件** —— 控制面板与其他插件的浮层不受影响。
- **浮层引用只作用于通知表面**：`request_ui_surface` 不再让控制面板弹出来，
  面板打开着也不因为浮层到期而关掉（[03-控制面板.md](03-控制面板.md) §1.3）。
  面板、通知、详情三类引用的存活条件**各算各的**：面板只看 `panel_open`，
  通知表面只看 `surfaces`，详情表面只看 `views`。
- **引用不另存计数**：三种引用里只有 [面板] 是一个开关，另外两种就是那两个
  容器本身。存一份计数的写法必然要有人在每个 push/erase 旁边同步它，而漏掉
  一处的结果是"浮层还在、会话却被销毁"。
- 每帧第 4 步（`Tick`）：先剔除到期的浮层引用，再对**面板与通知表面**各判一次
  "该不该活着"，各自给出"刚创建 / 刚销毁 / 没变"三个结论之一。要两个结论而不是
  一个，是因为同一帧里"面板关了、通知来了"是常规情况，而调用方对这两张表面要做的
  事不同（面板要保存位置尺寸，通知表面不用）。详情窗口不参与 `Tick`：App 每帧
  把 `views` 与自己的窗口集合对齐（新增、改标题、删除），见 §11.5。
- **运行时不在这里造**（DIP）：面板的运行时由应用在启动时注入（窗口一直在，只是
  隐藏），通知表面的运行时由一个**工厂**按需提供 —— 那扇窗口要先按
  `[notify_window]` 摆好、要多大由内容决定，都是应用的事（见 §11.6）。
  详情窗口更彻底：窗口、运行时、标题、摆放全部由 App 管理。会话只判断"该不该
  有"，造不出来时（窗口或设备失败）退化为"没有界面"并**不每帧重试** —— 一个
  通知弹不出来不该让宿主每帧建一次窗口。

### 11.2 会话的创建

创建开销（按顺序，都不可省）：

```
1. ImGui::CreateContext()
2. 填 ImGuiIO（键盘/显示尺寸/DPI 缩放）
3. 加载字体图集（见 §13）—— 实测几毫秒（常用简体字集）
4. ImGui_ImplGlfw_InitForOther(window)     ← 输入（键盘/鼠标/IME/滚轮）与显示尺寸
5. 渲染后端 Init(window)：建设备与交换链，并 ImGui_ImplDX11_Init /
   ImGui_ImplOpenGL3_Init —— 由后端自己挑，后端接口（`render_backend.h`）之上
   看不到这两种上下文
6. 字体纹理由渲染后端在首帧按需创建
```

**一张表面一份**：面板与通知表面各调一次上面这一串，各自有自己的
`ImGuiContext`、后端数据与字体图集（§13）。窗口后端那份调的是
`InitForOther` 而不是 `InitForOpenGL` / `InitForDX11`：它在这里只负责输入与
显示尺寸，绘制由渲染后端自己做（后端接口是 DIP 的落点，会话不认识 D3D 与 GL）。

**第 4 步必须在建完窗口之后**：imgui 的 GLFW 后端收的是那个窗口的平台句柄，
它把回调装到窗口上（`glfwSet*Callback`），窗口没了它就没有落脚点。

**还有两条必须改掉的 imgui 默认值**：`io.IniFilename = nullptr`（窗口位置与
尺寸由宿主的 `ui_state.toml` 管，imgui 自己那份 ini 是同一件事的第二份真相，
两处必然打架），以及 `ImGui::GetStyle().DisplaySafeAreaPadding = 0`（默认那
一圈边距是给真实屏幕留的，对"窗口尺寸由内容决定"的那张表面是致命的，见 §11.6）。

**建之前再折算一次**：启动时的探测只能决定"建窗口时要不要图形上下文"，
而窗口**实际**拿到了什么，要等窗口建出来才知道 —— 所以真正建后端时调的是
`ResolveAgainstWindow(renderer_, window->client_api())`。请求了 OpenGL 而驱动
没给上下文的机器，正是靠这一步落到 DX11 上（见 `render_probe.cpp`）。

> **第 6 步没有对应的公开函数**：imgui 1.93 的 DX11 后端里
> `ImGui_ImplDX11_CreateFontsTexture()` 已是内部实现（字体纹理走
> `ImTextureData` + `ImGui_ImplDX11_UpdateTexture()` 自动上传），
> 外部只需保证 `ImGui_ImplDX11_NewFrame()` 被调用 —— 它会自己补齐设备对象。
> 重建字体（改字号）同理：`io.Fonts->ClearFonts()` 后重新装字体即可，
> **不要**手工去调不存在的 `CreateFontsTexture`。

**创建是同步的、发生在主线程**，因此会造成一次可见的卡顿。
实测（见 §17）这个卡顿几乎全部来自 **D3D11 设备的创建**（进程内第一次
约 900 ms，是驱动初始化；同一进程内的后续会话约 126 ms），
字体图集只占其中个位数毫秒。缓解手段：字体图集用**最小必要字符集**
（`GetGlyphRangesChineseSimplifiedCommon()` 而不是全部 CJK，见 §13），
并且**只在真正需要时创建**（用户第一次打开面板，或第一条浮层出现）。
绝不在启动时预建。

### 11.3 会话的销毁

```
1. ImGui::SetCurrentContext(这一张表面的上下文)
2. 渲染后端 Shutdown()     ← 内含 ImGui_ImplDX11_Shutdown / ImGui_ImplOpenGL3_Shutdown
3. ImGui_ImplGlfw_Shutdown()
4. ImGui::DestroyContext()
5. 归还本表面这一份设备引用（设备共享，最后一个持有者走时才真的放掉，§11.4）
```

**第 1 步不能省。** imgui 的"当前上下文"是**线程级的单例**，而宿主有多张
表面（面板、通知、各详情窗口）。两个后端的 `Shutdown` 都是按"当前上下文里的
后端数据"取自己的句柄 ——
拨错了上下文，拆掉的是**另一张表面**的后端，那张表面在下一帧就没有窗口后端了。
创建那一侧同样要自己管住：`CreateContext()` 在"调用前已经有别的上下文"时会
**把上一个恢复成当前**，于是第二张表面刚建出来的上下文立刻不再是当前，紧接着的
`io` / 样式 / 字体图集 / 两个后端初始化会全部落到另一张表面上去。
**每建一帧、每建一次、每拆一次，都显式地把当前上下文拨到自己这一张上。**

**必须销毁得彻底**：留下任何一个句柄都会让下一轮的
`CreateContext` 出错（imgui 的全局状态是按上下文分组的单例，宿主要自己保证
"哪一份是当前"）。因此实现上要求
**创建/销毁都是幂等的、成对的**，并用一个不变量检查
（Debug 构建下：会话的 `alive()` 为 false 时，imgui 上下文必须是 `nullptr`）。

### 11.4 渲染设备与交换链的生存期

**设备共享，交换链不共享**：

| 东西 | 生存期 | 为什么 |
|---|---|---|
| D3D11 设备 | **进程级一份**，由所有表面（面板、通知、详情窗口）共享，最后一个持有者走时放掉 | 一个窗口一个独立设备在 DX11 里是允许的，代价是成倍的显存与驱动状态，而所有表面画的是同一个界面的各部分 |
| 交换链 | **每扇窗口一条**，随会话创建/销毁 | 它绑在窗口的 `HWND` 上，是窗口的属性，不是设备的属性 |
| 字体纹理 | 每个上下文一份（§13） | 图集属于上下文 |

"随会话创建/销毁"这条取舍仍然成立：每张表面的会话都不是常驻的
（面板关掉、浮层到期就销毁），**空闲时设备与显存占用仍为 0**。代价是
每次重建设备（实测首次约 900 ms，同进程内后续约 126 ms，见 §17.1），
只在用户主动打开面板、或第一条浮层出现时体现一次。

OpenGL 后端没有"交换链"这个对象，**也没有可共享的设备层**：GL 上下文由 GLFW
在建窗口时一并给出，**每扇窗口一份**（`ClientApi`，见 `platform/window.h`），
每帧还要重新绑定一次 —— "当前上下文"同样是线程级状态，进程里不止一扇窗口。
这些差别被 `render_backend.h` 挡在会话之外。

### 11.5 详情的承载

详情视图是**每个插件一扇的独立普通窗口**：有标题栏、可缩放、可最小化，
不是 imgui viewport、不是控制面板里的视图页、也不是模态框。窗口里只调用该
插件的 `draw_view()`，不绘制控制面板的任何一页。

**打开详情视图不会打开控制面板。** 插件调用 `set_view_title()` 之后，App 在
下一帧发现 `views` 里多了一项，就为它建窗口、建上下文、显示出来；控制面板
保持原状（关着就还关着）。关掉控制面板也不会带走详情窗口 —— 两者的引用与
生命周期完全独立。

**同一插件只有一扇详情窗口。** 插件在已有视图时再次调 `set_view_title()`，
只更新标题与内容（例如在浮层上点了另一条通知的「详情」），不会叠加第二扇。
不同插件各自一扇；每扇窗口的关闭按钮只影响本插件。

**浮层没有这个能力**：它有自己的窗口（§11.6），一条通知不该把控制面板弹出来，
面板打开着也不该因为浮层到期而关掉（[03-控制面板.md](03-控制面板.md) §1.3）。

| 细节 | 做法 | 为什么 |
|---|---|---|
| 建窗时机 | `views` 里第一次出现该插件 | 与插件调 `set_view_title` 的语义一一对应 |
| 标题 | `set_view_title()` 的值；为空时用插件名 | 用户从任务栏也能认出是哪条详情 |
| 尺寸与位置 | 默认 720×560，主显示器工作区居中；多扇时依次错开 | 详情内容通常比浮层长，需要一扇能读的窗口 |
| 关闭 | 窗口的 ×、插件调 `close_view()`、插件被卸载 | 三种路径都只移除本插件的视图 |
| 缩放 | 各自的 `on_content_scale` 直接转给该窗口的运行时 | 几扇窗口可能分属不同 DPI 的显示器 |
| 字号 | 跟随 `[app] ui_font_size`，下一帧对存活的详情运行时 `RebuildFonts` | 设置页改字号不重启窗口 |
| 失败 | 窗口或设备建不出来时记 Warn，并记住该插件本次视图周期内不再重试 | 避免每帧建窗刷日志 |

### 11.6 通知表面

**它是什么**：第二扇窗口 —— 无边框、不进任务栏、不抢焦点、置顶，
带自己的 `ImGuiContext` 与渲染后端，上面**只**画各 Notifier 的浮层。
控制面板与详情窗口在另外的窗口里。这是"通知和主界面挤在同一扇窗口"这个原始
问题的解法：每张表面各有自己的窗口、上下文与引用计数
（[01-架构总览.md](01-架构总览.md) §8.2）。

**谁决定什么**：

| 事 | 归谁 |
|---|---|
| 摆在哪块屏幕的哪个角、离边缘多远 | **宿主**：`[notify_window]`（[插件开发/03-配置格式.md](插件开发/03-配置格式.md) §3.4），每帧现读，改了立刻生效；写错的显示器名回退主屏并记 Warn。控制面板"通知"页顶部有这两个键的控件（[03-控制面板.md](03-控制面板.md) §4.6） |
| 窗口多大 | **内容**：一帧画完之后由 `content_bounds()` 量出来（§11.1）。**内容**的宽度区间由插件的设置定（`notifier.imgui` 的 `toast_width_min/max`）—— 表面尺寸仍随内容，这条断言不变 |
| 浮层画什么、什么时候消失 | **插件**：`draw_ui()` + `request_ui_surface()` 的引用计数 |
| 一条浮层"被点掉了"之后宿主还要做什么 | **宿主**：动作分发时把它标为已读（§8.5）。插件只负责请求 `dismiss` |

**插件看不到这扇窗口。** 它不定位、不读 `io.DisplaySize`、不需要知道宿主分了
几张表面 —— 一张卡片摆在哪是宿主的事，"卡片比它贴的那块屏幕更大"由 imgui
自己的自动适配保住。

**窗口按需创建、只创建一次，之后隐藏而不销毁**：第一次真的有浮层要画时才建它
（启动、只开面板都不建），关停时才拆 —— 与面板窗口同构。窗口的**运行时**
（上下文、后端、字体图集）则跟着会话生灭（§11.1）。

| 细节 | 做法 | 为什么 |
|---|---|---|
| 每帧的顺序 | 画一帧 → 量内容 → 摆窗口 | 尺寸与位置要在同一帧里定下来，否则卡片按上一帧的尺寸重新摆一次，看起来是自己跳 |
| 内容为空 | 整扇窗口藏起来 | 浮层的窗口是不透明的：一扇盖在工作区上的空窗口用户点得到、却什么都看不见，还会挡住下面的窗口 |
| 显示 | `Show(focus = false)` | 通知不该把用户正在打字的那扇窗口挤到后面 |
| 定位 | 按**客户区**算，离工作区边缘 16 像素 | 无边框窗口的客户区就是整扇窗口，不差那一圈边框 |
| 这张表面的"屏幕" | **它贴的那块工作区，不是那扇窗口**（每帧 `SetViewportSize`） | 窗口尺寸由内容决定，imgui 的"屏幕"要是也跟着缩，内容就会被自己上一帧的大小裁住 —— 底部那一截（往往正是按钮）再也长不回来，也就点不到。见 `IUiRuntime::SetViewportSize` |
| 缩放变了 | 作废工作区备忘，下一帧按新工作区重新摆 | 显示设置动了，工作区（分辨率、任务栏那一侧）常常是同一件事的另一半；而 GLFW 在 `WM_DPICHANGED` 里会套用系统建议矩形，重新锚定必须由宿主自己做 |
| `Esc` | **没有含义** | 面板那边的 Esc 与 × 同义；通知表面既没有可关的东西（该不该消失由引用计数决定），也不该被一次按键清空 |

### 11.7 通知表面的休眠

引用还在、但连续 **30 秒**（`kNotifyDormantMs`）画出来都是空的 —— 例如只开着
一个详情窗口、屏幕上没有浮层 —— 这张表面就**停止出帧**，主循环也不再为它按
vsync 转：CPU 与显存一并归零（见 §17 的实测）。下一条通知到达时唤醒，
**运行时并不重建**：唤醒要的是"再画一帧"，不是"重建设备"。

三条实现上的硬要求：

1. **判定必须在帧循环之外**。块内的条件就是"还没休眠"，而数够门槛的那一帧它
   已经不进去了 —— 把"进入休眠"写在那里，那句话永远不会出现在日志里。
2. **计时与"已经报告过休眠"由一处清零**，四个调用点：画出内容了 / 表面刚建出来 /
   表面销毁 / 被新通知叫醒。只清计时的话，这张表面第二次睡过去就没人来说一声了。
3. **投递通知之后要主动叫醒**（`FrameStep` 的顶部）：睡着的时候没有人在画，
   也就没有人会发现新内容。

> "空闲 30 秒"之所以单独做一层：只开着详情窗口时，通知表面每帧画出来的都是
> 空的 —— 这些帧全是白烧的。

### 11.8 帧与上下文：容易重新踩的坑

- **每帧开头必须 `ImGui::SetCurrentContext(context_)`。** "当前上下文"是
  **线程级单例**；漏掉它的症状是**面板开着时浮层上的按钮点不动**、关掉面板又正常。
- **内容驱动尺寸的表面每帧要在 `NewFrame()` 之前把 `io.DisplaySize` 换成它贴的
  那块工作区**（不是那扇窗口的尺寸），否则窗口的 `ClipRect` 被物理窗口尺寸裁住、
  量出的内容大小永远等于上一帧的窗口大小 → 浮层最下面一行按钮被切掉而且**点不到**。
  尺寸与位置必须在**同一帧**里定下来，否则卡片逐帧跳。
- **不能用裁剪矩形当"内容范围"**：窗口第一条命令（背景底板）拿到的 `ClipRect`
  常是整块视口，按它算出的内容大小永远等于建窗默认尺寸。
- 表面**刚建出来那一帧不要显示**（尺寸要画完才知道），并且必须清零休眠计时器，
  否则新表面可能一帧不画就休眠。**"进入休眠"的日志必须写在条件块外面**（写在
  里面是死代码：数够门槛的那一帧已经不进去了）。
- 工作区按**显示器名**缓存 —— 名字没变则分辨率/接法变动永远不会自动刷新，所以
  要显式失效。**只在矩形真的变了时才 `SetRect`**（每帧 `WM_WINDOWPOSCHANGED`
  是纯开销 + 一次多余重绘）。
- 有表面在画时主循环返回 0 让 vsync 定节拍；**休眠中的浮层不算"在画"**，否则把
  主循环按在 vsync 上白烧 CPU；空闲等待要夹到"配置防抖到期时刻"，下限 1 ms
  防空转。
- **"引用计数归零"就是"面板关闭"这一时刻**（另一个时刻是进程退出），
  `SaveUiStateNow()` 挂在这里。通知表面上**只能**画浮层；`Esc` 在该表面无含义。

## 12. 日志子系统

### 12.1 格式

```
[2026-10-15 14:03:22.481][WARN ][source.mail][sched] 连接超时，将在 300 秒后重试
```

| 部分 | 说明 |
|---|---|
| 时间 | 本地时间，`YYYY-MM-DD HH:MM:SS.mmm` |
| 级别 | `TRACE` / `DEBUG` / `INFO` / `WARN` / `ERROR`，**左对齐补空格到 5 字符** |
| 来源 | 插件 id；宿主自身为 `host`；日志子系统启动早期为 `-` |
| 线程 | `main` / `sched` / `log` / `ext`（插件自建线程，无法细分） |
| 消息 | 单行。**内部换行被替换为空格** |

### 12.2 环形缓冲与写线程

```
环形缓冲：1024 条记录，每条上限 1024 字节（最坏约 1 MiB）
```

| 事件 | 动作 |
|---|---|
| 任一线程 `Log(...)` | 取锁 → 级别过滤 → 格式化 → 写入环形缓冲 → 解锁。**永不阻塞** |
| 缓冲满 | 丢弃**最旧的**，`dropped++` |
| `Warn` 及以上 | 立即 `signal` 写线程（不等批量） |
| 写线程 | 被 signal 或每 200 ms 醒来一次，取锁抄出**【还没写进文件的那一段】**，解锁后写文件 |
| 缓冲非空时会话退出 | flush 全部 |

**为什么 `Warn` 及以上要立即唤醒**：出错时的日志往往紧接着就是崩溃。
把它们留在缓冲里，崩溃时可能就丢了。

**写线程只抄不搬（写游标）。** 记录**不**因为"已经写进文件"而从缓冲里消失：
写线程记着自己写到哪一条了（一个只增不减的绝对序号），每次把那之后的抄进文件。
这一条同时决定了三件事：

- 缓冲是**面板日志页的数据源**（[03-控制面板.md](03-控制面板.md) §7.1 说"日志页显示的是
  环形缓冲的最近内容"）。要是写完就搬空，缓冲在 99% 的时间里是空的，日志页
  也就什么都显示不出来 —— 而文件里一条不少。
- 缓冲满时丢掉最旧的，只是让"缓冲里的第一条"这个序号往前挪。写线程落后再多
  也只补**还留在缓冲里**的那一段，更早的确实无从补写，`dropped` 就是它们的条数。
- 缓冲满得快于落盘时，被丢掉的那些是真的丢了。因此 `dropped` 的正确读法是
  "滚出内存缓冲的条数"：正常情况下它们已经在文件里，只有产出速度超过落盘速度
  时才意味着丢失。

### 12.3 级别过滤

`[app] log_level`（默认 `info`）过滤**写入日志文件**的最低级别。
过滤在**入缓冲之前**做（省内存与格式化开销），因此改级别立即生效。

**例外**：宿主自身的关键错误（崩溃、配置损坏、启动失败）**不受级别过滤**，
永远写入。理由：用户为了减少日志量把级别调到 `error` 之后，
恰恰最需要看到"插件崩了"。

### 12.4 文件命名与轮转

```
<数据目录>/logs/simplemessage-YYYY-MM-DD.log     ← 按【本地】日期命名，追加写
```

| 时机 | 动作 |
|---|---|
| 启动 | 建好日志目录、清理到期文件（当天的文件在**第一次要写的时候**才创建） |
| 每次写入 | 打开当天的文件（追加、共享）→ 写入 → flush → **关闭** |
| 跨过本地午夜 | 文件名每次都按**当前**本地日期算，下一次写入自然落到新文件上 |
| 启动时 | 清理：先删超过 `log_retention_days` 的，再按总大小删最旧的，直到总量 ≤ `log_max_total_mb` |

**清理只在启动时做**，不在运行中做 —— 运行中删除"当前正在写的那个文件"
会与正在发生的写入抢同一把锁，徒增分支。

**宿主不长期持有日志文件的句柄**：要写的时候才"打开 → 追加 → flush → 关闭"，
两次写入之间文件是自由的。

- 外部工具（记事本、`tail`、`type`）**随时可以读**正在写的那个文件，也可以
  在空闲时重命名或删除它。要做到这一点，打开时必须显式带共享标志
  （`_wfsopen(..., _SH_DENYNO)`）—— CRT 的 `fopen` 系列**默认不与别人共享**，
  实测在写线程持有句柄期间连只读打开都会被拒："另一个程序正在使用此文件"。
- 打开失败不丢日志：写游标**不前进**，那些记录留在缓冲里，退避重试
  （200 ms 起，翻倍，封顶 5 秒）。重试期间缓冲照常滚动，滚掉的部分才真的丢。
- 代价是每次批量写多一对 `CreateFile`/`CloseHandle`。与"文件不被独占"相比，
  这点开销可以忽略（批量本身已经把写入频率压到 ≤5 次/秒）。

要看实时日志既可以用控制面板的"日志"页（读内存里的环形缓冲，不依赖文件），
也可以直接用外部工具读文件 —— 后者现在随时可用。

**按本地日期而不是 UTC**：用户看文件名时要能和自己"昨天"的直觉对上。

### 12.5 崩溃时的强制 flush

崩溃屏障捕获到异常后，**必须**在禁用插件之前同步 flush 一次日志：

```cpp
LogForceFlush();   // 取锁，把缓冲里【还欠着的那一段】直接写文件，不走写线程
```

**只补写，不清空缓冲**：缓冲同时是面板日志页的数据源（§12.2）。崩溃路径上把它
清掉，用户重启后打开日志页看到的是一片空白 —— 而那几行往往正是最需要看的。
写游标照常前进，写线程醒来后不会重复写。

**为什么不能只是 signal 写线程**：写线程可能正卡在文件 IO 上，
而崩溃路径需要尽快完成（进程状态已经不可信）。直接写是唯一能保证
"崩溃前最后那几行确实落盘"的做法。

**实现注意**：`LogForceFlush` 与写线程共用同一把文件锁。
如果崩溃发生在**持有该锁的线程**里（例如崩溃发生在写日志的过程中），
强制 flush 会死锁。因此强制 flush 必须用 **`try_lock`**：拿不到锁就
直接放弃（那说明写线程正在写，缓冲里的数据大概率也正在被处理）。

### 12.6 初始化的位置

`LogInit()` 必须是 `main()` 的**第一条**语句 —— 它之后的每一步
（解析命令行、读配置、建窗口）都可能失败，而失败时必须能写日志。

**为什么不用"惰性初始化"**：惰性初始化意味着"第一条日志之前的失败原因
无法被记录"，而程序最早期的失败恰恰是最常见的（路径不对、权限不足、
依赖缺失）。

`LogShutdown()` 必须是最后一条 —— 它 flush 剩余记录、join 写线程、关文件。
**关停顺序见 [01-架构总览.md](01-架构总览.md) §12 的第 7、8 步。**

### 12.7 通知自身的日志

通知的入队、路由、投递**只写 `Trace` / `Debug`**，不写 `Info`。

理由：一条通知的旅程涉及多个组件，按 `Info` 写会让日志被高频通知淹没。
默认的 `log_level = "info"` 意味着"默认看不到通知的详细日志" ——
需要排查通知管线时临时改成 `debug`。

## 13. 字体

加载链（按顺序在系统字体目录里找第一个存在的；目录用 `SHGetFolderPathW(CSIDL_FONTS)` 取得，**不硬编码 `C:\Windows\Fonts`**）：`msyh.ttc`（微软雅黑）→ `simhei.ttf`（黑体）→ `simsun.ttc`（宋体）→ 内置位图字体（最后兜底）。字集用 `GetGlyphRangesChineseSimplifiedCommon()`（常用简体字，约 2500 字）而不是全部 CJK，`OversampleH/V` 设为 1；生僻字会显示成"？"，这是刻意的取舍（换来启动少几十毫秒、显存少几 MB）。若某个插件的内容必然包含生僻字，可以在它自己的浮层里加载一个更大的字集。

字号 = `[app] ui_font_size`（默认 16）× 该表面的内容缩放系数（`1.0` = 96 DPI），**两个量都是逐张表面的**（imgui 1.93 把它们放在 `ImGuiStyle` 的 `FontSizeBase` 与 `FontScaleDpi` 上）—— 面板、通知表面与各详情窗口可能在不同的显示器上。改字号时对**每张表面各做一次** `io.Fonts->ClearFonts()` + 重新装字体，**不销毁上下文**，图集与纹理由 imgui 在下一帧自动重建（§11.2）。

**新字号必须同时写进 `ImGuiStyle::_NextFrameFontSizeBase`，不能只写 `FontSizeBase`。** 改字号的那个滑块是在**一帧的中途**跑起来的，而 imgui 在一帧结束时会 `PopFont()`，内部有一句 `g.Style.FontSizeBase = g.FontSizeBase;` 把这个值写回"这一帧开头记下的那个" —— 只写 `FontSizeBase`，赋值当帧就被抹掉，症状正是"**字号要等下次启动才生效**"。写 `_NextFrameFontSizeBase` 的代价是晚一帧（约 16 ms），用户看不出来。

链上的所有字体都找不到时：用 imgui 内置字体（不含中文，中文会显示成 `?`）、记一条 Error 日志并**作为结构性事件通知**，而**程序仍然正常启动** —— 界面上的中文变成问号是可以忍受的，启动不了是不可忍受的。这件事**是逐张表面的**（图集分家），先建出来的那张表面报过一次就不再报。另有可选的 `SM_EMBED_CJK_FONT=ON` 编译项：把 `SM_EMBED_CJK_FONT_FILE` 指定的字体编进二进制，适用"目标机器保证不了有中文字体"的场景，**默认关闭**（一个中文字体文件通常 5–15 MB，与"资源受限"冲突）。

## 14. 配置模块

职责与键的格式见 [插件开发/03-配置格式.md](插件开发/03-配置格式.md)。这里只列宿主侧的实现要点：

- **`config.cpp` 不认识任何插件的设置项**。它按 `PluginMeta::settings`
  这个 schema 做通用的读取/校验/写回，因此加一个插件不需要改宿主的任何代码。
- **写回是防抖 + 原子替换**（[插件开发/03-配置格式.md](插件开发/03-配置格式.md) §6）。
  写回动作发生在**主线程**（因为触发它的都是 UI 操作），
  且**不得阻塞界面超过几十毫秒** —— 一个 200 KB 的 TOML 写入是毫秒级的，
  但不能在写回里做任何格式化/校验的重活。
- **插件设置的改动立即对 `setting_*()` 可见**：写回是异步的，
  但内存中的值立即更新。这保证"改完立刻生效"这条承诺不依赖于磁盘写入完成。
- **`rules.toml` 不归 `config.cpp` 管**。它由 `rules.cpp` 单独解析（格式与
  `config.toml` 不同），`config.cpp` 只负责 `[rules]` 这个**扁平 bool 表**
  —— 与 `[[instances]]` 的 `enabled` 同一套语义：缺失的规则 id 默认启用，
  非 bool 值按 `true` 处理并记 Warn。规则内容的修改只在用户编辑文件后
  "重新加载"时生效。

## 15. 设置读写与"立即生效"

```
用户在控制面板改动一个值
  → 更新内存中的值（立即）
  → 标记"配置已脏"，重置防抖计时器
  → 下一个 500 ms 静默期后写回磁盘
  → 若涉及日志级别 / 字体字号，立即应用到运行时
```

**宿主不得缓存插件设置值的副本**：`setting_*()` 每次都从内存中的
当前值读。这样"立即生效"不需要任何失效通知机制。

**`requires_restart` 只是 UI 提示**（[插件开发/02-SDK接口参考.md](插件开发/02-SDK接口参考.md) §7.3）：
宿主在界面上标注"（重启后生效）"，但**不会**因为设置变化而重启插件。

## 16. 安全模式

`--safe-mode` 的行为，**只有三件事**：

1. **不加载任何插件**（跳过启动顺序的第 ⑨ 步，见 [01-架构总览.md](01-架构总览.md) §12）。
2. **不做配置写回**（防止"用户正在修配置"时被程序覆盖）。
3. **直接打开控制面板**，并在"插件"页显示一条横幅说明当前处于安全模式。

> 安全模式必须打开面板：用户进入安全模式几乎总是为了"关掉一个坏插件"，
> 直接把面板打开就是把下一步动作摆在用户面前，否则用户还得自己点托盘图标。

**安全模式不影响日志** —— 它仍然正常写日志，因为退出安全模式后
用户通常要做的第一件事就是看日志。

## 17. 资源占用预算

这些数字是**设计目标**，实现后应当实测并记录（回填见 §17.1、§17.2）。
"目标值"一列取自性能用例（T-PERF）的目标。

| 指标 | 目标 | 目标值 | 说明 |
|---|---|---|---|
| 空闲 CPU | ≈ 0%（实测 0%） | T-PERF-1：10 秒平均 ≈ 0% | 无 UI 会话时主线程阻塞等待；唯一的周期唤醒是看门狗检查（1 次/秒） |
| 有 UI 会话时的 CPU | 一帧的绘制成本 | — | 只在会话存活时发生；会话一结束就归零 |
| 空闲内存（RSS） | < 20 MB，不含插件 | T-PERF-2：< 20 MB（不含插件自身） | 3 条线程 + 配置 + 通知历史（200 条） |
| 通知历史上的界 | 200 条 × 每条 ≤ 64 KiB ≈ 最坏 12.8 MB | T-PERF-7：符合估算 | 实际远小于此（真实通知多为几百字节） |
| 线程数 | 3（main / sched / log） | T-PERF-3：3（不含插件自建线程） | 插件自建的线程不计入 |
| 启动时间（到可交互） | < 300 ms | T-PERF-4：< 300 ms | **不含**首次打开面板时的字体图集生成；同一次开机里的第一次运行还要多付一次 D3D11 驱动加载（§17.2） |
| 首次打开面板的额外耗时 | < 300 ms | T-PERF-5：< 300 ms | 主要是字体图集生成 |
| 1000 条通知积压时的界面帧率 | — | T-PERF-6：≥ 30 fps | 每帧最多消费 64 条 |
| 连续运行 24 小时（每小时 100 条） | — | T-PERF-8：内存无持续增长；日志按策略轮转 | 长跑用例 |
| 0 → 200 条通知后等浮层全部消失 | — | T-PERF-9：CPU 回到 0%，内存回到基线附近 | — |
| 5 个插件、每分钟各 1 条、运行 8 小时 | — | T-PERF-10：无泄漏、无句柄增长 | 长跑用例 |

> 12.8 MB 是理论上界，要求连续 200 条通知每条都有 64 KiB 正文（说明
> `kMaxContentBytes` 在工作）；真要更紧，把 `notification_history_size` 调小即可。

### 17.1 实测（2026-10-15，Windows 11 Pro / MSVC v145 / Release）

| 指标 | 目标 | 实测 |
|---|---|---|
| 空闲 CPU | ≈ 0% | **0.000%**（单核，10 秒平均；无插件与 3 插件两种配置相同） |
| 空闲内存（RSS） | < 20 MB | **12.94 MB**（无插件、且从未创建过 UI 会话）。3 个插件加载并跑过一次 UI 会话后为 **28.4 MB**（其中主要是插件自身的常驻部分） |
| 线程数 | 3 | 宿主自建 **3** 条（`main` / `sched` / `log`，实测线程起始地址分别落在 `sm_host.exe` 与 `ucrtbase.dll`）；进程内可见 6 条，另外 3 条由 `ntdll.dll`（线程池/加载器）创建，非宿主所为。3 插件场景下 9 条（含插件自建线程） |
| 启动到托盘图标可用 | < 300 ms | **23–33 ms** |
| 首次打开面板的额外耗时 | < 300 ms | **首次约 900 ms，后续约 126 ms**（见下）；其中字体图集只有 **6–8 ms** |

> 900 ms 是唯一偏差，来自 D3D11 设备的首次创建（驱动初始化，非字体图集或
> imgui 上下文）：同进程内第二次只需 126 ms，是一次性的驱动/运行时成本。
> 按 §11.4 的取舍（设备随会话创建销毁）它无法消除，除非改成"设备常驻"
> （代价是空闲时占用显存）。句柄数基线为 145。

### 17.2 实测（2026-10-16，窗口层换成 GLFW、通知表面到位之后）

| 指标 | 目标 | 实测 |
|---|---|---|
| 启动到托盘图标可用 | < 300 ms | **231–276 ms**（暖机：同一次开机里的后续运行）；**923–1054 ms**（同一次开机里的**第一次**运行，见下） |
| 托盘之后到第一扇界面窗口可见 | — | 通知表面（开机浮层那条 320×60 的窗口）**约 200 ms**（`auto`）/ 约 40 ms（`--renderer opengl`）；`--safe-mode` 下面板（918×647）约 **150 ms**，即进程起来后 370–410 ms |
| 空闲 CPU（3 插件、无 UI 会话） | ≈ 0% | **0.000%**（单核，10 秒平均） |
| 空闲内存（RSS，3 插件、无 UI 会话） | < 20 MB | **25.4–29.1 MB**（§17.1 里"3 插件跑过一次 UI 会话后"是 28.4 MB，同量级） |
| 线程数（3 插件） | 3（宿主自建） | 进程内可见 **10–11** 条（上一轮 9 条；多出的 1–2 条属于新的窗口/渲染层，未逐条归因）。宿主自建的仍是 3 条（`main` / `sched` / `log`） |
| 通知表面每帧画空内容时的 CPU | 一帧的绘制成本 | **1094–1234 ms / 10 s**（面板开着、通知表面画出来是空的） |
| 通知表面休眠之后的 CPU | 归零 | **672–797 ms / 10 s**（只剩面板在画；通知表面那部分确实停了 —— 两者之差就是这张表面空转的代价） |
| 退出码（`WM_ENDSESSION` 关停） | 0 | **0** |

> **冷启动那 700 多毫秒跑在启动探测里。** `auto` 与 `--renderer dx11` 要在建窗口
> **之前**回答"有没有可用的硬件 D3D11 设备"，为此建的裸设备会加载 D3D11 驱动
> （同一次开机里第一次约 750 ms，同进程内后续只要 ~126 ms，见 §11.2）；
> `--renderer opengl` 不走这条探测（`ProbeRenderer` 直接返回），因此是 199–276 ms。
> 换 GLFW 前这笔成本落在首次打开面板上（§17.1），现在被提前到启动路径。
> **"启动 < 300 ms"在暖机下仍成立，冷启动是 3 倍多** —— 明确的已知代价，不是
> 待修的 bug：消掉它就得放弃"建窗口之前定下渲染器"这条约束。

> 休眠省下的就是上面两行之差（约 400 ms / 10 s）：面板开着时通知表面仍每帧
> 画一遍空内容。它跟"引用还在"是两件事 —— 详情窗口开着时用户看的是那扇窗口，
> 通知表面是空的。

> **未跑到的用例。** 上表的数字是"设计目标"与"已实测部分"的混合，下面这几类
> **本轮没有跑过**：长跑（连续 24 小时 / 8 小时，T-PERF-8/10）、跨机器（第二台
> 干净机器上的兼容性用例、把产物拷过去"第一次双击就是好的"）、以及需要人眼的
> 界面项（T-UI 的绝大多数、1000 条积压的帧率 T-PERF-6、历史全满的内存 T-PERF-7、
> 从 0 到 200 条后回到基线 T-PERF-9）。这些用例每一条都已有对应的测试插件或配置
> 开关，缺的是环境、时间与眼睛，不是代码；读表时请把它们按"未验"对待。

## 20. 依赖与构建

### 20.1 需要什么

| 依赖 | 用途 | 形态 | 放置位置 |
|---|---|---|---|
| **imgui** | 界面 | 源码（无根 CMakeLists） | `external/imgui/` |
| **toml++** | 配置读写 | 单头文件 | `external/tomlplusplus/toml.hpp` |
| **GLFW** | 窗口与输入 | 源码（自带 CMakeLists） | `external/glfw/` |

CMake 通过三个存在性检查发现它们（`external/CMakeLists.txt`）：

```cmake
if(EXISTS "${CMAKE_CURRENT_SOURCE_DIR}/imgui/imgui.cpp")       → SM_HAVE_IMGUI
if(EXISTS "${CMAKE_CURRENT_SOURCE_DIR}/tomlplusplus/toml.hpp") → SM_HAVE_TOMLPP
if(EXISTS "${CMAKE_CURRENT_SOURCE_DIR}/glfw/CMakeLists.txt")   → SM_HAVE_GLFW
```

任一缺失时都不在配置阶段失败，而是打印一条 WARNING：缺 imgui 或 toml++ 时
宿主目标被**跳过**，缺 GLFW 时宿主缺少窗口层实现（imgui 的 GLFW/OpenGL3
后端不编译）。这是刻意的：让"依赖没拉下来"表现为一个明确的提示，而不是
一屏编译错误。

### 20.2 依赖已经就位（先看这里）

**本仓库把三个依赖以普通文件的形式随仓库提交了**，所以 `git clone` 之后
它们就在 `external/` 下，**不需要任何拉取步骤** —— 直接 `cmake -B build` 即可。

| 依赖 | 版本 | 在仓库里的形态 |
|---|---|---|
| imgui | 1.93.0 | `external/imgui/**`（普通文件，已被 git 跟踪） |
| toml++ | 3.4.0 | `external/tomlplusplus/toml.hpp`（普通文件） |
| GLFW | 3.5.1 | `external/glfw/**`（普通文件，已被 git 跟踪） |

- 没有 `.gitmodules`，也没有任何子模块登记项。因此
  `git submodule update --init --recursive` 会是**"成功但什么都不做"**。
- 判断依赖是否就绪，唯一的依据是 20.3 的目录形态**实际存在**
  （`ls external/imgui/imgui.cpp`、`ls external/glfw/CMakeLists.txt` 最省事），
  不是任何命令的退出码。
- 版本必须与 `external/PROVENANCE.txt` 对齐：imgui 版本不一致的症状是
  运行时随机的内存踩踏，而不是一个能看懂的报错（见 [插件开发/01-入门.md](插件开发/01-入门.md) §3）。

**只有在依赖缺失时**（例如有人删掉了它们），才需要走下面的获取链。

#### 20.2.1 获取链（仅在依赖缺失时使用，严格按顺序尝试）

```
① 用 git 子模块获取（会把仓库变成"带子模块"的形态）  ↓ 失败
② 联网下载归档包，解压到指定目录（见 20.3）          ↓ 失败
③ 停下来，通知用户手工放置（见 20.4），不要继续尝试别的办法
```

**①：`git submodule add` 不能加进一个非空目录**，所以前提是四个目录已不存在：

```sh
git submodule add https://github.com/ocornut/imgui.git          external/imgui
git submodule add https://github.com/marzer/tomlplusplus.git    external/tomlplusplus
git submodule add https://github.com/glfw/glfw.git              external/glfw
git submodule add https://github.com/mackron/miniaudio.git      external/miniaudio
git -C external/imgui        checkout v1.93.0     # 锁 tag，与 external/PROVENANCE.txt 一致
git -C external/tomlplusplus checkout v3.4.0
git -C external/glfw         checkout 3.5.1
git -C external/miniaudio    checkout 0.11.25
git add external/imgui external/tomlplusplus external/glfw external/miniaudio .gitmodules
git commit -m "添加 imgui、toml++、GLFW 与 miniaudio 子模块并锁定版本"
```

**必须锁 tag，不能跟分支**（跟分支意味着"今天能编过，下周克隆下来编不过"）：
`external/CMakeLists.txt` 引用了 imgui 的 `backends/imgui_impl_*` 路径，这些路径
历史上变动过；GLFW 的版本也必须与 `imgui_impl_glfw.cpp` 期望的 API 对上（3.5
才有 `glfwGetWin32Window()`）。本项目不使用 docking/viewport，官方发布 tag 就够。
一旦改用子模块，`external/PROVENANCE.txt` 与本节都要相应更新 —— 那时
`git submodule update --init --recursive` 才真正是"克隆后必做的一步"。

**②：直接下载归档**（版本一致；解压后不要保留多出来的外层目录）：

```sh
curl -L -o imgui.zip https://github.com/ocornut/imgui/archive/refs/tags/v1.93.0.zip
# → 把内层内容（imgui.cpp、backends/ 等）放进 external/imgui/
curl -L -o tomlplusplus.zip https://github.com/marzer/tomlplusplus/archive/refs/tags/v3.4.0.zip
# → 把 toml.hpp 放进 external/tomlplusplus/
curl -L -o glfw.zip https://github.com/glfw/glfw/archive/refs/tags/3.5.1.zip
# → 把内层内容（CMakeLists.txt、include/、src/ 等）放进 external/glfw/
curl -L -o miniaudio.zip https://github.com/mackron/miniaudio/archive/refs/tags/0.11.25.zip
# → 把 miniaudio.h 放进 external/miniaudio/（miniaudio_impl.cpp 由本项目提供）
```

若用 `git submodule` 之外的方式获取，**必须**在 `external/` 下留一个
`PROVENANCE.txt` 记录：来源 URL、版本/tag、日期、下载来源（谁下的）。

**③：停下来通知用户** —— 不要继续找镜像、不要换别的 TOML 库、不要用
vendored 的过期副本：

```
需要四个依赖，自动获取失败。请手工下载并放到：
  external/imgui/         ← 需要 imgui.cpp 直接位于此目录
  external/tomlplusplus/  ← 需要 toml.hpp 直接位于此目录
  external/glfw/          ← 需要 CMakeLists.txt 直接位于此目录
  external/miniaudio/     ← 需要 miniaudio.h 直接位于此目录
版本：imgui v1.93.0、toml++ v3.4.0、GLFW 3.5.1、miniaudio 0.11.25
放好后重新运行 cmake 配置即可。
```

libcurl 与 cpp-httplib 是一次**有意破例**的产物：示例插件本来只
链接 `sm::sdk`，而 IMAP 与 HTTP 的解析自己写既不划算也不安全。miniaudio 不是
"插件破例"：宿主自己的"试听"也用它解码，所以是宿主与插件共用的基础库。约束是
**不把依赖的类型带过插件边界**；链接方式则按依赖的形态选择 —— cpp-httplib 是
单头文件，直接编进 `source.webhook`；libcurl 与 imgui 一样编成进程内共享的
`sm_curl.dll`，两个源插件只保留导入表，避免每个插件各背一份 libcurl。

miniaudio 虽然能力很全，本项目只用它"解码 WAV / MP3 并从默认输出设备播放"。
`external/CMakeLists.txt` 因此在编译期把这些关掉：编码与生成器
（`MA_NO_ENCODING` / `MA_NO_GENERATION`）、FLAC 与 Vorbis
（`MA_NO_FLAC` / `MA_NO_VORBIS`）、资源管理器（`MA_NO_RESOURCE_MANAGER`，
异步加载那一整套），以及不用的后端 —— 只保留 WASAPI（Windows）、
ALSA + PulseAudio（Linux）、Core Audio（macOS）。因为资源管理器被关掉，
`ma_sound_init_from_file()` 不再可用，播放代码改为先 `ma_decoder_init_file()`、
再 `ma_sound_init_from_data_source()`。另外对 MSVC 加
`/Gy /Gw /Zc:inline /O1`（GCC / Clang 用 `-Os -ffunction-sections
-fdata-sections` + `--gc-sections`），让链接器把没被引用的函数从最终产物里删掉。

宿主还额外导入 `sm_curl.dll`，用于按需下载 `Notification::icon` 里的网络图片
（见 §7.5）。因此"关于"页在构建包含 libcurl 时也会列出它 —— 那一页列的是宿主
自己的依赖。

### 21.1 MIT / Zlib / curl 的义务

MIT、Zlib/libpng 与 curl 许可证都要求**保留版权声明与许可文本**。因此：

- 发布包中**必须**包含一个 `THIRD-PARTY-NOTICES.txt`，
  内含 imgui、toml++、GLFW、miniaudio 的 LICENSE 全文与版权行，
  **以及 libcurl（`external/curl/COPYING`）与 cpp-httplib 的许可文本** ——
  它们虽然只进了插件，但仍然随发布包分发；
- 控制面板的"关于"页列出了依赖名称、版本、许可证与项目地址
  （[03-控制面板.md](03-控制面板.md) §8）；
- 本项目自己的 `LICENSE` 尚未确定（`README` 里是占位）。

### 21.2 字体：一条需要特别注意的许可问题

`SM_EMBED_CJK_FONT` 选项**不提供字体文件**，使用者必须自己指定
`SM_EMBED_CJK_FONT_FILE`。

**默认的字体加载链（`msyh.ttc` / `simhei.ttf` / `simsun.ttc`）是
从系统里读取的，不随程序分发，因此不涉及再分发许可。**
但只要把字体文件**编进二进制**，就是在再分发它 —— 而
微软雅黑 / 黑体 / 宋体是微软的字体，**不允许**这样做。

**因此内嵌字体时只能使用许可允许再分发的字体**，例如：

| 字体 | 许可证 |
|---|---|
| 思源黑体 / Source Han Sans / Noto Sans CJK | SIL OFL 1.1 |
| 文泉驿微米黑 | GPL v3 + 字体例外 / Apache 2.0 双许可 |
| 朱雀仿宋等 OFL 字体 | SIL OFL 1.1 |

**在同一个二进制里内嵌 OFL 字体的注意事项**：OFL 允许与其它软件一起
分发，但字体本身**不能**被单独售卖，且必须附带 OFL 全文；
若对字体做了修改，修改版不能使用其保留名称（Reserved Font Name）。

> **给实现者的一句话**：如果构建时指定了一个非开源系统字体，
> 应当在 CMake 配置阶段打印一条**明确的警告**，
> 说明这可能违反该字体的许可。这不是技术问题，但它是发布问题。

### 21.3 不引入新依赖

宿主侧有四个第三方依赖（imgui、toml++、GLFW、miniaudio），加上插件侧的 libcurl
与 cpp-httplib 一共六个，全部是源码级别的、许可宽松（MIT / Zlib / curl 许可证 /
公有领域）、体积可控的。代价要如实记着：curl 的源码树约 60 MB，是仓库里最大的一块
（见 `external/PROVENANCE.txt` 末尾关于"最该早日改成子模块的那一棵"）。

**新增任何依赖都需要论证三件事**：它解决了什么本可以手写的问题、
它的许可证是否兼容、它给二进制增加了多少体积。
一个资源受限的托盘工具的依赖预算**应当**是紧的。

## 22. 编码约定

| 约定 | 说明 |
|---|---|
| **C++17**（`cxx_std_17`，四个目标一致），`/permissive- /W4 /utf-8 /EHsc`，警告当错误 | 编译选项由 `cmake/SmPlatform.cmake` 强制；标准由各目标的 `target_compile_features` 声明（见 [01-架构总览.md](01-架构总览.md) §6.1） |

| 平台 API 只出现在 `src/platform/` 下 | 业务代码里出现 `#ifdef _WIN32` 一律视为 bug（除了 `include/sm/export.h` 的导出修饰） |
| 中文字面量集中在 `src/host/strings.h` | 见 [03-控制面板.md](03-控制面板.md) §11 |
| 不引入新的第三方依赖 | 宿主侧是 imgui + toml++ + GLFW + miniaudio 四个；**插件侧另有 libcurl 与 cpp-httplib**，前者编成 `sm_curl.dll` 供 `source.email` / `source.gotify` 导入，后者只编进 `source.webhook`，**都不进宿主**；miniaudio 是静态库，宿主与 `notifier.sound` 共用。再加依赖需要论证（见 §21） |
| 不用 STL 容器跨 DLL 边界 | 见 [插件开发/01-入门.md](插件开发/01-入门.md) §2.2 |
| 不写 `catch (...)` 吞掉异常 | 崩溃隔离靠 SEH 屏障，不靠"到处 try" |

## 附录 A 常见陷阱速查

实现过程中最容易浪费时间的几个：

| 症状 | 原因 | 解法 |
|---|---|---|
| 插件一调用 `ImGui::` 就崩 | imgui 被静态编进宿主 | imgui 必须是 SHARED（[插件开发/01-入门.md](插件开发/01-入门.md) §7.1） |
| 加载插件返回 126 | 找不到依赖 DLL | 把 exe 目录与插件目录都加入搜索路径（见 §4.3） |
| `C2712` 编译错误 | `__try` 与需要栈展开的对象共存 | 把 `guarded_call` 写干净（见 §5.1） |
| 退出时静默崩溃 | 插件留下了线程/窗口 | [插件开发/01-入门.md](插件开发/01-入门.md) §6.1 |
| 改了设置不生效 | 插件在 `initialize` 里缓存了设置 | 按需读（[插件开发/02-SDK接口参考.md](插件开发/02-SDK接口参考.md) §6.3） |
| 调度"有时候晚很久" | 改了堆却没 `wake()` | 任何改堆的操作都 `wake()`（见 §6.1） |
| 被禁用的插件偶尔还被调度 | 堆里没摘除，野指针 | 用代际号校验（见 §6.2） |
| 通知无限增殖 | 日志桥没有递归中断 | `tls_notify_depth`（见 §10.3） |
| 面板开着时，浮层上的按钮点不动 | 面板与通知表面各建了 `ImGuiContext`，但 `CreateContext()` 只在**没有**当前上下文时才把它设为当前 —— 通知表面的帧落进了主上下文 | 显式 `CreateContext()` + `SetCurrentContext()`，并在 `Destroy`/`RebuildFonts`/`RenderFrame` 入口各自重设（见 §11.3） |
| 通知卡片最下面一行按钮被切掉、点不到 | 内容驱动尺寸的那张表面，`io.DisplaySize` 还是物理窗口大小 → `ClipRect` 把内容裁住，量出来的"内容大小"永远等于上一帧的窗口 | 每帧在 `NewFrame()` 前把 `io.DisplaySize` 换成它贴的工作区（`IUiRuntime::SetViewportSize`，见 §11.6） |
| 右键"关掉这一条"却把屏幕上所有浮层一起清空了 | 判定写成了 `IsWindowHovered()` —— 那是"鼠标在哪张表面上" | 每条卡片用 `PushID(seq)` + `BeginGroup/EndGroup` 包住，`EndGroup()` 之后判 `IsItemHovered()`，那才是"这一条" |
| 两条浮层的按钮互相抢：点上面那条的「已读」，下面那条也一起关掉 | 同一个 imgui 窗口里同名控件撞了 id（`SmallButton("已读")` 在两条上字面相同） | 整条卡片（含「打开链接」）统一放进 `PushID(seq)` |
| `[[instances]]` 一条都没读出来 | 写成了 `[instances]`，或 `id`/`plugin` 没加引号；也可能是 v1 的 `[plugins]` 里键名含点号却没加引号，迁移看到非 bool | [插件开发/03-配置格式.md](插件开发/03-配置格式.md) §3.2、§7.1 |
| 删掉最后一个实例后它又回来了 | 自动补实例只看“该类型零实例”，没有写 `[removed_types]` 墓碑 | 删类型下最后一个实例时写墓碑（[插件开发/03-配置格式.md](插件开发/03-配置格式.md) §3.2） |
| 删一个实例时崩溃 / 访问已释放对象 | 调度线程还在 `start()`，记录已被删除 | 延迟删除：`IsExecuting(id)` 为假后再销毁（见 §4.1.1） |
| 删掉一个实例后另一个实例的设置也没了 | 模块被提前卸载，或设置文件按类型 id 删除 | 模块按类型引用计数；设置文件按**实例 id** 删除 |
| 注释被吃掉 | 写回是整体重写 | 已知取舍（[插件开发/03-配置格式.md](插件开发/03-配置格式.md) §6.4） |
| `unresolved external symbol WinMain`（只在 MSVC 上出现） | `WIN32_EXECUTABLE` 要的是 WinMain 系入口，`main`/`wmain` 是控制台入口 | 入口用 `WinMain`，命令行另取（[01-架构总览.md](01-架构总览.md) §13） |
| `undefined reference to D3DCompile` | 宿主没链 `d3dcompiler` | 宿主需要链接 `d3dcompiler` |
| 依赖明明在，却报"依赖不完整"并跳过宿主 | `add_subdirectory` 是子作用域，`set()` 传不上去 | 子目录里写 `PARENT_SCOPE` |
| 编译一切正常，一运行就 126 找不到 `sm_imgui.dll` / `sm_curl.dll` | 产物散落在不同目录 | 统一输出目录；两个共享库都必须与 exe 同目录 |
| CMake 警告 `Function-style preprocessor definitions` | 用了带括号的宏定义，括号被丢掉 | 改走 `IMGUI_USER_CONFIG`（[插件开发/01-入门.md](插件开发/01-入门.md) §7.4） |
| `'#include' expects "FILENAME"` | `IMGUI_USER_CONFIG` 的值没带引号 | 写成 `\"sm_imgui_config.h\"` |
| 未知参数/缺取值的提示跑进了 stdout | 顺手用了同一个输出函数 | 提示一律走 stderr（[01-架构总览.md](01-架构总览.md) §13） |
| `--config-dir --version` 在磁盘上建出一个名叫 `--version` 的目录，程序照常启动 | 取值以 `-` 开头被当成路径 | 取值以 `-` 开头一律判为"忘了写取值"，记 stderr 并继续（不静默吞掉） |
| 日志里在 `SimpleMessage 已退出` **之后**又冒出"在插件管理器析构时释放其模块" | 未初始化、被禁用、安全模式跳过的插件从没走到 `Unload()` | 发现即登记，退出时**显式**释放所有还持有的模块（`ReleaseDiscoveredModules`）——析构函数不该是唯一的兜底 |
| 运行中改不动插件 DLL 的名字/删不掉它 | Windows 把已加载的映像映射在进程里 | 这是**正常**的：反过来说，改名成功就是"模块真的被卸载了"的证据；日志文件同理（见 §12.4） |
| `ui_state.toml` 保存失败：`无法创建临时文件 …\data\host\ui_state.toml.tmp` | 原子写要求同目录可写，而 `data\host\` 从来没被创建 | 解析路径时把所有会被原子写的目录一并 `ensure_directory` |
| 改字号时调用 `ImGui_ImplDX11_CreateFontsTexture()` 编译不过 | 它在 imgui 1.93 里已不是公开函数 | `io.Fonts->ClearFonts()` 后重新装字体即可，纹理由后端在下一帧按需上传（见 §11.2） |
| 注销/关机时，每一扇 GLFW 窗口都被记了一次"该关了" | GLFW 在 Windows 上的事件泵看到 `WM_QUIT` 会给**每一扇**窗口都记一次（其源码里就写着 HACK） | 宿主必须自己区分 `WM_QUIT` 与单窗口的关闭请求 |
| DPI 一变，整片 UI 变成空白 | `OnContentScaleChanged` 收到 `x_scale <= 0` → 字号 0 | 回调里必须拦住 `x_scale <= 0`；`WM_DPICHANGED` 里系统给的建议矩形要无条件采用 |
