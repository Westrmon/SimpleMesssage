# 插件开发 01 — 入门

**写插件之前必读。**本篇的每一条"禁止"都对应一个真实存在的、表现为随机崩溃
或静默错误的坑。每条规则后面都写了**违反之后会看到什么现象** ——
如果你遇到了那种现象，回来查这一篇。

---

## 1. 最小可运行插件

先看一个**能跑起来的完整骨架**，再往下读规则。下面是一个 Source 插件：
它每隔 `interval_sec` 秒产生一条通知。Notifier 的骨架只有最后一步不同 ——
不覆盖 `start()`，改为覆盖 `on_notify()`（两类插件继承同一个基类，逐符号的
细节见 [02-SDK接口参考](02-SDK接口参考.md)）。

```cpp
// myplugin.cpp —— 最小可运行的 Source 插件
#include "sm/export.h"          // SM_DEFINE_PLUGIN 与四个导出符号
#include "sm/host_context.h"    // sm::IHostContext
#include "sm/notification.h"    // sm::Notification
#include "sm/plugin.h"          // sm::PluginBase / PluginMeta / StartResult

namespace {

// 设置项 schema。宿主据此自动生成配置表单与 TOML 文件，插件不碰 UI 与文件 IO。
constexpr sm::SettingDef kSettings[] = {
    sm::setting::integer("interval_sec", 60, 5, 86400, "间隔（秒）"),
    sm::setting::text("message", "你好", 128, "通知内容"),
};

// 元信息必须是【静态存储期】—— 宿主在创建插件实例之前就会读它（见 §5）。
constexpr sm::PluginMeta kMeta = {
    /* id            */ "source.example",  // 必须等于 DLL 文件名（去掉扩展名）
    /* name          */ "示例源",
    /* author        */ "……",
    /* version       */ "1.0.0",
    /* description   */ "每隔一段时间产生一条通知。",
    /* kind          */ sm::PluginKind::Source,
    /* host_range    */ ">=0.1.0,<1.0.0",
    /* subscriptions */ sm::Span<const char*>{},  // Source 不使用订阅
    /* settings      */ sm::span_of(kSettings),
    /* api_version   */ SM_API_VERSION,           // 必须写这个常量
};

class ExampleSource final : public sm::PluginBase {
 public:
  explicit ExampleSource(sm::IHostContext* host) : sm::PluginBase(host, kMeta) {}

  sm::StartResult start(sm::StartOutput* out) override {
    const std::int64_t interval = host()->setting_int("interval_sec", 60);

    // 通知只能从 start() 里产生（见 §4）；字符串必须住进本次回调的 arena（见 §5）。
    auto* items = host()->allocate_array<sm::Notification>(1);
    if (items == nullptr) {                 // 分配可能失败，必须检查
      host()->schedule_next(interval * 1000);
      return sm::StartResult::Error;
    }
    const char* message = host()->setting_string("message", "你好");
    items[0] = sm::Notification{};
    items[0].title = host()->allocate_string(message, sm::limits::kMaxTitleBytes);
    items[0].topic = host()->allocate_string("example.tick", 64);
    items[0].level = sm::Level::Info;
    items[0].time_unix_ms = host()->now_unix_ms();

    out->items = sm::Span<const sm::Notification>(items, 1);
    host()->schedule_next(interval * 1000);  // 不注册下一次调度，插件就休眠
    return sm::StartResult::Ok;
  }
};

}  // namespace

// 四个导出符号由这一行生成；必须在【全局作用域】调用（extern "C" 符号）。
SM_DEFINE_PLUGIN(kMeta, ExampleSource);
```

把它编译成 DLL，**把产出的 DLL 放进 `plugins/` 目录**（文件名必须等于
`kMeta.id`，这里是 `source.example.dll`），宿主下次启动时就会加载它。

- 想照着真实插件读，见 [04-示例插件](04-示例插件.md)；
- 配置文件的格式与位置见 [03-配置格式](03-配置格式.md)；
- **Source 会被宿主创建多个实例**：你的 DLL 只加载一次，但
  `sm_create_plugin` 可能被调用多次，每次是一个独立实例。`plugin_id()` 与
  `own_config_path()` 返回的是**实例级**身份（`source.example`、`source.example@2`），
  不要假设进程里只有一个自己，也不要拿类型 id 当身份做进程级单例。
  需要实例级的数据目录文件时，从 `own_config_path()` 的文件名派生
  （[03-配置格式 §1](03-配置格式.md)）；
- 本节之后的每一条"禁止"都对应一个真实存在的坑，**不要跳过 §6**。

## 2. 插件是一个 DLL，导出四个符号

```
extern "C" std::int32_t  sm_abi_version();                      // API 版本
extern "C" const sm::PluginMeta* sm_plugin_meta();              // 元信息
extern "C" sm::IPlugin*  sm_create_plugin(sm::IHostContext*);   // 创建实例
extern "C" void          sm_destroy_plugin(sm::IPlugin*);       // 销毁实例
```

不要手写这四个函数 —— 在全局作用域用一次宏即可：

```cpp
namespace {
constexpr sm::PluginMeta kMeta = { /* … */ };
class MyPlugin final : public sm::PluginBase { /* … */ };
}

SM_DEFINE_PLUGIN(kMeta, MyPlugin);
```

### 2.1 为什么前两个符号必须存在

宿主用它们做**加载前的校验**：

```
LoadLibrary(插件.dll)
    │
    ├─ 取 sm_abi_version  ─── 缺失?          → 拒绝
    │                       不等于本宿主?     → 拒绝
    │
    ├─ 取 sm_plugin_meta  ─── 缺失?          → 拒绝
    │                        id 非法/保留前缀? → 拒绝
    │                        host_range 不满足?→ 拒绝
    │                        schema 不合法?    → 拒绝
    │                        api_version 不一致?→ 拒绝
    │
    └─ 全部通过 → 取 sm_create_plugin 并实例化
```

关键在于：**元信息是静态数据，不需要创建对象就能读到。**因此一个
"ABI 不匹配的插件"从来不曾被执行过一行插件代码。如果让宿主先创建实例
再问"你兼容吗"，那在 ABI 不匹配的情况下执行构造函数本身就是未定义行为。

### 2.2 加载校验清单（宿主实现必须逐条执行）

| # | 检查 | 不通过时的处理 |
|---|---|---|
| 1 | 四个导出符号齐全 | 拒绝，日志写明缺哪一个 |
| 2 | `sm_abi_version() == SM_API_VERSION` | 拒绝，日志写明双方版本 |
| 3 | `sm_plugin_meta()` 非空 | 拒绝 |
| 4 | `meta->api_version == SM_API_VERSION` | 拒绝（交叉校验，防插件写错常量） |
| 5 | `meta->id` 非空、字符集合法、长度合规、**不以 `sm.` 开头** | 拒绝 |
| 6 | **DLL 文件名（去掉扩展名）等于 `meta->id`** | 拒绝 |
| 7 | `meta->version` 可被 `parse_version()` 解析 | 拒绝，日志给出原因 |
| 8 | `meta->host_range` 通过 `is_valid_range()` 且 `version_satisfies(宿主版本, range)` | 拒绝，日志给出原因 |
| 9 | 设置项数量、`name` 字符集、重名、Enum 的 options 非空 | 拒绝，日志指出第几项 |
| 10 | 设置项 `name` **不得**为 `schema_version` | 拒绝 |
| 11 | 订阅模式数量不超限、每个都非空 | 截断并记 Warn |
| 12 | 插件 id 与**已加载的**其他插件不重复 | 拒绝后来者 |

> **第 5 条为什么禁止 `sm.` 前缀。** `sm.host` 是宿主的保留 id ——
> 宿主自身作为通知来源时用它。如果允许插件占用这个 id，
> 就会出现"假宿主通知"，而用户完全无法分辨。

> **第 6 条为什么要文件名等于 id。** 这是最便宜的一致性校验。
> 当用户报告"我的插件不生效"时，"文件名和 id 不一致"是第一位的可疑原因，
> 让它变成一个明确报错，比让人去读代码快得多。

### 2.3 拒绝必须是可见的

上述任何一条拒绝，都**必须**同时做到：

1. 写进日志（Warn 级，含原因）；
2. 出现在控制面板的"插件"页里，标记为"拒绝加载"，并显示原因；
3. 计入概览页的统计。

**禁止静默跳过。** 静默跳过会让"插件为什么没生效"变成一场耗时数小时的
排查，而答案就在一行日志里。

## 3. 工具集与 CRT 约束

**插件与宿主必须用同一个工具集、同一种 CRT 链接方式编译，Debug 与 Release
不可混用。**

### 3.1 为什么

跨模块的 C++ 对象会同时触及三样东西，任何一样不一致都会出事：

| 触及的东西 | 不一致时的现象 |
|---|---|
| **虚函数表布局** | 调用一个虚函数跳到错误的地址 → 访问违例，崩在看似无关的地方 |
| **类型布局与对齐** | 结构体字段错位 → 读到垃圾数据，不崩但结果完全错误 |
| **堆与 CRT 状态** | 在一个 CRT 里 `new`、在另一个 CRT 里 `delete` → 堆损坏，通常在关程序时崩 |

第三条尤其隐蔽：**它经常在程序退出时才崩**，而此时日志已经关了，
你看到的是"程序退出时静默消失"。

### 3.2 由此产生的三条硬规则

1. **跨边界禁止传 STL 类型。**`std::string` / `std::vector` / `std::function` /
   `std::span` / `std::string_view` 全都禁止。它们的布局随标准库版本与
   `_ITERATOR_DEBUG_LEVEL` 变化。**允许的**是：POD 结构体、定长整型/浮点、
   `const char*`（UTF-8、NUL 结尾、arena 拥有）、`sm::Span<>`、不透明 `void*`。
2. **禁止跨模块释放内存。** 见 §5 —— 本 SDK 用 arena 把这件事故从根本上消除了。
3. **禁止跨 DLL 使用 `dynamic_cast` / `typeid`。**它们依赖 RTTI 表的跨模块
   一致性，且是实现细节最不稳定的部分。

> **违反规则 1 的现象**：在 Debug 构建的宿主要求下加载 Release 构建的插件，
> 表现为程序启动时正常，一旦有通知经过就崩在 `std::string` 的析构里。

## 4. 线程约束速查表

| 方法 | 调用线程 | 是否禁止阻塞 |
|---|---|---|
| `meta()` | 任意（实际只在加载期调用） | — |
| `initialize()` | **主线程** | 应当（会卡住界面） |
| `start()` | **调度线程** | **禁止**（会卡住所有 Source） |
| `stop()` | 主线程 | 应当 |
| `exit()` | 主线程 | 应当 |
| `on_notify()` | 主线程 | **禁止** |
| `on_action()` | 主线程 | **禁止** |
| `draw_ui()` | 主线程 | **禁止**（每帧调用） |
| `draw_view()` | 主线程 | **禁止**（每帧调用） |
| `post_to_main_thread` 的任务函数 | 主线程 | **禁止** |
| `IHostContext::log` / `logf` | 任意 | 永不阻塞（有界队列） |
| `IHostContext::now_unix_ms` | 任意 | — |
| `IHostContext::allocate` | 对应回调期间 | — |
| 其余 `IHostContext` 方法 | 见 [02](02-SDK接口参考.md) | — |

> **违反 `start()` 的"禁止阻塞"会看到什么**：一个插件在等一个超时的网络
> 请求，用户发现"另一个完全无关的插件也不更新了"。这是共享调度线程的
> 必然结果，也是看门狗存在的唯一理由。

> **通知只能从 `start()` 里产生。** SDK 没有"随时投递一条通知"的接口 ——
> 插件若在自己的线程里拿到数据，只能先排进自己的队列，等下一次 `start()`
> 时交付出去。`source.webhook` 就是这么做的：接收线程只负责入队。

### 4.1 自己起线程的插件：三条结构性约束

宿主不禁止插件起线程，但跨线程的部分必须收敛成三件事：

1. **派生线程与调度线程之间只通过一把锁保护的队列通信**，没有别的共享状态；
2. **派生线程不得调用宿主接口**，除了 `log` / `logf` / `now_unix_ms` 这三个
   "任意线程可调用"的方法 —— 设置项也一样，需要用的设置由 `start()` 先快照
   一份，再交给派生线程读。（要从派生线程回到主线程，用
   `post_to_main_thread`，见 §8。）
3. **`exit()` 返回之前必须 join 所有派生线程** —— 宿主在 `exit()` 返回后
   马上 `FreeLibrary`，留下的线程会跳进已释放的代码段。

## 5. 内存所有权

这是本 SDK 里最容易理解错、后果最严重的一块。规则只有三条：

### 5.1 插件从宿主借内存，从不释放任何东西

```cpp
StartResult MySource::start(StartOutput* out) {
    auto* items = host()->allocate_array<sm::Notification>(2);   // 向 arena 借
    if (items == nullptr) return StartResult::Error;             // 必须检查！

    items[0].title = host()->allocate_string("标题", sm::limits::kMaxTitleBytes);
    items[0].summary = nullptr;      // 留空 → 宿主自动生成
    // ……

    out->items = sm::Span<const sm::Notification>(items, 2);
    return StartResult::Ok;
}   // ← 这里之后，arena 里的东西就归宿主了，插件不得再碰
```

- **arena 的生命周期 = 一次回调**。`start()` 返回后它就被回收了。
- **`allocate` 可能返回 `nullptr`**（超出上限）。不检查它，
  你会得到一个空指针写入，而崩溃发生在宿主里，日志看起来像是宿主的问题。
- **插件永远不调用任何释放函数。** 没有 `host->Free()`，也不需要。
  这条规则让"跨模块释放"这个崩溃高发区彻底消失。

### 5.2 宿主给的通知视图只在回调期间有效

```cpp
void MyNotifier::on_action(const sm::Notification& n, const char* action_id) {
    m_pending = n;        // ✗ 错：n 指向的内存会在本回调返回后失效
    m_pending = *n;       // ✗ 仍然错：*n 里的 const char* 指向的还是宿主内存
    // ✓ 正确：把需要的字段自己拷一份（用插件自己的 string / vector，
    //    并保证在 exit() 之前释放）
}
```

> **违反之后的现象**：点击通知详情，界面显示乱码或直接崩溃，且**只在
> 历史队列已经滚动过之后才出现** —— 因为旧的通知被挤掉了，宿主复用了
> 那块内存。这类"偶尔崩"的问题极难定位，所以这条是硬规则。

### 5.3 宿主的字符串，插件不拥有

`meta()` 返回的 `PluginMeta` 与其内部的 `Span` 指向**插件自己的静态数据**，
宿主不复制也不释放。因此：

- `PluginMeta` 及其引用的所有数组**必须**是静态存储期（`constexpr`）；
- **必须**在 DLL 被加载的整个期间保持不变（宿主可能随时回头读它）。

```cpp
// ✓ 正确
constexpr sm::SettingDef kSettings[] = { /* … */ };
constexpr sm::PluginMeta kMeta = { /* … */ };

// ✗ 错误：函数内临时构造，宿主拿到的是野指针
sm::PluginMeta make_meta() { return { /* … */ }; }
```

### 5.4 截断与上限

- **字符串截断必须按 UTF-8 码点做。** 宿主那边是按【字节】截断的
  （见 `allocate_string` 的说明），直接按字节切会把一个中文字符切成半个字，
  显示成乱码。需要截断时请自己按码点切 —— `sm::summary.h` 里的 `utf8_*`
  与 `make_summary()` 就是给这件事用的。
- **插件自己声明的上限应当低于宿主的上限，留出余量。** 内置插件的惯例：
  请求体 1 MiB、title 200 字节（宿主 256）、content 60 KB（宿主 64 KB）。
  贴着宿主的线上限写，等于把"会不会被截断"交给了宿主去决定。

## 6. 禁止事项清单

按"违反后的现象"分组，便于对照排查。

### 6.1 会随机崩溃的

| 禁止 | 违反后的现象 |
|---|---|
| 跨边界传 STL 类型 | 崩在字符串/向量析构里，Debug/Release 混编时必现 |
| 跨模块释放内存 | 堆损坏，常在退出时崩，日志已关看不出原因 |
| 缓存宿主投递的 `Notification` 引用 | 通知被挤掉后偶发乱码/崩溃 |
| 缓存任何 imgui 指针或跨帧状态 | 用户关掉面板后再触发一次绘制就崩 |
| 在 `exit()` 返回后留下活跃线程/窗口 | `FreeLibrary` 后线程跳到已卸载的代码段，必崩 |
| 元信息不是静态存储期 | 加载时读到野指针，随机崩在宿主里 |
| 跨 DLL `dynamic_cast` / `typeid` | 返回错误结果或崩溃，取决于构建配置 |

### 6.2 会静默出错的

| 禁止 | 违反后的现象 |
|---|---|
| 在 `initialize()` 里读设置并缓存 | 用户改了设置却不生效，看起来像"设置没保存" |
| 不检查 `allocate()` 返回值 | 崩溃发生在宿主里，日志指向错误的模块 |
| 在 `start()` 里不检查 `is_cancelled()` | 关程序时界面卡住数秒（等宽限期超时） |
| 忘记调用 `schedule_next` | 插件只跑一次就休眠，用户以为它坏了 |
| 在 `draw_ui` 里直接调自己的 `on_action` | 重入导致的界面状态错乱 |
| 使用 `sm.` 开头的 id 或 topic | 加载被拒绝（topic 则会被宿主日志警告） |

### 6.3 会拖垮整个程序的

| 禁止 | 违反后的现象 |
|---|---|
| `start()` 里做无超时的 IO | **所有** Source 都停摆，用户以为软件死了 |
| `on_notify` / `draw_*` 里做同步 IO | 界面卡顿，且每来一条通知就卡一次 |
| 在循环里无节制 `allocate` | arena 耗尽，本插件的通知全部失败 |
| 高频写日志（每条通知一条 Info） | 日志文件迅速膨胀；环形缓冲满后丢失更重要的记录 |
| 自己用 SEH 吞掉访问违例 | 宿主的崩溃屏障失效，插件带着损坏状态继续跑 |

### 6.4 最后一条要单独说

> **插件禁止使用 SEH（`__try` / `__except`）来吞掉访问违例。**
>
> 允许用 C++ 异常并在方法**内部**处理完（异常禁止越过边界）。
> 但用 SEH 吞掉一个访问违例，会让宿主误判"这次调用一切正常"，
> 于是插件带着已经损坏的内部状态继续运行 —— 这比直接崩溃**危险得多**，
> 因为崩溃至少有日志，而损坏的状态会以各种不可预期的形式表现出来。
>
> 崩溃不是敌人，"不知道自己已经坏了"才是。

## 7. imgui 共享约定

### 7.1 imgui 是共享库

**imgui 被编译为独立的 `sm_imgui.dll`，宿主与所有用到它的插件都链接它。**

为什么不能各编一份静态库：

- 静态编进 `sm_host.exe` → 插件 DLL 根本链接不到 `ImGui::` 的符号
  （exe 默认不导出）。
- 让每个插件静态编一份自己的 imgui → 同一个进程里存在多份 imgui 实现和
  多份全局状态。虽然版本完全一致时"用 `SetCurrentContext` 共享上下文"
  勉强能跑，但它依赖两边代码的全局变量布局逐字节相同 ——
  某次升级只更新了一边，就是随机的内存踩踏。

共享一份实现之后，语义与"单进程内使用 imgui"完全一致 ——
**共享的是实现，不是上下文**：宿主自己会为每张表面各建一个上下文
（[01-架构总览 §4.2](../01-架构总览.md)），插件不需要、也禁止参与这件事。

> **为什么文件名叫 `sm_imgui.dll` 而不是 `imgui.dll`。**
> 这个名字会被写进**每一个用到 imgui 的插件的导入表**里，
> 因此它必须足够独特：用户机器上、PATH 里、甚至插件目录里，
> 都可能存在与 Dear ImGui 完全无关的 `imgui.dll`（这是相当常见的库名）。
> 一旦撞名，Windows 会毫不迟疑地加载错误的那一个，症状是
> "某台机器上就是起不来"，而在开发机上永远复现不了。<br>
> 本项目自己的共享库一律带 `sm_` 前缀，就是为了让这种撞名不可能发生。
> 名字在 `external/CMakeLists.txt` 里由目标名 `sm_imgui` 决定。

### 7.2 部署要求（宿主实现必须满足）

```
<安装目录>/
├── sm_host.exe
├── sm_imgui.dll              ← 必须与 exe 同目录
├── sm_curl.dll               ← 必须与 exe 同目录（宿主下载通知图标；source.email / source.gotify 导入）
├── config.toml
├── plugins/
│   ├── source.email.dll
│   ├── source.gotify.dll
│   ├── source.webhook.dll
│   ├── notifier.imgui.dll
│   ├── notifier.console.dll
│   └── notifier.sound.dll
├── config/
│   └── plugins/
│       ├── source.email.toml       ← 插件设置，文件名 = 实例 id
│       └── source.email@2.toml     ← 同一 DLL 的第二个实例
└── logs/
```

**插件加载器必须保证 `sm_imgui.dll` 与 `sm_curl.dll` 能被解析到。**
这两个共享库和 exe 放在同一目录；如果加载时使用了受限的
DLL 搜索路径（这是安全的做法，见 [02](../02-宿主设计.md)），
就**必须**显式地把"exe 所在目录"和"插件目录"加入搜索路径，
否则 `notifier.imgui.dll` / `source.email.dll` / `source.gotify.dll`
会因为找不到它们而加载失败。

> **违反之后的现象**：`LoadLibrary` 失败，错误码
> `ERROR_MOD_NOT_FOUND (126)`，而日志里只会说"加载失败"，
> 看不出缺的是 `sm_imgui.dll` 还是 `sm_curl.dll`。因此加载失败时**必须**把
> 系统错误码与文本一并写进日志。

### 7.3 插件侧的四条规则

```cpp
void MyNotifier::draw_ui(sm::Span<const sm::Notification> history) {
    auto* ctx = static_cast<ImGuiContext*>(host()->imgui_context());
    if (ctx == nullptr) return;   // ① 会话可能已销毁，先判空
    // ② 不要 CreateContext / DestroyContext —— 上下文归宿主
    // ③ 不要把这个指针存进成员变量
}
```

1. **先判空。**`imgui_context()` 在没有活跃会话时返回 `nullptr`。
2. **禁止自己创建或销毁上下文。** `ImGui::CreateContext()` /
   `DestroyContext()` 属于宿主。
3. **禁止缓存。** 不保存 `ImGuiContext*`、`ImDrawList*`、字体指针，
   也不保存任何"上一帧的 imgui 状态"。会话销毁后这些立即失效。
4. **不要自己决定表面摆在哪、多大。** 内容决定大小的那类表面（通知浮层）
   由宿主按插件画出的内容撑开并摆放，插件只从自己那块表面的左上角开始画。
   **禁止**自行计算屏幕坐标，也**禁止**依赖 `io.DisplaySize` —— 窗口尺寸
   取决于内容、内容又取决于窗口尺寸，自己定位会把这两条线绕成一个越缩越小的
   死循环。

**同一个插件的不同回调可能落在不同的上下文上。** 宿主有三类表面 ——
控制面板、通知表面、每个插件一扇的详情窗口 —— 各有自己的 imgui 上下文
（[01-架构总览 §4.2](../01-架构总览.md) 的引用计数）：
`draw_ui()` 画在**通知表面**上，`draw_view()` 画在**该插件的详情窗口**上。
它们不是同一个上下文，因此 `imgui_context()` 回答的是"**当前这一帧画在哪张
表面上**"，每次回调都要重新取（[02-SDK接口参考 §6](02-SDK接口参考.md)）。
把 `draw_ui` 里拿到的指针存下来、在 `draw_view` 里接着用，画出来的东西会落到
另一个上下文上 —— 症状是"什么都不显示"，且不报错。

此外：插件**必须**用宿主随附的 `external/imgui` 同一版本编译。
不同版本的 imgui 共享上下文会直接崩溃，且症状千奇百怪。

### 7.4 插件侧的构建要求

要链接到宿主的 `sm_imgui.dll`，插件编译时必须让 `IMGUI_API` 为
`__declspec(dllimport)`。在本仓库内这**不需要做任何事** ——
`target_link_libraries(<插件> PRIVATE sm::imgui)` 已经把它通过
`INTERFACE` 传过来了。

在仓库外自己写构建脚本的插件作者，有两个等价做法：

1. 让 imgui 头走到 `external/sm_imgui_config.h`（推荐，与宿主完全一致）：
   定义 `IMGUI_USER_CONFIG="sm_imgui_config.h"`，并把该文件所在目录加进
   头文件搜索路径。imgui.h 会在定义 `IMGUI_API` 之前先 `#include` 它。
2. 自己定义 `IMGUI_API=__declspec(dllimport)`（编译期宏，命令行或源码里都行）。

> **不要**用 `target_compile_definitions(... IMGUI_API=__declspec(dllimport))`
> 这种写法。CMake 认为带括号的定义是"函数式宏"，会把括号里的内容丢掉，
> 实际传给编译器的是 `-DIMGUI_API=__declspec -Ddllimport -D)` ——
> 于是导出/导入方向整个失效，且**编译期不报错**，只在加载时才以
> `ERROR_MOD_NOT_FOUND (126)` 的形式暴露。详见
> `external/sm_imgui_config.h` 的文件头。

## 8. 自定义 UI 插件

插件完全可以用自己的原生窗口（Win32 弹窗、Toast、甚至是一个独立的
OpenGL 窗口），而不碰 imgui。这类插件需要遵守的规则更少，但有两条必须记住：

1. **窗口与消息循环由插件自己负责。** 宿主不提供窗口宿主环境。
   插件自己的窗口必须在自己的线程上跑消息循环，且**必须**在 `exit()` 返回前
   销毁 —— 否则 `FreeLibrary` 之后消息循环还会被投递到已卸载的代码段。
2. **从自己的线程回到宿主，只能通过 `post_to_main_thread()`。**
   见 [02](02-SDK接口参考.md) 里对该方法的说明。宿主对任务函数也包了崩溃屏障，
   因此它崩溃会连累**投递它的那个插件**被禁用。

> **一个常见的错误设计**：插件想"用户点击我的原生窗口时通知宿主"，
> 于是在窗口过程里直接调用 `host()->on_notify` 之类的东西。
> `IHostContext` 里**没有**任何允许从任意线程调用的方法（除了 `log` /
> `logf` / `now_unix_ms`）。正确做法是用 `post_to_main_thread` 投递。
