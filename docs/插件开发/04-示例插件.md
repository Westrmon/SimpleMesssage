# 插件开发 04 — 示例插件

仓库里的六个示例插件都在 `plugins/` 下，既是一份**用法示范**，也是宿主各子系统的
**测试载体**。每个插件在 `config/plugins/` 下都有一份带注释的示例设置文件
（文件名 = **实例 id**，见 [03-配置格式](03-配置格式.md)）；那份文件是给你抄的起点，
可以随手改。

**三个 Source 都可以开多个实例**：在控制面板的插件页点“添加实例”即可，每个实例
得到独立的设置文件（`source.email.toml` / `source.email@2.toml`）与独立的运行状态。
需要实例级数据文件时，插件从 `own_config_path()` 的文件名派生
（[02-SDK接口参考 §6.3](02-SDK接口参考.md)）；`source.gotify` 的 token 缓存就是这么做的。

| 插件 | 类型 | 用途 |
|---|---|---|
| `source.email` | Source | 用 libcurl 直连 IMAP/IMAPS 轮询邮箱，把新邮件变成通知。展示网络源、凭据类设置、"每次尝试都留痕"的失败处理 |
| `source.webhook` | Source | 用 cpp-httplib 起一个接收端口，把收到的 HTTP 请求变成通知。展示"外部推进来"的源、后台线程与 `exit()` 的关停 |
| `source.gotify` | Source | 用 libcurl 连上 Gotify 服务端的 WebSocket 流（`/stream`），把推送的消息变成通知。展示长连接客户端、断线重连与后台线程轮询读取 |
| `notifier.imgui` | Notifier | 通知浮层 + 详情视图（宽度可配），展示 `request_ui_surface` / `imgui_context` / `invoke_action` 与 imgui 的鼠标状态 |
| `notifier.console` | Notifier | 把通知写进日志，展示最小可用 Notifier（无 UI） |
| `notifier.sound` | Notifier | 按通知级别播放 WAV / MP3（可调音量），展示"纯副作用"型 Notifier、第三方解码库、后台播放线程与节流 |

几个插件会链接额外的依赖（`sm::curl` / `sm::httplib` / `sm::miniaudio`），这是对
"插件只链接 `sm::sdk`"（见 `plugins/CMakeLists.txt` 顶部第 2 条）的一次**有意破例**：
它们谈的是网络协议或音频解码，自己实现 IMAP、HTTP 解析、WAV/MP3 解码既没有价值
也不安全。破例的约束是**不得**把依赖的类型带过插件边界（[01-入门 §3.2](01-入门.md)
的规则不变：边界上只有 POD / `const char*` / `Span<>`）；链接方式按依赖形态选择 ——
libcurl 编成共享库 `sm_curl.dll`（与 `sm_imgui.dll` 同目录，两个源插件只保留导入
表），cpp-httplib 是单头文件、直接编进 `source.webhook`，miniaudio 也是单头文件、
编成静态库后分别链进宿主与 `notifier.sound`。

> **这里没有"本地文件监视"这个源。** `source.filewatch` 曾经占着 Source 的示例位，
> 但它让用户看到的是"什么都没发生"：退避基数就是插件注册的间隔、连败五次自动禁用
> 且只能手动恢复、第一次成功扫描只建基线、常态运行一条日志都不写 —— 四条语义叠在
> 一起。替代它的是下面几个**每一次尝试都会在日志里留下痕迹**的源。这也解释了为
> 什么这几个源插件在"失败可见"上格外用力。

### 两类插件，各读一半

六个插件按类型分成两组，正好覆盖两条不同的调用路径：

- **Source**（`source.email` / `source.webhook` / `source.gotify`）被**调度线程**驱动：宿主隔一段时间
  调用一次 `start()`，插件返回 0..N 条通知，并注册下一次调度时刻。它们关心的是
  "怎么在 `start()` 返回之前拿到数据，又不超时"。
- **Notifier**（`notifier.imgui` / `notifier.console` / `notifier.sound`）被**通知投递**驱动：宿主把
  匹配它订阅的通知交给它，由它决定怎么呈现。它们在**主线程**上跑，关心的是"怎么在
  一帧之内把东西画完、又不阻塞"。

两类插件继承同一个基类，宿主对它们的加载、版本校验、隔离、启停、异常处理走**完全
相同**的代码路径（见 [01-入门](01-入门.md)）。

每一节都是同一个模板：**它做什么 / 有哪些设置项 / 有哪些设计要点与坑**。

## 1. notifier.console — 不使用 imgui 的通知出口

### 它做什么

把匹配的通知写进宿主的日志，**完全不碰 UI**。它存在的意义有三个：

1. 证明非 UI 的通知出口是可行且自然的**一等公民**，而不是需要绕路的边角情况；
2. 它是"自定义 UI 插件"的**最小形态** —— 既不画 imgui、也不开窗口，只是把事件
   转成另一种输出；
3. 排障时它是**最可靠的那个观察点**：imgui 那边可能因为窗口看不见、字体没加载、
   会话被销毁而什么都不显示，而这个插件只依赖日志，日志一定是好的。

它从不调用 `request_ui_surface` / `imgui_context`，因此一个只装有本插件的安装，
空闲时**不会有任何窗口与渲染线程** —— 这正是"不用 imgui 的插件应当零 UI 开销"的
具体体现。

它只有一个回调：`on_notify`。它**不覆盖** `start()` —— 调度循环根本不会调用
Notifier 的 `start()`，`PluginBase` 的默认实现（返回 `Empty`）已经够用。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `min_level` | Enum | `warning` | `info` / `warning` / `error` | 低于该级别的通知不写进日志；默认只记 Warning 以上，避免日志被通知内容淹没 |
| `format` | Enum | `oneline` | `oneline` / `block` | 单行输出，或用多条日志拼出的多行块 |
| `include_source` | Bool | `true` | — | 是否在每行里附带来源插件 id（`Notification::source_plugin`） |

### 设计要点与坑

- **通知级别 → 日志级别是本插件自己的策略。** 它与宿主"日志转通知"的那处映射方向
  相反、概念独立，两者**不必对称**。映射的最高一档是 `Warn`：日志里的 `Error`
  表示宿主或插件自身出错，而"来了一条 Error 通知"只是通知内容，不该把日志也标成
  错误；这同时堵住了"日志 → 通知"桥（默认只消费 `Error` 日志）的反向喂养入口。
  新增级别时的退路是"宁可不升档，也不静默丢"。映射关系是：

  | 通知级别 | 日志级别 |
  |---|---|
  | `Debug` | `Trace` |
  | `Info` | `Info` |
  | `Warning` | `Warn` |
  | `Error` | `Warn` |
  | `Critical` | `Warn` |
- **`min_level` 的三个选项落在 Info / Warning / Error 三档上**，比较用的是 `Level`
  的序数：`Debug(0) < Info(1) < Warning(2) < Error(3) < Critical(4)`。
- **`include_source` 附带的"来源"指产生这条通知的插件**（`source_plugin`，由宿主
  填入）—— 与 `topic` 不同，它回答的是"谁报的"而不是"报的什么"。内部源
  （`sm.host.*`）也会出现在这里，同样有用：一眼能看出这条是日志桥转出来的。
- **`summary` 由宿主保证非空**（管线在入队时会为缺省的 summary 自动生成一个），
  插件里再兜一次底只是为了让格式串永远不会打印出 `(null)`。
- `format = "block"` 用的是**多条日志**，而不是一条带换行的日志。宿主会把消息内部的
  换行替换成空格（日志格式是每条一行），所以"在一条消息里塞换行"根本得不到多行的
  效果。
- 它**不**主动弹 UI。用户如果给一个通知配了 Action，本插件也不会渲染它 —— Action
  是否可见由具体 Notifier 决定，这是设计上刻意的分工。因此 `on_action` / `draw_ui` /
  `draw_view` 全部保持空实现。
- **默认 `warning` 的目的是"别让日志被通知内容淹没"**，而不是因为 Warning 最重要。
  需要排查"通知到底有没有到"时，临时把 `min_level` 改成 `info` 即可。
- **日志格式里不会出现换行。** 宿主把每条消息压成一行，所以摘要、title、topic 都应当
  当作单行文本处理；需要多行观感就用 `format = "block"` 拆成多条日志。

## 2. notifier.imgui — imgui 浮层与详情视图

### 它做什么

这是随附的、开箱可用的通知出口：宿主摆好的通知表面上的**无边框浮层**，默认若干秒
后自动消失（把 `toast_duration_sec` 设为 0 则常驻，直到用户收起）；点浮层上的 Action 会
打开一个**详情视图**，承载通知的完整 `content`。它同时也是"在插件里使用 imgui"的
参考实现。

**它验证了这条链路**：UI 会话引用计数（`request_ui_surface`）→ 浮层的按需创建与
销毁 → Action → `on_action` → `draw_view` 的完整往返 → 与宿主共享 imgui 上下文；
通知带 `icon` 时，还会走一遍 `icon_texture()` 的异步加载与纹理绘制。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `toast_duration_sec` | Int | `5` | 0–120 | **默认**浮层驻留时间；重要等级没有单独配置时使用。`0` 表示常驻，直到用户点「已读」/右键收起。非 0 时它就是 `request_ui_surface(秒 × 1000)` 的参数，同时决定"imgui 上下文至少活多久" |
| `toast_duration_importance_1` | Int | `-1` | -1–120 | 重要等级 1 的驻留时间；`-1` 使用默认值，`0` 表示常驻 |
| `toast_duration_importance_2` | Int | `-1` | -1–120 | 重要等级 2 的驻留时间；同上 |
| `toast_duration_importance_3` | Int | `-1` | -1–120 | 重要等级 3 的驻留时间；同上 |
| `toast_duration_importance_4` | Int | `-1` | -1–120 | 重要等级 4 的驻留时间；同上 |
| `toast_duration_importance_5` | Int | `-1` | -1–120 | 重要等级 5 的驻留时间；同上 |
| `max_toasts` | Int | `3` | 1–10 | 同时显示的最大浮层数；超出的通知不弹层，只在通知页的历史里 |
| `toast_width_min` | Int | `320` | 200–1200 | 浮层**内容**的最小宽度（像素） |
| `toast_width_max` | Int | `460` | 240–2000 | 浮层**内容**的最大宽度（像素） |
| `show_actions` | Bool | `true` | — | 是否在卡片上画**通知自己声明的** Action 按钮（关掉后它们只在详情视图里） |
| `show_details_button` | Bool | `true` | — | 是否画内置的「详情」按钮 |
| `show_read_button` | Bool | `true` | — | 是否画内置的「已读」按钮 |

### 浮层里有什么

每一张卡片（从自己那块表面的左上角往下排）画这些：

- 图标：通知的 `icon` 非空时画在内容左侧（加载中先占一个空框）；
- 一行标题：`[级别] 标题`，级别带颜色，右侧跟着一个相对时间（"刚刚"、"3 分钟前"）。
  相对时间用的是 `Notification::time_unix_ms`；规则改写 `time` 后，这里显示的
  就是通知源里的真实时间，而浮层的**到期**仍从收到通知的时刻算起；
- 摘要：在宽度区间内**换行**，而不是把窗口撑宽顶出屏幕；
- 「打开链接」：通知带 `url` 时才画；
- 通知自己声明的 Action 按钮（受 `show_actions` 控制）；
- 内置的「详情」与「已读」（不受 `show_actions` 控制）；
- 卡片之间一条分隔线。

详情视图则是：级别 + topic + 相对时间 → 图标（若有）与标题/正文并排 → 占满剩余
高度的滚动正文 → 「打开链接」/ Action 按钮 → 「关闭」。通知表面与详情窗口都是
**宿主提供**的，插件只往里面画内容。

### 设计要点与坑

- **`toast_width_min` / `toast_width_max` 的跨项约束。** schema 表达不了"min ≤ max"，
  实现是在**读取处夹取**：min 比 max 大时以 max 为准，且两者都各自不低于它们各自的
  下限（200 / 240）—— 因为配置文件可以被手改。这条必须知道，否则用户把两个值写反、
  发现改了没用，会以为坏了。宽度区间的正确归属地是插件而不是宿主：表面那扇窗口由
  **内容**撑开，而内容是插件画的。
- **图标是异步的，加载失败就不占位。** `Notification::icon` 只描述"图在哪"，纹理要
  通过 `icon_texture()` 每帧去取：首帧返回 0（此时画一个空框占位，避免图标就绪时
  整行跳动），就绪后返回非 0 句柄。失败时 `out_failed` 为真，这张卡片直接回到纯
  文本布局 —— 一张图取不到不该让通知少一块内容。非正方形图片按中心裁切到正方形，
  卡片宽度不会随图片比例忽宽忽窄。
- **浮层上的右键＝收起这张浮层，并把宿主历史里那条标为已读** —— 等价于内置的
  「已读」按钮，两者都走 `invoke_action(seq, "dismiss")`。imgui 的按钮只响应左键，
  所以落在按钮上的右键也照样命中。
- **每张卡片的控件都要有唯一 id。** 同一帧里画多条浮层，必须 `PushID(seq)` —— 整条
  卡片是一个 id 作用域（`PushID` + `BeginGroup` / `EndGroup`）。否则两条都带 `url` 的
  通知会撞上「打开链接」这个按钮，imgui 会把它们当成同一个控件。
- **右键判定要按"鼠标落在某一张卡片上"来判。** 在 `EndGroup()` 之后判
  `IsItemHovered() && IsMouseClicked(ImGuiMouseButton_Right)`，问的是整组的包围盒。
  用 `IsWindowHovered()` 会把**整张表面**上的所有浮层一次清空。
- **不要在遍历浮层队列时删元素。** 命中右键的 seq 先收进一个局部数组，循环结束后
  统一删。理由与"点击只入队、不直接调 `on_action`"完全相同（重入）。
- **这里没有"浮层摆在哪个角"这一项。** 那是宿主的 `[notify_window]`（见
  [03-配置格式](03-配置格式.md) 与 [02-宿主设计](../02-宿主设计.md)），插件看不到也
  管不着那扇窗口。示例文件里曾经写过一个 `position = "bottom_right"`，它是**死键**：
  schema 里没有它，宿主只记一条 Warn 就忽略，改了也没用 —— 它已经被删掉了。插件只从
  自己那块表面的左上角 `(0, 0)` 开始画。
- **详情视图持有完整 `content`。** 点「详情」会 `set_view_title`（宿主据此新建
  一扇独立详情窗口，并靠这条 `[视图]` 引用维持它）；用户点「关闭」或窗口的关闭按钮
  时 `close_view()` 收掉窗口。**这里不要再调用 `request_ui_surface(0)`**：0 是不可
  自然到期的永久引用，钉住的是通知表面（浮层），只有 `close_view()` 能归还；而
  `close_view()` 会把它连同常驻浮层的续租一起清掉。详情窗口不依赖浮层，浮层到期
  不会把它带走。正文可能有几十 KB（一封
  长邮件、一段日志、一份被改成单行的 JSON），因此放进一个占满剩余高度的**滚动
  子窗口**里 —— 让它随内容无限撑高，既会把按钮顶出屏幕，也会让"关闭"变得遥不可及。
- **`draw_ui` 刻意不使用它的 `history` 参数。** 浮层要回答的是"刚刚新到了什么"，而
  历史里躺着的是过去半小时的全部通知；会话销毁再重建时若照历史重建浮层，用户会突然
  被一屏早就看过的通知糊住。

### 实现细节

这些是"照抄能少踩坑"的部分，值得逐条看：

- **`initialize()` 里有一次链接期自检。** 它取一次 `ImGui::NewFrame` 的地址（用
  `volatile` 保住，以免被优化掉）。这不是装饰：本插件真的调用 `ImGui::`，而"能链接
  到宿主那份 `sm_imgui`"这件事本身值得被钉在链接期 —— `IMGUI_API` / 导入库一旦配错
  （例如忘了 `dllimport`），产物里根本不会出现对 `sm_imgui.dll` 的导入，这一步会直接
  编译不过，不必等运行到某条特定路径上才发现。**此时不要碰 imgui**：UI 会话此刻可能
  还不存在，`imgui_context()` 会返回 `nullptr`，`ImGui::` 的任何调用都会撞上断言。
- **`on_notify` 靠单调递增的 `seq` 兜重复。** 它只会在真正新到一条时被调用，插件里
  再判一次"比见过的更小就是旧的"，是为了容忍重新启用、或将来宿主补投历史时的重复
  投递 —— 重复弹一次浮层是最显眼的 bug。
- **`request_ui_surface` 的时长用正数，而不是 0。** 正数表示"宿主让会话至少活到这一
  刻"，也就是"浮层还在的时候窗口不会被销毁、CPU 不会掉到 0 再弹回来"；用 0（持续
  持有）在这里是错的，那样会话永远不会释放。常驻浮层（`toast_duration_sec = 0`）也
  不用 0：它在屏幕上时每次 `draw_ui()` 续租 `kPersistKeepAliveMs`，最后一张被收起后
  不再续租，通知表面自然到期。
- **相对时间比绝对时刻好。** 浮层用"刚刚 / 3 分钟前"这样的相对时间。格式化本地时间
  要落到 `localtime` 上，而那是平台相关的写法（MSVC 上还得用 `_s` 变体才不会有废弃
  警告）；浮层的寿命只有几秒，相对时间也更好读，于是省下了这个平台分支。
- **窗口是宿主撑开的，插件只给约束。** `SetNextWindowPos((0,0))` + 窗口 flag 组合
  （无标题栏 / 不可缩放 / 不可移动 / 不可折叠 / 不存设置 / 随内容自适应 / 出现时不
  抢焦点 / 不参与键盘导航）。宽度用 `SetNextWindowSizeConstraints` 压在区间里（太窄
  读不了、太宽顶出屏幕），高度交给内容。摘要的换行宽度从**最大宽度**推出（减去窗口
  内边距），下限 80 像素 —— 窗口宽度是被内容撑开的，把换行点定在最大宽度以内才不会
  超出上面那条约束。窗口名用 `###` 之后的 id 部分唯一化，它只是 imgui 内部查表用的
  键，不会显示。
- **按钮行有一处收尾。** 每个按钮后面都留一个 `SameLine`（好让下一个接在同一行），
  最后一个留下的那个必须吃掉（`NewLine`），否则紧接着的 `Separator` 会被画成同一行
  上的一条竖线。
- **两条内置入口不受 `show_actions` 门控。** `show_actions` 管的是**通知声明的**
  Action；「详情」/「已读」是 Notifier 自己的基本能力。通知自己已经声明过同 id 的
  按钮时，不会再画一个重复的。「已读」被点击时会立即把浮层收掉（用户不必等下一帧；
  点了按钮却还留在屏幕上是最像"没反应"的一种）。
- **`on_action` 处理三个分支**：`dismiss` 移除对应浮层；`details` 把通知拷一份放进
  详情状态、打开视图、移除对应浮层、设标题、持续持有 UI 表面；未知的 `action_id`
  直接忽略 —— 记日志反而是噪音，因为 source 插件可能就是在为别的 Notifier 声明动作。
- **跨边界进来的 `const char*` 只在本次回调内有效**，所以插件内部有一份自己的
  `NoticeCopy`（用 `std::string` 拷贝通知的各字段）。这份内存是本插件分配的，也必须
  由本插件在 `exit()` 里释放 —— 宿主既看不见也管不着。
- **`exit()` 不调用 `close_view()`。** 视图与 UI 表面引用由宿主在卸载时统一释放；
  此刻再调一次，等于在宿主正拆解会话的时候从插件里反向改它的引用计数。
- **每帧先清过期、再按上限裁剪。** `draw_ui` 开头先移除所有已到期的浮层（**全表
  扫描**，而不是只看队首 —— 常驻浮层的到期时刻是 `INT64_MAX`，它挡在队首时后面的
  限时浮层仍然必须过期），再按 `max_toasts`（读取时夹取到 `[1, 10]`）裁掉最旧的；
  裁剪之后若无话可说，这一帧什么都不画。
- **浮层驻留时长按重要等级查询。** `Notification::importance` 为 1–5 时先读
  `toast_duration_importance_N`；值是 `-1`（默认）或等级不在 1–5 时回退到
  `toast_duration_sec`。所有值在读取处再夹到 `0–120`。0 表示常驻：浮层的到期
  时刻记为 `INT64_MAX`，并在它还在屏幕上时逐帧续租通知表面；限时与常驻可以
  并存，宿主按"最长引用"记账。**到期从收到通知的当下算**，所以一条时间被规则
  重写成几小时前的存量通知，仍然会完整显示配置的时长。

## 3. notifier.sound — 按级别播放提示音

### 它做什么

一个"纯副作用"型的 Notifier：不画界面、不申请 UI 表面。每收到一条
（路由给它的）通知，就根据 `Notification::level` 选一个 WAV / MP3 文件播放。
解码与播放都交给 **miniaudio**（`external/miniaudio` 下的单文件库），插件本身
不碰任何平台音频 API —— 同一份代码在 Windows / Linux / macOS 上行为一致。

它演示的是 Notifier 的另一条边界：**不是所有 Notifier 都要有 UI**。用户可以把不同
topic 路由给不同 Notifier，让"声音提醒"只跟真正需要打扰人的源配对。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `enabled` | Bool | `true` | — | 关掉后不播放任何声音；通知仍由其它 Notifier 处理 |
| `min_level` | Enum | `info` | `debug` / `info` / `warning` / `error` / `critical` | 低于该级别的通知不发声。默认 Info 及以上；Debug 常是轮询类插件的常态输出，默认不出声 |
| `volume_percent` | Int | `100` | 0–100 | 播放通知音时的音量。0 = 静音，100 = 原始音量；只作用于本插件播放的声音 |
| `sound_debug` | Sound | `""` | ≤512 字节 | Debug 提示音；留空 = 不发声 |
| `sound_info` | Sound | `""` | ≤512 字节 | Info 提示音：WAV / MP3 文件路径 |
| `sound_warning` | Sound | `""` | ≤512 字节 | Warning 提示音 |
| `sound_error` | Sound | `""` | ≤512 字节 | Error 提示音 |
| `sound_critical` | Sound | `""` | ≤512 字节 | Critical 提示音；可以换成比 Error 更醒目的声音 |
| `throttle_ms` | Int | `500` | 0–60000 | 两次声音的最小间隔；间隔内到达的**同级或更低级别**通知不出声，更高级别仍会播放。0 = 不限制 |

**声音怎么写**：填 **WAV 或 MP3 文件的路径**（按扩展名判断，大小写不敏感）。
相对路径按宿主的配置目录（`IHostContext::config_dir()`）解析；留空表示该级别
不发声。旧版本接受的 Windows 系统声音别名（`SystemAsterisk` 等）已经不支持，
配置里留着这类值时会记一条 Warn 并跳过。默认值全部为空，因此新装或升级后需要
先选一个音频文件。

这五项用的是 SDK 的 `SettingType::Sound`：控制面板里的文本框旁会多出
**“浏览…”**（系统文件对话框，列出 `*.wav;*.mp3`）和 **“试听”**（立即播放当前值，
相对路径的解析方式与插件实际播放时一致）。文本框仍然保留，手工输入的路径照样
可以直接用；试听失败时弹窗说明原因（文件不存在、格式不受支持等）。
改完立即生效，不需要重启插件。

**音量怎么写**：`ma_sound_set_volume` 在每次播放前把 `volume_percent` 换算成
`0.0–1.0` 的增益，只作用于这一段声音；不改变系统音量，也不影响其他程序。
播放中修改设置会在下一条通知生效。“试听”走的是宿主自己的播放路径，按系统音量
播放，不读插件的 `volume_percent`。

### 设计要点与坑

- **级别来自通知本身，不是本插件推算的。** 每个 Source 自己决定 `Notification::level`
  （例如 `source.gotify` 把 Gotify 的 priority ≥8 映射为 Critical、≥5 为 Error、
  ≥4 为 Warning、≥0 为 Info、<0 为 Debug）。声音插件只消费这个结果，因此换一个源、
  换一套映射，声音策略都不需要改。
- **`throttle_ms` 只压同级或更低级别。** 刚响过 Info，紧接着来了一条 Critical，
  仍然要出声；反过来，Critical 之后的 Info 在窗口内保持安静。否则一次批量导入可能
  用几十条 Info 把真正紧急的那条盖掉。
- **提示音之间不混音。** 队列只保留最新一条：新通知到来时，仍在播放的上一段会被
  停掉并立即换成新声音。对提示音来说这是想要的行为（总播最新的事件）。
- **解码与等待都在后台线程。** `on_notify` 只把路径塞进单槽队列就返回，绝不为
  文件 IO 或音频设备阻塞主线程。设置里的 `volume_percent` 也在后台线程读取。
- **失败必须可见，但不能刷屏。** 文件不存在、没有权限、内容不是有效的 WAV/MP3、
  扩展名不是这两种、音频设备初始化失败，都会记一条 Warn；同一个错误设置只警告
  一次，直到设置值变化。
- **只要 wav / mp3。** 本项目的 miniaudio 构建本身就裁掉了 FLAC / Vorbis 解码器，
  插件还会在扩展名处再拒绝一次，避免"文档说只支持两种、实际却能播第三种"的
  模糊边界。
- **音频设备懒初始化。** 第一次真正需要播放时才 `ma_engine_init`；没有通知时
  不占用音频设备。初始化失败只警告一次，禁用再启用插件时会重试。
- **没有 UI 的 Notifier 也要正确实现生命周期。** `stop()` / `exit()` 会通知后台
  线程退出、join 它，并由线程自己 `ma_engine_uninit`：插件被禁用或卸载后继续响、
  或留下线程，都是用户与宿主都无法接受的。

### 实现细节

- **miniaudio 只实例化一次。** `external/miniaudio/miniaudio_impl.cpp` 定义
  `MINIAUDIO_IMPLEMENTATION` 并编成静态库 `sm::miniaudio`；宿主与插件只包含头文件。
  这样每个模块里都有一份实现，互不依赖，也不需要额外部署 DLL。
- **构建期只保留播放所需的部分。** `external/CMakeLists.txt` 给 `sm::miniaudio`
  加了 `MA_NO_ENCODING`、`MA_NO_GENERATION`、`MA_NO_FLAC`、`MA_NO_VORBIS`、
  `MA_NO_RESOURCE_MANAGER`，并按平台只留 WASAPI / ALSA + PulseAudio /
  Core Audio 一个或两个后端；再加 `/Gy /Gw /Zc:inline /O1`（GCC / Clang 是
  `-Os -ffunction-sections -fdata-sections`），让链接器把未引用的函数丢掉。
  关掉资源管理器后，`ma_sound_init_from_file()` 不可用 —— 播放路径改成了
  "`ma_decoder_init_file()` → `ma_sound_init_from_data_source()`"。
- **Windows 上用宽字符路径。** miniaudio 的窄路径版本在 Windows 上按当前 ANSI
  代码页打开文件，中文目录名会失败；插件用
  `std::filesystem::u8path(path).wstring()` 得到宽路径后调用
  `ma_decoder_init_file_w`，POSIX 上直接传 UTF-8 调窄版本。
- **解码器必须比 `ma_sound` 活得久。** 声音引用的是解码器这个数据源，
  因此清理顺序固定为 `ma_sound_uninit` → `ma_decoder_uninit`；试听模块
  把两者一起存在常驻状态里，插件则在后台线程的局部作用域里成对创建、成对销毁。
- **`ma_sound` 不能拷贝。** 它内嵌 `ma_engine_node`，节点地址会被注册进音频图；
  因此声音对象直接初始化到后台线程的局部变量里，绝不按值传递。
- **用 `ma_sound_at_end` 轮询播放结束。** 后台线程每 20 ms 检查一次，同时用
  条件变量等待"新通知/插件停用"；三者任一发生就 `ma_sound_uninit`。
- **链接的是 miniaudio 的依赖，不是系统音频库。** Windows 上只有 `ole32`
  （WASAPI/COM）；POSIX 上是 `Threads::Threads`、`dl`、`m`。没有 winmm，
  也没有平台条件编译的播放代码。

## 4. source.email — IMAP 轮询

### 它做什么

用 libcurl 直连邮箱（IMAP/IMAPS），把**未读**邮件变成通知。它与
`source.webhook` 正好相对：那边等别人推过来，这边按时自己去取。

**一次执行的 IMAP 对话**（实测）：

```
CAPABILITY → LOGIN → SELECT <folder> → UID SEARCH UNSEEN
    → 对每个命中项 UID FETCH <uid> BODY[]
    →（可选）UID STORE <uid> +FLAGS (\Seen)
```

只看未读、**不记高水位 UID**：后者正是"第一次成功只建基线、之后一条都不报"的
同类陷阱，本插件刻意绕开它。

**为什么用 libcurl 而不是自己写 IMAP**：自己实现意味着自己处理分片响应、字面量
长度、TLS 握手、证书校验、代理、DNS、超时 —— 每一件都是安全相关的，而它们都没有
"示例"可言。

### 它怎么把一封邮件变成通知

拿到一封原始邮件（CRLF 分隔的头部 + 空行 + 正文）后，解析只做最必要的几件事：

1. 拆头部与正文，把头部条目收进一张表；折行的续行拼回上一个字段。
2. 取 `Subject` / `From` / `Date` / `Content-Type` / `Content-Transfer-Encoding`；
   主题与发件人解 RFC 2047 的 encoded-word。
3. 是 multipart 就按 boundary 挑一份：优先 `text/plain`，其次 `text/html`（会剥
   标签），都没有就取第一份。
4. 按那份自己的 `Content-Transfer-Encoding` 解码，再按它的 `charset` 转成 UTF-8。
5. 认不出来的编码 / 字符集**保留原始字节**，并在正文最前面写一行说明。

最后组装成通知：标题取主题（按 UTF-8 码点截到 200 字节）；`content` 是
`charset_note`（如果有）+ 发件人 / 时间 + 正文（按 `content_max_kb` 截断）。

**它不做什么**：不记高水位 UID（只看未读状态）、不把已报过的邮件落盘、不转换除
UTF-8 / ISO-8859-1 以外的字符集 —— 后者需要码表或系统转换 API，前者是几千行数据，
后者会把插件绑死在 Windows 上。遇到 GB2312 / Big5 / Shift_JIS 这类字符集，它保留
原始内容并说明，而不是猜。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `host` | String | `""` | ≤128 字节 | IMAP 服务器名；**留空 = 不取邮件**，但插件仍按间隔跑，第一次记一条 Info 说明未配置 |
| `port` | Int | `993` | 1–65535 | 端口 |
| `security` | Enum | `imaps` | `imaps` / `starttls` / `plain` | 加密方式 |
| `username` | String | `""` | ≤128 字节 | 账号，通常是完整邮箱地址 |
| `password` | String | `""` | ≤256 字节 | **明文保存在插件配置文件里**；多数邮箱要的是授权码/应用专用密码 |
| `folder` | String | `INBOX` | ≤128 字节 | IMAP 文件夹名 |
| `interval_sec` | Int | `300` | 30–86400 | 轮询间隔，**同时是失败退避的基数** |
| `max_messages` | Int | `10` | 1–100 | 单次最多取几封；取不完的留到下一次（未读状态没变，不会漏） |
| `run_budget_sec` | Int | `20` | 5–25 | 单次 `start()` 的时间预算；看门狗阈值 30 秒，因此上限被卡在 25 |
| `content_max_kb` | Int | `32` | 1–48 | 正文上限，超出截断 |
| `tls_verify` | Bool | `true` | — | 校验服务器证书；只在调试时才考虑关闭 |
| `mark_seen` | Bool | `false` | — | 报告之后把邮件标为已读（`UID STORE +FLAGS \Seen`） |
| `topic` | String | `mail.inbox` | ≤128 字节 | 通知 topic，用于路由 |

**要同时接两个邮箱，就开两个实例**：各填自己的 `host` / `username` / `password`，
设置文件分别是 `source.email.toml` 与 `source.email@2.toml`。高水位就是"未读状态"
本身，两个实例各查各的账号，互不影响。若想让两个邮箱的路由/规则不同，给它们设不同的
`topic`，或用规则区分来源实例 id（[03-配置格式 §9.2](03-配置格式.md)）。

### 设计要点与坑

- **密码是明文保存在插件配置文件里的。** 本版本没有系统凭据库集成；而且多数邮箱
  需要的**不是登录密码，而是授权码 / 应用专用密码** —— 请先在服务商那边生成一个
  再填进去。这个文件包含凭据，不要提交进版本库、也不要分享给他人。
- **失败退避是"指数"的。** 第一次失败等 2×间隔，第二次 4×，依此类推，上限 30 分钟；
  连续 5 次失败后插件被**自动禁用**（只能到控制面板手动重新启用）。因此一次网络
  抖动不会立刻让你永久失去这个源，但持续失败会。
- **一次 `start()` 的执行预算上限写死为 25 秒。** 宿主看门狗阈值是 30 秒，25 留了
  余量。libcurl 的超时取的是"预算的剩余值"，**绝不写死成一个比预算还大的数** ——
  那等于让看门狗先于自己的超时开火。
- **所有可能阻塞的等待都要能被 `is_cancelled()` 打断。** libcurl 这边挂在
  `CURLOPT_XFERINFOFUNCTION` 上，回调里同时检查 `is_cancelled()` 与时间预算；被取消
  时返回 `Cancelled`（不是 `Error`），因此不计入退避。预算用完时会把已经取到的结果
  交出去，剩下的下一轮再取（未读状态没变）。
- **curl 的写回调必须返回累计接收长度，而不是本次长度。** 我们只是不要那么多数据，
  不是要中断传输 —— 返回一个短值会让 curl 报一个假的 `CURLE_WRITE_ERROR`，把"响应
  太大"误报成"传输错误"。
- **头部折行的续行要自己记住"上一个字段名"。** `std::map` 是按 **key** 排序的，
  `rbegin()` 拿到的不是"最后插入的那条" —— 一个被折成三行的 Subject 会因此只剩
  一段。
- **"已经报过哪些邮件"只记在内存里，重启后会再报一次。** 这是刻意的取舍：不落盘就
  没有状态文件损坏的问题。打开 `mark_seen` 可以避免重复，或者先在自己客户端里把
  邮件读掉。
- **失败用 `StartResult::Error` + `host()->set_error()`，绝不用 `Abort`。** "邮箱今天
  连不上"不是"这个插件该被永久禁用"。**每一次尝试都在日志里留痕**：成功投递记 Info，
  连不上记 Warn，什么都没发生记 Debug —— 不存在"它到底有没有在跑"这种问题。
- **正文与标题按 UTF-8 码点截断**（不是按字节），否则中文会被切成半个字。
- **`host` 留空时不会静默空转**：第一次执行记一条 Info 说明未配置，之后只记 Debug。
  此外 `topic` 里含非法字符会被替换成下划线并记 Warn。

### 实现细节

- **单次 IMAP 响应设了 512 KB 上限。** 给足但有限，防止一个坏掉的服务器把插件拖进
  无界内存增长。因为一次只取一封，这个上限只需容得下"一封最大的邮件"；超出的部分
  被丢弃并记一条 Warn。
- **每次请求都从干净状态开始。** 每次都 `curl_easy_reset`，漏掉这一步的典型症状是
  上一次的 `CUSTOMREQUEST` 还挂在这次请求上。另外：多线程下必须设 `CURLOPT_NOSIGNAL`
  （否则 curl 会用信号做超时），连接超时 10 秒，协议限制在 `imap,imaps`。
- **加密方式落到 libcurl 的选项上。** `imaps` 与 `starttls` 都要求
  `CURLOPT_USE_SSL=ALL`，且升级失败**必须**让整次请求失败；`tls_verify` 同时作用于
  `VERIFYPEER` 与 `VERIFYHOST`。
- **错误信息要保留 libcurl 的原话。** 用户真正需要区分的是"连不上"、"密码不对"还是
  "证书不认"，而这三者的区别只在 libcurl 的原话里。响应里**没有 `SEARCH` 行**（多半
  是服务端拒绝了这个命令）与"有行但没有数字"（没有未读邮件）是两回事，插件分开处理，
  并把响应开头一段原文写进日志 —— 没有它，这条错误就只能猜。
- **比较 `SEARCH` 行必须拿同长度的两边。** 写成 `line.substr(0, 7)` 去比 8 个字符的
  `"* search"` 永远不等 —— 这个 bug 真发生过，症状是"服务器明明回了 SEARCH，插件却
  说没收到"。
- **标已读的 `UID` 必须写进命令里。** URL 上的 `;UID=n` 只对"取信"（FETCH）这条路径
  有效；`CUSTOMREQUEST` 是原样发出去的，所以要自己拼一条完整的 `UID STORE` 命令。漏
  掉这一步的症状是服务器回一句 `Bad command` —— 邮件照报，只是没标已读。
- **通知的三份字符串一次分配。** 标题、正文、topic 放进同一块 arena，与 arena 的用法
  一致；`content` 由 `charset_note`（如果有）+ 发件人/时间 + 正文组装而成。去重键
  （`id`）留空 —— 完全不去重，由插件自己的 `reported_` 负责不重复。
- **MIME 处理是"够用就好"的。** 只认最常见的形状：multipart 取第一个 `text/plain`，
  只有 HTML 就粗剥标签；认不出来的传输编码 / 字符集一律**原样保留**，并把"为什么
  可能看不懂"写在正文最前面，而不是去猜。`multipart/alternative`（纯文本 + HTML
  两份）时，`content` 取自**纯文本**那一份。中文邮件的主题几乎总是 RFC 2047 的
  encoded-word（`=?UTF-8?B?...?=`），所以要解它 —— 不解的话用户看到的就是一串
  `=?UTF-8?B?5rWL6K+V?=`，等于没有标题。
- **先转码再剥标签。** 把 ISO-8859-1 展开成 UTF-8 之后，正文里就不会再出现"夹在多
  字节序列中间的 ASCII 尖括号"。反过来的话，一个 `0x3C` 字节既可能是 `<` 也可能是
  某个字符的一半，剥标签会从正文里吃掉一块。
- **常态与失败分得很清。** 没有新邮件是 `Empty` + 一条 Debug；列表里确实有未读、却
  一封都没取到，那是 `Error`（带上最后一封的原因）。**每条返回路径都 `schedule_next`**，
  否则插件只跑一次就休眠，用户会以为它坏了。
- **`curl_global_init` 放在 `initialize()` 里。** 它不是线程安全的，必须在别的线程用
  它之前调用，而 `initialize()` 正好是"插件被加载之后、第一次 `start()` 之前、主线程"
  这个时机；`exit()` 里对应地 `curl_easy_cleanup` + `curl_global_cleanup`。

## 5. source.gotify — Gotify WebSocket 客户端

### 它做什么

连接 Gotify 服务端的 **WebSocket 流**（默认 `/stream?token=<客户端令牌>`），把服务端
推过来的每条消息变成通知。它与 `source.webhook` 是同一职责的两个方向：那边在本机开
端口等别人连进来，这边作为**客户端**主动连出去，并一直保持连接。

Gotify 服务端只会把消息推给**当时在线**的客户端；断线期间产生的消息不会补发。因此
这不是一个"离线也能收齐"的通道，重连成功之后只会有新消息。另外，本插件用的是
**客户端令牌**（Client Token），它才能看到所有 App 的消息；应用令牌（App Token）只
用于向 Gotify 发消息，不是这里的凭据。

凭据有两种给法：直接填 `client_token`；或者填 `username` + `password`，让插件用
HTTP Basic Auth 调 `POST /client` 自动创建客户端并取回令牌。后者不需要用户手工去
Gotify 的 Clients 页复制令牌。

### 一条消息的一生

1. 拿到客户端令牌后（手工填写，或登录 `POST /client` 取得），先立刻用
   `GET /application` 拉取应用列表，记录 `id → {name, image}`。
   `image` 是服务端根地址下的相对路径，插件把它拼成完整的 `http(s)://` 图标 URL。
2. 接收线程用 libcurl 完成 WebSocket 握手：`CURLOPT_CONNECT_ONLY=2`，协议限定在
   `ws,wss`。
3. 接收线程以 100 ms 的节奏调用 `curl_ws_recv`。它不阻塞：没数据时返回
   `CURLE_AGAIN`，所以线程既不会空转烧 CPU，也能及时看到 `stop_`。
4. 分片消息按 `CURLWS_CONT` / `meta->bytesleft` 攒齐；单条消息超过 1 MiB 就整条丢弃。
5. 一条完整消息交给极小的 JSON 扫描器，取出 `id` / `appid` / `title` / `message` /
   `priority` / `date` / `extras`，按 `min_priority` 过滤后入队（满了丢最旧的）。
   命中的应用决定通知的呈现：
   - **应用名** → `Notification::title`
   - **Gotify 消息的 `title`** → `Notification::summary`（简介）
   - **Gotify 消息的 `message`** → `Notification::content`（详情正文）
   - **应用图标** → `Notification::icon`
6. 下一次 `start()`（**调度线程**）把队列取走、分配进 arena、变成通知投递，并注册
   下一次调度。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `server_url` | String | `http://127.0.0.1:8080` | ≤512 字节 | Gotify 服务端**根地址**；`http` 走 `ws`、`https` 走 `wss`，也接受 `ws://` / `wss://`。可以带反向代理的子路径前缀，不要带 `/stream`（带了也不会重复拼接） |
| `username` | String | `""` | ≤256 字节 | 登录用户名（可选）；与 `password` 一起填写后，插件通过 HTTP Basic Auth 调 `POST /client` 获取客户端令牌 |
| `password` | String | `""` | ≤256 字节 | 登录密码（可选）；会以明文随插件设置保存，`http://` 连接时网络上只做了 Base64，建议改用 HTTPS |
| `client_token` | String | `""` | ≤256 字节 | **客户端令牌 Client Token**（`gtfyc.` 开头），不是应用令牌（`gtfya.` 开头）；在 Gotify 网页的 Clients 页创建。非空时优先使用，不再登录。与 `username`/`password` 都不填 = 不接收任何消息（日志说明原因） |
| `client_name` | String | `SimpleMessage` | ≤128 字节 | 登录模式下创建的客户端名；拿到的令牌缓存在数据目录，后续启动直接复用。多个实例请使用不同的名字 |
| `stream_path` | String | `/stream` | ≤128 字节 | WebSocket 端点；反向代理把 Gotify 挂在子路径下时通常保持默认，前缀写在 `server_url` 里 |
| `topic` | String | `gotify.in` | ≤128 字节 | 通知 topic，用于路由；非法字符会被替换成下划线并记 Warn |
| `poll_interval_sec` | Int | `2` | 1–60 | 收到的消息最多攒这么久才变成通知；即"收到 → 看见"的延迟上限 |
| `min_priority` | Int | `-128` | -128–1024 | 低于此值的消息直接丢弃；`-128` 表示全部接收 |
| `use_priority_level` | Bool | `true` | — | 用 Gotify 优先级决定通知级别：≥8 Critical、≥5 Error、≥4 Warning、≥0 Info、<0 Debug；关闭后一律 Info |
| `content_max_kb` | Int | `32` | 1–48 | 正文上限（按 UTF-8 码点边界截断）；上限低于宿主的 64 KB |
| `queue_max` | Int | `256` | 4–4096 | 待投递队列上限；满时丢**最旧**的一条并计数 |
| `ping_interval_sec` | Int | `30` | 0–3600 | 定期发 WebSocket PING，避免被中间代理当空闲连接断开；0 = 不主动发（服务端的 PING 仍由 libcurl 自动回 PONG） |
| `tls_verify` | Bool | `true` | — | 校验服务器证书；**只在调试时才考虑关闭**，自签名证书请装进系统信任链 |
| `include_extras` | Bool | `false` | — | 把原始的 `extras` JSON 附在正文后面，便于排查发送方带了什么 |

### 设计要点与坑

- **令牌在 URL 里，所以日志里绝不能出现完整 URL。** `stream_url` 带
  `?token=...`，而 `display_url` 是去掉查询串的那份，所有日志用的都是后者。令牌还会
  做 URL 编码 —— 它可能包含 `+`、`/`、`=` 这类字符，直接拼进查询串会被服务端解成
  别的东西。
- **登录拿到的令牌必须自己缓存。** Gotify 3.x 的 `GET /client` 不返回 token，
  `PUT /client/{id}` 返回的 token 实际不可用；只有 `POST /client` 响应里的那个
  token 能用于 `/stream`。所以插件把它连同 server / username / client_name 写进
  `<data_dir>/<实例 id>-client-token.json`，启动时先读缓存；WebSocket 握手返回
  401 时删除缓存并重新登录一次（避免密码也错时无限新建客户端）。
  **文件名从 `own_config_path()` 派生**：首个实例仍是
  `source.gotify-client-token.json`，`source.gotify@2` 得到自己的
  `source.gotify@2-client-token.json`。固定文件名会让两个实例互相覆盖凭据。
- **应用元数据只在启动或配置变化时拉取。** `GET /application` 用
  `X-Gotify-Key: <客户端令牌>` 认证；拿到应用列表后，消息里的 `appid` 才能映射成
  应用名、图标与简介。拉取失败不会阻塞接收消息，只是退回旧行为（用 Gotify 消息
  自己的 `title` 当标题，不显示图标）；连接过程中应用改名或换图标要等下一次
  重连/配置变化才会刷新。
- **图标直接交给宿主下载，不落盘。** Gotify 的 `Application.image` 是类似
  `image/xxxx.png`、`static/defaultapp.png` 的相对路径，前端的用法是
  `server_url + image`。插件按同样规则拼成完整 URL 填进 `Notification::icon`；
  宿主的 `icon_texture()` 会异步下载、解码并缓存，失败只是不显示图标。
- **配置一变就重连。** `identity` 由"流地址、用户名、客户端名、令牌、密码、是否
  校验 TLS"组成，`start()` 把它与上次比较；不同就递增 `generation`，接收线程看到
  新代号后主动断开旧连接再连新的。这样改服务器、改账号、改令牌、开关证书校验都不
  需要重启插件。
- **断线重连是指数退避的**：3、6、12、24、48、60、60……秒封顶。第一次失败记 Warn，
  之后的失败记 Debug，恢复时记一条 Info —— 长时间断网不应该把日志刷满。重连不会丢弃
  已经在队列里的通知。
- **WebSocket 读取是非阻塞的，所以要自己轮询。** `curl_ws_recv` 在没有数据时返回
  `CURLE_AGAIN`；接收线程用 100 ms 的可中断休眠循环，而不是在 `recv` 上阻塞 ——
  否则 `exit()` 想 join 时可能永远等不到线程醒来。`CURLE_GOT_NOTHING` 与
  `CURLWS_CLOSE` 都按"连接已关闭"处理并触发重连。
- **分片消息必须攒齐再解析。** 一个 JSON 通知可能被拆成多个帧；只有
  `bytesleft == 0` 且没有 `CURLWS_CONT` 时才是最后一片。单条消息硬上限 1 MiB，
  超过就丢弃并计数 —— Gotify 的通知远小于它，这个上限只用来防坏服务端。
- **PING/PONG 由 libcurl 自动处理。** 收到服务端 PING 时它会自动回 PONG，不会把控制
  帧交给调用方；插件自己的 `ping_interval_sec` 只是额外保活，设 0 是安全的。
- **时间优先用 Gotify 的 `date`。** 它是 RFC 3339（带时区偏移，例如
  `2024-08-29T23:22:22.7696814+08:00`）；解析失败才退回 `now_unix_ms()`。解析器故意
  只认 RFC 3339 的固定形状，认不出就降级，不猜。
- **去重键是 `gotify:<id>`。** `Notification::id` 是稳定的去重键，Gotify 的消息 id
  正好是稳定的；没有 id 的消息才留空。
- **标题、简介与正文都有兜底。** 映射到应用时，标题用应用名，Gotify 消息自己的
  `title` 降为简介；映射不到（应用列表没拉到、appid 不认识）才退回用消息 `title`
  当标题，连它都为空时用 `Gotify 应用 <appid>`（连 appid 都没有就是 `Gotify 消息`）。
  正文为空时用 `(无正文)`。用户不会看到一张空白卡片。
- **`poll_interval_sec` 是延迟上限，不是"处理时间"。** 通知只能在 `start()` 里产生
  （见 [01-入门 §4](01-入门.md)），接收线程只负责入队。
- **失败用 `Error` + `set_error()`，不用 `Abort`。** "Gotify 今天连不上"不是"这个插件
  该被永久禁用"；错误原文（libcurl 的 `errbuf`）会一直显示在插件页上，直到连接恢复
  或配置被清空。

### 实现细节

- **libcurl 的 easy 句柄只在接收线程里创建、使用、销毁。** 它不是线程安全的，跨线程
  共用需要额外的锁；这里让一个句柄只属于一个线程，省掉了这类问题。`initialize()`
  里的 `curl_global_init` 与 `exit()` 里的 `curl_global_cleanup` 成对出现，且都在
  主线程。
- **`CURLOPT_NOSIGNAL` 是必须的。** 多线程程序里 libcurl 不能用信号做超时（否则会
  打到别的线程）。连接超时 8 秒、总超时 15 秒，足够覆盖握手，又不至于让 `stop()`
  等太久。
- **`PROTOCOLS_STR="ws,wss"` 把协议锁死。** 即使有人把 `server_url` 写成了
  `file://`，也会在 curl 这一层被拒绝。
- **`tls_verify` 同时作用于 `SSL_VERIFYPEER` 与 `SSL_VERIFYHOST`。** 只关其中一个
  并不会真正"跳过校验"，反而会得到一个更难解释的错误。
- **错误信息保留 libcurl 的原话。** `CURLOPT_ERRORBUFFER` 拿到的文本（证书、DNS、
  连接被拒）比 `curl_easy_strerror` 的通用描述有用得多，它会被写进 `set_error()`；
  用户看到的就不再只是一句"连接失败"。
- **`NOMINMAX` 必须在所有头之前定义。** libcurl 的 Windows 头会带进 `<windows.h>`，
  后者把 `min` / `max` 定义成宏，会让 `std::min` / `std::clamp` 直接编译失败。
- **接收线程与调度线程之间只有一把锁保护的队列。** 设置由 `start()` 快照成 `Config`
  交给接收线程；接收线程只调用 `log` / `logf` / `now_unix_ms`，不碰其它宿主接口。

## 6. source.webhook — 本机 HTTP 接收

### 它做什么

在**本机开一个 HTTP 接收端口**，等外部系统把事件推过来。其它 Source 都是"宿主按时
问我、我去外面取"（轮询），本插件反过来：它必须在自己起的线程里接请求，再用一次
`start()` 把攒下的请求变成通知。这是"把外面的东西收进来"这个职责在**接收方向**上
的落点，另一个方向由 `source.email` 承担。

**四类响应**（实测）：

| 情形 | 响应 |
|---|---|
| 路径匹配且令牌对 | `202` |
| 令牌不对 | `401` |
| 路径不对 | `404`，并记一条 Warn 说明"当前只接收 POST `<path>`" |
| 方法不是 POST | `404`，记同样的 Warn |

### 一条请求的一生

1. 请求到达**监听线程**，先过 pre-routing 钩子：路径对不上或不是 POST，记一条 Warn
   后照旧交给 httplib（回 404）。
2. 命中路由的请求进处理函数：查令牌（不对回 401）→ 查体积（超了回 413）→ 按快照里
   的规则取标题、级别、图标、正文，攒成一条待投递记录。
3. 记录推进队列（满了先丢最旧的一条并计数），立刻回 `202`。
4. 下一次 `start()`（**调度线程**）把整条队列取走、变成通知投递给宿主，并注册下一次
   调度。

### 设置项

| 设置项 | 类型 | 默认值 | 范围 | 说明 |
|---|---|---|---|---|
| `port` | Int | `8721` | 1024–65535 | 接收端口；改端口在下一次调度时重建监听，不需要重启插件。**多实例时必须给每个实例不同的端口** |
| `bind_addr` | String | `127.0.0.1` | ≤64 字节 | 绑定地址；`0.0.0.0` 会让同网段任何机器都能投递 |
| `path` | String | `/hook` | ≤128 字节 | 只接收这个路径上的 POST，留空 = 任何路径；不含正则元字符时按**字面量**比较，含 `.^$\|()[]{}*+?\` 时按**正则**匹配 |
| `token` | String | `""` | ≤128 字节 | 留空 = 不校验；非空时比对请求头 `token_header` 或查询参数 `?token=` |
| `token_header` | String | `X-SimpleMessage-Token` | ≤64 字节 | 令牌所在请求头 |
| `topic` | String | `webhook.in` | ≤128 字节 | 通知 topic，用于路由 |
| `poll_interval_sec` | Int | `5` | 1–3600 | 收到的请求最多攒这么久才变成通知；**这是"对方发过来"到"你看见"的延迟上限** |
| `max_body_kb` | Int | `16` | 1–1024 | 请求体上限，超过拒绝（HTTP 413） |
| `queue_max` | Int | `256` | 4–4096 | 待投递队列上限；满时丢**最旧**的并计数 |
| `include_headers` | Bool | `false` | — | 打开后把请求头并进 `content`，便于排查对方到底发了什么 |

### 设计要点与坑

**三条结构性约束**（改动它时不要破坏，同 [01-入门 §4.1](01-入门.md)）：

1. 监听线程与调度线程之间**只通过一把锁保护的队列**通信，没有别的共享状态；
2. 监听线程**不**直接调用宿主的任何方法，除了 `log` / `logf` / `now_unix_ms` 这三个
   "任意线程可调用"的；设置也一样 —— 需要用的设置由 `start()` 快照一份，再交给监听
   线程读；
3. `exit()` 返回前必须让监听线程与它派生的所有线程都结束。宿主在 `exit()` 返回后就
   会 `FreeLibrary` 本模块，留下的线程会跳进已释放的代码段。

- **端口被占用这件事在 Windows 上是静默的，所以插件自己探一次。** httplib 给监听
  套接字设的是 `SO_REUSEADDR`，它允许第二个进程绑同一个端口（后绑的抢走新连接），
  于是 `bind` **不会**失败 —— 两个实例都打印"已开始监听"，请求只落到其中一个。所以
  **光靠 bind 失败判断不出来**，必须在绑定之前用一次短超时的 HTTP 探测问一句"这个
  端口上是不是已经有东西在讲 HTTP"。探到冲突**只记 Warn 不拦**：拦下来会破坏"改了
  设置就在同一个端口上重建监听"这条路径。代价是 httplib 的**客户端**实现也被拉进了
  这个插件（只为了这一句日志）。探不到"占着端口却不讲 HTTP"的邻居 —— 而那种邻居
  本来也不会抢走我们的请求。
  **两个 `source.webhook` 实例共用同一个端口时，症状正是"两个都显示运行中，
  但只有其中一个收到请求"** —— 各自设置文件里的 `port` 必须不同。监听失败只影响
  该实例的 `initialize()` / 下一次调度，另一个实例不受牵连。
- **重建监听的条件必须包含 `path`。** 端口或地址变了要重建，`path` 变了也**必须**
  重建 —— 因为路由模式是在注册时定死的，光换配置里的 `path` 并不会让 httplib 改判。
  症状是"改了 path 却还是只有老路径能投递"，而且新路径的请求会被 pre-routing 钩子
  记成 Warn，看起来像钩子错了。改设置在下一次调度时生效，不需要重启插件（两次监听
  之间会有最多一个间隔的空窗）。
- **请求体硬上限 1 MiB，队列 `queue_max` 满了丢最旧的那条并计数。** 丢最新的话，用户
  会**永远看不到当前发生的事**。1 MiB 是"再大也不接受"的兜底：宿主自己的 `content`
  上限是 64 KB，超过它宿主会截断，没必要把更大的东西留在内存里。
- **为什么请求要攒到下一次 `start()` 才变成通知。** 通知只能在 `start()` 里产生
  （见 [01-入门 §4](01-入门.md)），接收线程只负责入队。因此 `poll_interval_sec` 就是
  端到端延迟的上限，而不是"处理时间"。
- **路径设置要先编译一次正则。** cpp-httplib 的 `Server::Post` 内部会构造
  `std::regex`，一个写错的正则会在**注册路由时**抛异常；异常从 `start()` 里穿出去
  就是跨模块边界的行为，等于崩溃。所以插件自己先 `try/catch` 编译一次，失败就记
  Warn 并保持原有监听不变。设置是用户输入，必须当成不可信数据先验。
- **需要一个 pre-routing 钩子。** 打错端口或打错路径的那次请求，httplib 会直接回
  404 —— 我们的处理函数根本不会被调用，于是"外面确实打过来了，只是设置对不上"在
  日志里**一行都不会有**。钩子只记一条 Warn，然后照旧把请求交回给 httplib，404 的
  对外行为不变。钩子的路径判据必须与 httplib 完全一致，否则它会为一条**正常的**
  请求报假警。
- `topic` 里含非法字符会被替换成下划线并记 Warn。

### 实现细节

- **`RequestConfig` 快照。** 监听线程不许调 `setting_*`，所以需要用的设置由 `start()`
  拷一份进快照，监听线程只读这份快照。它同时保证"用户改了设置"与"正在处理的这条
  请求"之间不会打架：一次请求从头到尾只看同一份快照。
- **自己写了个极小的 JSON 扫描器。** 不引 JSON 库只是为了避免为"取顶层对象的一个
  字符串字段"多一棵依赖树、多一份要跟进的安全公告。它只认最简单的形状，认不出来就
  回退到"用第一行当标题"，降级路径明确。标题的优先级是：JSON 顶层 `title` → 请求体
  第一行 → `METHOD path`；`level` 字段认识就尊重它，不认识就当没写；顶层 `icon`
  原样带给 Notifier（按 `kMaxIconBytes` 截断），内容是否是能加载的图片由宿主在
  展示时判断 —— Source 不该为了校验图标去下载它。`\uXXXX` 转义按
  "两个码点各自编码"处理 —— 超过 U+FFFF 的字符会变成两个三字节序列，不会崩、只是
  长得不对。
- **令牌与体积都在处理函数里再查一遍。** 令牌来自请求头 `token_header` 或查询参数
  `?token=`，二者其一完全一致即可；体积检查是必要的，因为设置变小之后仍要拦。
  `include_headers` 打开时，会把来源 `IP:port`、方法、路径和请求头附在 `content`
  前面。
- **队列满了 `pop_front` 先丢最旧的，再 `push_back`。** `start()` 里先用一次 `swap`
  把整条队列取走再做投递，因此监听线程与调度线程的临界区都很短（拷几个小字符串 /
  移动一个结构体），不会有锁竞争问题。
- **arena 分配失败时丢这一批，而不是返回 `Error`。** "这一批太大"不是"插件坏了"，
  返回 `Error` 会让调度器退避。处理器本身还挂了 `set_exception_handler`，把未预期的
  异常变成一条 Warn 加一个 `500`，不让异常越过边界。
- **线程池与超时是刻意压小的。** 对一个只收本机 webhook 的接收端，httplib 默认的
  `max(8, CPU 核数)` 个线程是浪费，改成 2 常驻、最多 4；读写都要有超时（否则一个
  只连上不发数据的客户端能让线程一直卡在 `read` 上，而 `stop()` 要等线程池里的线程
  全部结束）；keep-alive 超时压到 1 秒，退出就快得多。响应头顺手带上
  `Connection: close`，让线程立刻回到空闲。
- **`exit()` 里再兜一次关停。** `stop()` 通常已经停了监听并清了队列，但 `exit()` 可能
  在没有 `stop()` 的路径上被调用（例如 `initialize` 失败后卸载），所以它自己也要确保
  所有线程都已结束。
- **上限与截断都留了余量。** 标题按 UTF-8 码点截到 200 字节、正文截到 60 KB ——
  分别低于宿主的 256 字节与 64 KB 上限。收到了多少条、拒绝了多少条、丢了多少条各有
  计数器，用于在日志里把话说清楚。

## 7. 从这些插件里能学到什么

六个插件合起来，能提炼出几条所有插件都适用的共性：

- **失败必须可见。** 不许静默空转、不许静默忽略：第一次执行说明"为什么什么都没做"，
  常态运行只记 Debug，真正的失败记 Warn + `set_error`。
- **把"常态"与"失败"分开。** 没有新数据 / 没有新请求是 `Empty`；真正的失败才是
  `Error` + `set_error()`。
- **不要用 `Abort`**，除非"配置不可恢复地失效"（那等于自己要求被永久禁用）。
- **通知只能在 `start()` 里产生**；需要跨线程时只走队列，派生线程不碰宿主接口。
- **边界上只有 POD / `const char*` / `Span<>`**；额外依赖（`sm_curl.dll` /
  cpp-httplib）的类型绝不带过边界。
- **设置项在 `start()` / `draw_*` 里读，不缓存** —— 用户改了设置要立即生效。
- **自己声明的上限低于宿主的上限**，字符串截断按 UTF-8 码点做。
- **`exit()` 里释放自己创建的一切**（线程、窗口、句柄、定时器、非 arena 内存）。
- **给用户看的错误要保留原始文本**（服务端 / libcurl / 操作系统的原话），不要把它
  翻译成一句笼统的"失败了" —— 分布式问题里，原话往往就是定位的全部线索。
- **别把"常态"写成 Info。** 每次轮询都记一条 Info 会把日志灌满；常态用 Debug，让
  Info 留给"真的做了什么"。
