# 插件开发 03 — 配置格式

配置全部是 TOML。**只有三类文件**，边界划得很清楚：

| 文件 | 回答什么问题 | 谁写 |
|---|---|---|
| `config.toml` | 宿主自己的事：应用行为、插件启用状态、路由覆盖 | 用户手工编辑 + 宿主写回 |
| `config/plugins/<插件id>.toml` | 某个插件的设置项 | 用户手工编辑 + 宿主写回 |
| 插件自己的状态文件（在 `data_dir`） | 插件的缓存、索引、运行状态 | 只有插件自己（宿主不碰，也不要求格式） |

> **为什么插件设置不放在 `config.toml` 里。** 因为这两类数据的生命周期不同：
> 插件 DLL 可能被删掉，而配置里还留着它的启用状态；反过来，插件设置应当能
> 跟着插件单独分发、备份、重置。混在一个文件里会同时破坏这两件事 ——
> 删插件时得记得清配置，备份插件时得从大文件里抠出属于它的那几行。

**本文的每条规则都是实现约束** —— 宿主按它实现，校验失败时的行为也由它规定。

## 1. 目录布局与路径解析

```
<配置目录>/
├── config.toml                    ← 宿主配置
├── config.toml.bak                ← 写回前自动备份（只保留一份）
└── plugins/
    ├── source.email.toml      ← 插件设置，文件名 = 插件 id
    ├── source.email.toml.bak
    └── notifier.imgui.toml

<数据目录>/
├── logs/
│   └── simplemessage-YYYY-MM-DD.log
└── <插件id>/                      ← 插件自己的状态文件，宿主不解析
```

### 1.1 配置目录的确定顺序

```
1. 命令行 --config-dir <路径>          ← 最高优先级
2. <exe 所在目录>/config/              ← 若能创建且可写
3. %APPDATA%\SimpleMessage\config\     ← 回退（Windows）
   ~/.config/simplemessage/            ← 回退（POSIX）
```

**目录不存在时自动创建。**如果第 2 项因为"安装在 `C:\Program Files` 下"
而不可写，就安静地回退到第 3 项，并在日志里记一条 Info 说明实际用的路径。

> **为什么"exe 目录优先"而不是反过来**：这是一个绿色软件风格的工具，
> 用户把它解压到 U 盘里跑、或者放在一个便携目录里，期望配置就在旁边。
> 但安装在受保护目录时又不能失败，所以保留回退。**实际用的路径必须
> 写进日志** —— 否则用户会对着"我改了配置怎么没生效"发呆，
> 而真相是他改的是另一个 `config.toml`。

### 1.2 数据目录的确定顺序

```
1. 命令行 --data-dir <路径>
2. <配置目录的父目录>/data/            ← 通常是 exe 目录旁
3. %APPDATA%\SimpleMessage\data\
```

**必须与配置目录区分开。**配置目录的内容会被用户手工编辑、被"重置配置"
逻辑处理、被备份；数据目录不会。插件的缓存、索引、上次运行状态应当放数据
目录（`IHostContext::data_dir()`），否则用户在重置配置时会莫名其妙丢掉它们。

### 1.3 插件目录

```
1. 命令行 --plugin-dir <路径>
2. <exe 所在目录>/plugins/
```

见 [06](../02-宿主设计.md) 的插件扫描与加载流程。

## 2. `schema_version` 与迁移

**每个配置文件的第一行都是 `schema_version`。**

```toml
schema_version = 1
```

### 2.1 三种情形

| 文件里的版本 | 宿主动作 |
|---|---|
| **等于**当前版本 | 正常读取 |
| **小于**当前版本 | 走**迁移链**（见 §2.3），成功后按新版本写回 |
| **大于**当前版本 | **拒绝启动**，日志与控制面板给出明确提示 |

> **为什么"更高版本"要拒绝，而"损坏"却不拒绝**（§5）。
> 这两件事的性质完全不同：
> - **更高版本**意味着用户刚用新版宿主跑过，配置里有旧版宿主**不认识的
>   语义**（比如某个键的含义被改掉了）。旧版宿主若照读，可能把用户的
>   设置静默改错 —— 而且它会用旧格式写回去，把新版的数据毁掉。
>   这是**数据损坏**，必须停下。
> - **损坏**（语法错、截断、乱码）不携带任何语义，用户不会因为"从默认值
>   开始"而损失什么有价值的东西。此时能启动比停下来更有用。
>
> 一条通用的判据：**能启动就启动，除非启动会破坏用户的既有数据。**

### 2.2 拒绝启动时的行为

- 日志记 Error，含期望版本、实际版本、文件路径。
- 以 `--console` 方式启动时，在控制台打印同样的信息。
- **不修改配置文件、不生成备份、不写回。**
- 退出码非零（见 [06](../02-宿主设计.md) 的退出码约定）。
- 提示用户：升级宿主，或删除该文件（会丢失该文件里的设置）。

### 2.3 迁移链

```
v1 ──→ v2 ──→ v3
```

**每次只走一步**，每一步是一个独立函数 `migrate_1_to_2(const toml::table&)`。
不支持直接 v1 → v3 的跳跃迁移 —— 那会让迁移逻辑变成 n² 条路径。

- 迁移**在内存中**完成：读原始 TOML → 逐级转换 → 得到当前版本的表。
- 迁移**成功后**才写回（并备份）。
- **迁移过程中的任何一步失败**（例如 v2 需要 v1 里的某个字段而它不存在）
  → 退回"按默认值 + 保留能读的项"处理，并记一条 Warn。
  **不拒绝启动** —— 迁移失败是宿主自己的 bug，不该让用户承担。
- 迁移函数必须**只增不改**：一旦 v1→v2 发布，`migrate_1_to_2` 的行为
  就固定了。改它等于让"用旧版宿主导出过 v2 配置的用户"走进另一条路径。

> **为什么迁移要做成链而不是"一次性转换"**：用户可能从 v1 直接升到 v5。
> 链式迁移让每一段的测试只需要覆盖"相邻两个版本"，而 n 个版本只需要
> n-1 个测试。这也让"哪一步改了什么"在代码里一眼可见。

## 3. `config.toml` 完整参考

### 3.1 `[app]` — 应用行为

| 键 | 类型 | 默认 | 取值范围 | 说明 |
|---|---|---|---|---|
| `notify_log_level` | string | `"error"` | `off` / `error` / `warn` / `info` | 由日志转成通知的最低级别 |
| `log_level` | string | `"info"` | `trace` / `debug` / `info` / `warn` / `error` | 写入日志文件的最低级别 |
| `log_retention_days` | integer | `7` | `1` – `365` | 日志保留天数 |
| `log_max_total_mb` | integer | `32` | `1` – `1024` | 日志总大小上限（MB） |
| `ui_font_size` | integer | `16` | `10` – `32` | imgui 字号（像素） |
| `single_instance` | boolean | `true` | — | 单实例保护 |
| `notification_history_size` | integer | `200` | `1` – `200` | 内存历史条数上限 |

#### `notify_log_level` 的细节

- 设成 `off` **只关闭"普通日志 → 通知"这条通道**。
- **结构性事件不受本项控制**：插件崩溃 / 被禁用、配置损坏、
  宿主启停、插件加载被拒绝 —— 这些**始终**产生通知。
- 由日志产生的通知有防刷限制：topic 为 `sm.host.log` 的通知被限制在
  **10 秒内最多 5 条**，超出的被合并计数。

> **为什么结构性事件不受阈值控制**：把"插件崩了却没告诉你"和"日志太吵"
> 当成同一件事，是本可以避免的两类失败。用户调低通知阈值时想要的是
> "别拿日常消息烦我"，而不是"别告诉我东西坏了"。**这两件事必须能被
> 分别配置**，而"结构性事件永远通知"是最简单的实现方式。

> **为什么 `sm.host.log` 要限速**：一个每 200ms 轮询失败一次的插件，
> 会在 10 秒内产生 50 条 Error 日志。没有限速的话，用户会被 50 条通知
> 淹没，而且每一条的内容都一样。合并成"6 条类似错误（已合并 45 条）"
> 传递的是同样的信息，且不会把界面变成一个无法阅读的列表。

#### `log_level` 与通知的关系

通知**不按 `info` 级写日志**，只进 `trace` / `debug`。
因为一条通知的旅程会涉及多个组件，按 `info` 写会让日志被高频通知淹没。

**默认的 `log_level = "info"` 意味着"默认情况下看不到通知的详细日志"。**
需要排查通知管线问题时，临时改成 `debug`。

#### `notification_history_size` 与 SDK 硬上限

`sm::limits::kNotificationHistoryCapacity`（200）是**硬上限**，
本项是**用户可调的实际值**：

```
实际历史条数 = min(notification_history_size, kNotificationHistoryCapacity)
```

配置超限时夹到 200 并记 Warn。**不能让配置突破 SDK 上限** ——
插件是基于上限写的（例如"最多显示 200 条"的缓冲区）。

#### `ui_font_size` 的范围为什么是 10–32

- 小于 10：中文笔画粘连，不可读。
- 大于 32：字号越大，imgui 的字体图集越大。为了一个"更大"的偏好而
  在资源受限的机器上占掉几 MB 显存不划算 —— 需要更大字号的用户
  应当改系统的 DPI 缩放。

### 3.2 `[plugins]` — 插件启用状态

```toml
[plugins]
"source.email" = true
"source.webhook" = true
"notifier.imgui" = true
"notifier.console" = false
```

- **键是插件 id**（`PluginMeta::id`），**值是该插件是否启用**。
- id 里含点号，作为 TOML 键**必须加引号**，否则 `source.email = true`
  会被解析成"`source` 表里的 `email` 键"。
- **这不是"已安装插件列表"。**插件列表**永远**由扫描插件目录得到。
  本表只记录"某个**已知**插件是否启用"。
- 表里存在但目录里没有对应 DLL 的项：**忽略并记一条 Info**，不导致启动失败，
  也不从表里删除（用户可能只是临时把 DLL 挪走了）。
- 目录里有 DLL 但表里没有的项：**使用该插件的默认启用状态**
  （即"启用"），并把这一项补写进配置。
  → 因此"装一个新插件"不需要编辑任何配置，直接放进目录即可。

> **为什么目录里有 DLL 就默认启用**：把插件放进目录是一个明确的"我要用它"
> 的动作。默认不启用会让每个新用户都经历一次"我装好了但什么也没发生"。
> 而 `--safe-mode`（见 [06](../02-宿主设计.md)）提供了相反的入口：
> 出问题时用它启动，所有插件都不加载。

### 3.3 `[routing]` — 路由覆盖

```toml
[routing]
"notifier.console" = ["sm.host.*"]
"notifier.imgui"   = ["mail.*", "system"]
```

| 项 | 说明 |
|---|---|
| 键 | 插件 id |
| 值 | topic 模式数组 |
| 缺省 | 该 Notifier 用自己元信息里声明的订阅 |
| **空数组** `[]` | 该 Notifier **不再收到任何通知** |
| 非空数组 | **完全覆盖**（不是追加）该 Notifier 声明的订阅 |
| 模式语法 | 点分命名；`"mail.*"` 匹配 `mail` 的**下级**（`mail.inbox`、`mail.inbox.spam`），**不**匹配 `mail` 本身；**不支持正则** |

**本表只影响被列出的插件**，不改变其它 Notifier 的行为。

路由的完整语义（包括一条通知可以命中多个 Notifier、广播而非单播）见
[06](../02-宿主设计.md) 的"路由"一节。

> **为什么值是"覆盖"而不是"追加"**：追加会让人无法判断"这个插件到底订阅了
> 什么" —— 得同时看元信息和配置。覆盖之后，配置里出现即为最终答案，
> 这是排障时唯一好用的语义。

> **为什么需要路由覆盖而不是直接禁用插件**：它们是不同的动作。
> 一个归档 Notifier 在测试期间可能只想收 `sm.host.*`，但它仍然加载着、
> 仍然可以被别的东西引用（例如它注册的 Action 处理器）。用 `[]` 精确地
> 表达"不再收通知"，比"把整个插件关掉"更贴近实际意图。

### 3.4 `[notify_window]` — 通知表面摆在哪

```toml
[notify_window]
monitor = "primary"
position = "bottom_right"
```

| 项 | 允许的值 | 缺省 |
|---|---|---|
| `monitor` | `"primary"`，或某块显示器的**设备名**（形如 `\\.\DISPLAY2`） | `"primary"` |
| `position` | `"top_left"` / `"top_right"` / `"bottom_left"` / `"bottom_right"` | `"bottom_right"` |

- 位置按显示器的**工作区**算 —— 已经扣掉了任务栏以及其它停靠的 AppBar。贴右下角时窗口的右下边贴着工作区的右下边，不会被任务栏压住。
- 窗口与工作区边缘之间固定留 16 像素的缝。
- 窗口的**大小跟随浮层内容**：这两个键决定的是"钉住哪个角"，不是"多大"。浮层内容变化时窗口跟着变。
- **这两个键在控制面板上也能改**（"通知"页顶部的"通知表面"一节，见 [03-控制面板 §4.6](../03-控制面板.md)），改完立即生效并写回本节 —— 不必手工编辑文件再重启。面板上的显示器下拉列的是**当下枚举到的**所有显示器（带工作区坐标）加一项"主屏"；配置里的名字不在列表里时，会额外列出一项"（已断开）<名>"，让"为什么它回到主屏了"直接可见。
- **浮层内容的宽度区间不在这里**，而在插件的设置里（`notifier.imgui` 的 `toast_width_min` / `toast_width_max`，[04-示例插件.md](04-示例插件.md)）。表面尺寸仍由内容决定，本节的两个键只决定"钉在哪个角" —— 宽度是画在表面上的那个插件的事。
- 这是**独立于控制面板的第二扇窗口**（无边框、不抢焦点、不进任务栏/Alt+Tab）。没有浮层的
  内容连续 30 秒后它会自己休眠（隐藏、停止渲染），下一条通知到达时再醒来 —— 见
  [02-宿主设计 §11.6～§11.7](../02-宿主设计.md)。
- 名称写错（系统里没有这块显示器）**不报错**：改用主显示器并记一条 **Warn**，里面带着写错的那个名字。
- 本节的键都会写回文件；缺本节时会被补上，用户不必翻文档才知道有这回事。

> **写法提醒**：设备名里有反斜杠。用**单引号字面量**最省事 —— 双引号里的
> `\D` 是非法转义，TOML 解析器会直接拒绝整个文件：
>
> ```toml
> monitor = '\\.\DISPLAY2'
> ```

> **为什么是设备名而不是"第几块屏幕"**：编号会随插拔顺序与显示设置的变动而变，
> 而设备名是这块屏幕在系统里的身份。代价是它不好看，所以每次启动宿主都会把
> 当前所有显示器连同工作区写进日志：
>
> ```
> [...] 显示器 \\.\DISPLAY1（主） 2560x1440，工作区 2560x1400 于 (0,0)
> [...] 显示器 \\.\DISPLAY2 1920x1080，工作区 1920x1080 于 (2560,0)
> ```

## 4. `plugins/<插件id>.toml` 完整参考

```toml
# 文件名必须等于插件 id（不含扩展名）—— 这个文件是 plugins/notifier.console.toml
schema_version = 1

[settings]
min_level = "warning"
format = "oneline"
include_source = true
```

（每一项的具体含义由插件自己声明，见各自插件的设置表 ——
例如 [04-示例插件.md](04-示例插件.md) 列了四个随仓库发布的插件的全部设置项。）

### 4.1 结构

- `schema_version` — 与 `config.toml` 同一个版本号空间。
- `[settings]` — **所有设置项都在这一个表里**，不再嵌套。键即
  `SettingDef::name`。
- **文件里除了这两样不应有其他顶层键。**宿主对未知顶层键记 Warn 并忽略。

> **为什么设置项不分组**：插件的设置项上限是 64 个，一个扁平的
> `[settings]` 表在编辑器里完全可以阅读。引入分组意味着设置项 schema
> 要增加"组"的概念，`setting_*()` 的 `name` 也要变成路径 ——
> 复杂度涨了一档，收益只是"看起来整齐一点"。

### 4.2 缺省行为

| 情况 | 处理 |
|---|---|
| **文件不存在** | 按 schema 的默认值生成并写入（**首次运行即自动生成**） |
| 文件存在但缺 `[settings]` | 同上，补写 |
| 缺某个设置项 | 用 schema 的默认值，**立即补写进文件** |
| 多出未知的设置项 | 忽略并记 **Warn**（不删除，因为可能是插件降级后留下的） |
| 类型的值不匹配（如 int 位置写了 string） | 用 schema 默认值，记 Warn |
| 数值超出已声明的范围 | **夹到边界值**，记 Warn（例：`interval_sec = 2` → 10） |
| Enum 的值不在选项列表里 | 用默认值，记 Warn |
| String 超过 `max_string_bytes` | 截断，记 Warn |

**总结一句：插件设置文件里的任何错误都不会导致加载失败。**
它要么被纠正（夹取/回退/截断），要么被忽略。

> **为什么错误一律不回退到"拒绝加载"**：插件设置是用户手工编辑的，
> 里面有错是常态而不是意外。一个"因为我把 `interval_sec` 写成了 `0`
> 所以整个软件起不来"的行为，会让用户失去一个本可以正常工作的程序。

### 4.3 重置某个插件

删掉它的 `.toml` 文件即可 —— 下次启动会按 schema 的默认值重新生成。
控制面板的插件页也提供"重置为默认值"按钮（内部走同一个路径：
删除文件 + 重新生成）。

## 5. 解析失败与容错

### 5.1 `config.toml` 解析失败（语法错误 / 文件被截断 / 编码不是 UTF-8）

```
1. 把原文件重命名为 config.toml.corrupt-<时间戳>
2. 用全默认值生成新的 config.toml
3. 记一条 Error 日志，并把这件事作为【结构性事件】通知用户
4. 正常启动（不拒绝）
```

原文件**只重命名、不删除** —— 用户可能手工恢复了很久的设置，
而这个文件里可能还有能救回来的部分。

### 5.2 `config.toml` 部分合法（TOML 语法对，但某几个值非法）

不做整体回退，而是**逐项处理**：

| 情况 | 处理 |
|---|---|
| 类型不匹配、超范围、枚举值非法 | 用默认值，记 Warn |
| 未知的顶层键 / 未知的 `[app]` 键 | 忽略并记 Warn（**不删**） |
| `[plugins]` 里的值不是 bool | 用"启用"，记 Warn |
| `[routing]` 里的值不是字符串数组 | 忽略该项，记 Warn |

**原则：能读的项都读进来。**一个 `ui_font_size` 写错不该让其它 12 项设置
一起回到默认值。

### 5.3 插件配置解析失败

同 §5.1 的流程，但**只影响该插件**：备份 + 重新生成 + 记日志 + 该插件
按默认值运行。**绝不影响其它插件或宿主的启动。**

### 5.4 编码

**只接受 UTF-8**（允许有 BOM，读入时剥掉）。

- 带 UTF-8 BOM：剥掉 BOM 后正常解析。
- UTF-16 / GBK 等：解析必然失败 → 走 §5.1。
- 写出时**一律不带 BOM**。

> **为什么不接受 GBK**：TOML 规范本身要求 UTF-8，且一个"根据内容猜编码"的
> 读写器会在边界情况上做出难以预测的选择（比如一个短文件既像 GBK 又像
> UTF-8）。插件的设置值里可以有中文，那就用 UTF-8 —— 这是 2020 年代的
> 默认答案。

## 6. 写回机制

### 6.1 触发时机

| 事件 | 是否立即写回 |
|---|---|
| 用户在控制面板改动任一设置 | 否（进防抖队列） |
| 用户在控制面板启用/禁用插件 | 否（进防抖队列） |
| 插件被加载校验拒绝 | 否 |
| 插件因连续失败被自动禁用 | **是**（这是重要状态，立即持久化） |
| 宿主正常退出 | **是**（无条件 flush） |
| 宿主崩溃 / 被强杀 | 否（靠上一次写入的内容） |

### 6.2 防抖

```
改动 → 重置计时器 → 500ms 内无新改动 → 写回
```

理由：用户拖动一个滑块会在 1 秒内产生几十次 `int` 变化。
每次变化都写文件会让磁盘灯常亮，且在资源受限的设备上明显拖慢界面。

**上限**：即使持续有改动，**最多 2 秒**必须写一次。
（否则用户按住一个连发按钮不动，配置永远不会落盘。）

### 6.3 原子替换

```
1. 写 <文件>.tmp       （同目录，保证同文件系统）
2. flush + 关闭
3. 若 <文件> 存在：重命名为 <文件>.bak
4. 把 <文件>.tmp 重命名为 <文件>
```

**为什么必须"同目录 + 重命名"**：跨文件系统的重命名不是原子的（会退化成
拷贝+删除），而"写一半时断电"留下的半截文件正是我们要防的。
`<文件>.bak` **只保留一份**，每次写回时被覆盖。

### 6.4 注释会丢失

运行时写回是**整体重写**（用 toml++ 重新序列化），因此：

- 用户手工写的**注释在第一次写回后消失**。
- 键的顺序可能改变。

**这是刻意的取舍，且必须写进用户可见的文档里。**

> **为什么接受它**：保留注释需要引入一个"格式保留型" TOML 编辑器，
> 它会显著增加体积与复杂度和依赖，与"简洁、资源受限"的诉求直接冲突。
> 而配置被写回的频率并不高（只有用户主动改设置时）。
> 缓解办法是：**默认配置文件里不写注释**，让用户想加注释时自己加，
> 并明确告知他注释会在设置被改动后丢失。

### 6.5 写失败

磁盘满 / 权限不足 / 文件被占用：

- 记 Error 日志（含系统错误码与文本）。
- **重试**：退避 1s / 2s / 4s，最多 3 次。
- 仍失败：在控制面板的"概览"页显示一条醒目提示"配置未能保存"，
  并在宿主退出前再尝试一次。
- **绝不让写失败成为崩溃的原因** —— 配置保存不了是个问题，
  但因为保存不了而崩掉，是更大的问题。

## 7. 手工编辑速查

### 7.1 常见错误

| 症状 | 原因 | 修法 |
|---|---|---|
| 插件设置没生效 | 改错文件了 —— 插件设置在 `plugins/<id>.toml`，不是 `config.toml` | 确认路径（见 §1） |
| 改了设置但界面显示旧值 | 宿主正在运行，界面上是内存中的值 | 在界面上改（会立即生效并写回），或退出后改 |
| 启动报错退出 | `schema_version` 比宿主版本大 | 见 §2.2 |
| 某个插件"启动了但没反应" | `[plugins]` 里它是 `false` | 改成 `true`，或在控制面板里启用 |
| 装了新插件但没生效 | DLL 文件名与 `PluginMeta::id` 不一致 | 看日志，加载被拒绝时会写明 |
| 中文显示成乱码 | 文件不是 UTF-8 | 另存为 UTF-8（不带 BOM） |
| `[plugins]` 里的项报语法错 | id 没加引号 | `"source.email" = true` |

### 7.2 安全编辑流程

```
1. 退出宿主（或确认它在运行时会覆写你的改动）
2. 备份：copy config.toml config.toml.mine
3. 编辑
4. 启动宿主，看日志里有没有 Warn
```

**宿主运行时不要编辑配置文件。**内存中的值会在下一次写回时覆盖磁盘上的
内容 —— 用户会看到"我改的东西自己变回去了"。这是最容易让人困惑的行为，
因此 [07](../03-控制面板.md) 里规定控制面板的"关于"页必须显示配置文件路径，
让用户随时知道该改哪个文件。
