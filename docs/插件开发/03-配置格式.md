# 插件开发 03 — 配置格式

配置全部是 TOML。**只有四类文件**，边界划得很清楚：

| 文件 | 回答什么问题 | 谁写 |
|---|---|---|
| `config.toml` | 宿主自己的事：应用行为、插件实例（含启用状态）、规则启用状态、路由覆盖 | 用户手工编辑 + 宿主写回 |
| `config/rules.toml` | 通知规则：匹配、重写、丢弃 | **只有用户手工编辑**；宿主仅在文件缺失时生成默认模板 |
| `config/plugins/<实例id>.toml` | 某个**插件实例**的设置项 | 用户手工编辑 + 宿主写回 |
| 插件自己的状态文件（在 `data_dir`） | 插件的缓存、索引、运行状态 | 只有插件自己（宿主不碰，也不要求格式） |

> **为什么插件设置不放在 `config.toml` 里。** 因为这两类数据的生命周期不同：
> 插件 DLL 可能被删掉，而配置里还留着它的启用状态；反过来，插件设置应当能
> 跟着插件单独分发、备份、重置。混在一个文件里会同时破坏这两件事 ——
> 删插件时得记得清配置，备份插件时得从大文件里抠出属于它的那几行。

**本文的每条规则都是实现约束** —— 宿主按它实现，校验失败时的行为也由它规定。

## 1. 目录布局与路径解析

```
<配置目录>/
├── config.toml                    ← 宿主配置
├── config.toml.bak                ← 写回前自动备份（只保留一份）
├── rules.toml                     ← 通知规则（宿主不写回）
└── plugins/
    ├── source.email.toml          ← 插件设置，文件名 = 实例 id
    ├── source.email.toml.bak
    ├── source.email@2.toml        ← 同一插件的第二个实例
    └── notifier.imgui.toml

<数据目录>/
├── logs/
│   └── simplemessage-YYYY-MM-DD.log
└── <插件id>/                      ← 插件自己的状态文件，宿主不解析
                                    （多实例插件应自行按 own_config_path() 区分）
```

### 1.1 配置目录的确定顺序

```
1. 命令行 --config-dir <路径>          ← 最高优先级
2. <exe 所在目录>/config/              ← 若能创建且可写
3. %APPDATA%\SimpleMessage\config\     ← 回退（Windows）
   ~/.config/simplemessage/            ← 回退（POSIX）
```

**目录不存在时自动创建。**如果第 2 项因为"安装在 `C:\Program Files` 下"
而不可写，就安静地回退到第 3 项，并在日志里记一条 Info 说明实际用的路径。

> **为什么"exe 目录优先"而不是反过来**：这是一个绿色软件风格的工具，
> 用户把它解压到 U 盘里跑、或者放在一个便携目录里，期望配置就在旁边。
> 但安装在受保护目录时又不能失败，所以保留回退。**实际用的路径必须
> 写进日志** —— 否则用户会对着"我改了配置怎么没生效"发呆，
> 而真相是他改的是另一个 `config.toml`。

### 1.2 数据目录的确定顺序

```
1. 命令行 --data-dir <路径>
2. <配置目录的父目录>/data/            ← 通常是 exe 目录旁
3. %APPDATA%\SimpleMessage\data\
```

**必须与配置目录区分开。**配置目录的内容会被用户手工编辑、被"重置配置"
逻辑处理、被备份；数据目录不会。插件的缓存、索引、上次运行状态应当放数据
目录（`IHostContext::data_dir()`），否则用户在重置配置时会莫名其妙丢掉它们。

### 1.3 插件目录

```
1. 命令行 --plugin-dir <路径>
2. <exe 所在目录>/plugins/
```

见 [06](../02-宿主设计.md) 的插件扫描与加载流程。

## 2. `schema_version` 与迁移

**每个配置文件的第一行都是 `schema_version`。**

```toml
schema_version = 2
```

`config.toml` 与 `plugins/<实例id>.toml` 使用**两个独立的版本号空间**：
前者当前是 **2**（v1 的 `[plugins]` 迁移为 `[[instances]]`），后者当前是 **1**。
两者共用同一个常量会让升级 `config.toml` 时把每个既有插件设置文件都误判成旧版本。

### 2.1 三种情形

| 文件里的版本 | 宿主动作 |
|---|---|
| **等于**当前版本 | 正常读取 |
| **小于**当前版本 | 走**迁移链**（见 §2.3），成功后按新版本写回 |
| **大于**当前版本 | **拒绝启动**，日志与控制面板给出明确提示 |

> **为什么"更高版本"要拒绝，而"损坏"却不拒绝**（§5）。
> 这两件事的性质完全不同：
> - **更高版本**意味着用户刚用新版宿主跑过，配置里有旧版宿主**不认识的
>   语义**（比如某个键的含义被改掉了）。旧版宿主若照读，可能把用户的
>   设置静默改错 —— 而且它会用旧格式写回去，把新版的数据毁掉。
>   这是**数据损坏**，必须停下。
> - **损坏**（语法错、截断、乱码）不携带任何语义，用户不会因为"从默认值
>   开始"而损失什么有价值的东西。此时能启动比停下来更有用。
>
> 一条通用的判据：**能启动就启动，除非启动会破坏用户的既有数据。**

### 2.2 拒绝启动时的行为

- 日志记 Error，含期望版本、实际版本、文件路径。
- 以 `--console` 方式启动时，在控制台打印同样的信息。
- **不修改配置文件、不生成备份、不写回。**
- 退出码非零（见 [06](../02-宿主设计.md) 的退出码约定）。
- 提示用户：升级宿主，或删除该文件（会丢失该文件里的设置）。

### 2.3 迁移链

```
v1 ──→ v2 ──→ v3
```

**每次只走一步**，每一步是一个独立函数 `migrate_1_to_2(const toml::table&)`。
不支持直接 v1 → v3 的跳跃迁移 —— 那会让迁移逻辑变成 n² 条路径。

**`config.toml` 与插件设置文件各有一条链**（§2 的两个版本号空间）：
`config.toml` 当前的 `1 → 2` 把 `[plugins]` 变成 `[[instances]]`（§3.2）；
插件设置文件当前还停在 1，没有迁移步骤。

- 迁移**在内存中**完成：读原始 TOML → 逐级转换 → 得到当前版本的表。
- 迁移**成功后**才写回（并备份）。
- **迁移过程中的任何一步失败**（例如 v2 需要 v1 里的某个字段而它不存在）
  → 退回"按默认值 + 保留能读的项"处理，并记一条 Warn。
  **不拒绝启动** —— 迁移失败是宿主自己的 bug，不该让用户承担。
- 迁移函数必须**只增不改**：一旦 v1→v2 发布，`migrate_1_to_2` 的行为
  就固定了。改它等于让"用旧版宿主导出过 v2 配置的用户"走进另一条路径。

> **为什么迁移要做成链而不是"一次性转换"**：用户可能从 v1 直接升到 v5。
> 链式迁移让每一段的测试只需要覆盖"相邻两个版本"，而 n 个版本只需要
> n-1 个测试。这也让"哪一步改了什么"在代码里一眼可见。

## 3. `config.toml` 完整参考

### 3.1 `[app]` — 应用行为

| 键 | 类型 | 默认 | 取值范围 | 说明 |
|---|---|---|---|---|
| `notify_log_level` | string | `"error"` | `off` / `error` / `warn` / `info` | 由日志转成通知的最低级别 |
| `log_level` | string | `"info"` | `trace` / `debug` / `info` / `warn` / `error` | 写入日志文件的最低级别 |
| `log_retention_days` | integer | `7` | `1` – `365` | 日志保留天数 |
| `log_max_total_mb` | integer | `32` | `1` – `1024` | 日志总大小上限（MB） |
| `ui_font_size` | integer | `16` | `10` – `32` | imgui 字号（像素） |
| `single_instance` | boolean | `true` | — | 单实例保护 |
| `notification_history_size` | integer | `200` | `1` – `200` | 内存历史条数上限 |
| `allow_rule_save` | boolean | `false` | — | 允许 `rules.toml` 中启用 `save` 的规则把通知写入文件 |

#### `notify_log_level` 的细节

- 设成 `off` **只关闭"普通日志 → 通知"这条通道**。
- **结构性事件不受本项控制**：插件崩溃 / 被禁用、配置损坏、
  宿主启停、插件加载被拒绝 —— 这些**始终**产生通知。
- 由日志产生的通知有防刷限制：topic 为 `sm.host.log` 的通知被限制在
  **10 秒内最多 5 条**，超出的被合并计数。

> **为什么结构性事件不受阈值控制**：把"插件崩了却没告诉你"和"日志太吵"
> 当成同一件事，是本可以避免的两类失败。用户调低通知阈值时想要的是
> "别拿日常消息烦我"，而不是"别告诉我东西坏了"。**这两件事必须能被
> 分别配置**，而"结构性事件永远通知"是最简单的实现方式。

> **为什么 `sm.host.log` 要限速**：一个每 200ms 轮询失败一次的插件，
> 会在 10 秒内产生 50 条 Error 日志。没有限速的话，用户会被 50 条通知
> 淹没，而且每一条的内容都一样。合并成"6 条类似错误（已合并 45 条）"
> 传递的是同样的信息，且不会把界面变成一个无法阅读的列表。

#### `log_level` 与通知的关系

通知**不按 `info` 级写日志**，只进 `trace` / `debug`。
因为一条通知的旅程会涉及多个组件，按 `info` 写会让日志被高频通知淹没。

**默认的 `log_level = "info"` 意味着"默认情况下看不到通知的详细日志"。**
需要排查通知管线问题时，临时改成 `debug`。

#### `notification_history_size` 与 SDK 硬上限

`sm::limits::kNotificationHistoryCapacity`（200）是**硬上限**，
本项是**用户可调的实际值**：

```
实际历史条数 = min(notification_history_size, kNotificationHistoryCapacity)
```

配置超限时夹到 200 并记 Warn。**不能让配置突破 SDK 上限** ——
插件是基于上限写的（例如"最多显示 200 条"的缓冲区）。

#### `ui_font_size` 的范围为什么是 10–32

- 小于 10：中文笔画粘连，不可读。
- 大于 32：字号越大，imgui 的字体图集越大。为了一个"更大"的偏好而
  在资源受限的机器上占掉几 MB 显存不划算 —— 需要更大字号的用户
  应当改系统的 DPI 缩放。

#### `allow_rule_save` — 规则保存的总开关

规则文件里的 `save` 只是"这条规则想保存"，真正落盘还需要本项为 `true`。
默认**关闭**，可以在控制面板的"通知"页勾选"允许规则保存通知内容"，效果
与手改本项相同（改动会写回 `config.toml`）。

- 开关是全局的：打开后**无视通知来源**，任何匹配且启用了 `save` 的规则都会写文件。
- 关闭时完全不写文件；安全模式也会强制关闭（安全模式承诺不落盘）。
- 修改后无需重启，下一次命中的通知即按新状态处理。
- 规则保存的配置、占位符与文件格式见 [§9.9](#99-规则保存与占位符)。

### 3.2 `[[instances]]` — 插件实例与启用状态

```toml
[[instances]]
id = "source.email"
plugin = "source.email"
name = ""
enabled = true

[[instances]]
id = "source.email@2"
plugin = "source.email"
name = "工作邮箱"
enabled = true

[[instances]]
id = "notifier.imgui"
plugin = "notifier.imgui"
name = ""
enabled = true
```

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `id` | string | 必填 | 实例 id，由宿主生成；**不可手工改名** |
| `plugin` | string | 必填 | 插件类型 id（`PluginMeta::id`），也就是 DLL 文件名 |
| `name` | string | `""` | 界面显示名；空表示自动命名 |
| `enabled` | boolean | `true` | 该实例是否加载 |

**插件类型与插件实例是两层东西。**一个 DLL（类型）可以被加载并校验一次，
然后创建多个互相隔离的运行实例：各自一个 `sm_create_plugin` 对象、一份设置
文件、一个调度槽位、一份日志来源与统计。

#### 实例 id 的规则

- 首个实例沿用类型 id：`source.email`。
- 之后是 `类型id@2`、`类型id@3`……（`N` 为 2–16，无前导零）。
- `@` 保留给宿主，类型 id 自身不允许出现。
- 总长 ≤ 80 字节；类型 id 只允许 `a-z 0-9 _ . -`，且不得使用保留前缀 `sm.`。
- **删除后序号可以复用**，但实例存活期间 id 不变。历史与去重键是
  `(实例 id, 通知 id)`，因此复用 id 会被视为同一个来源。

#### 多实例只开放给 Source

- `PluginKind::Source` 的类型可以在控制面板里自由添加/删除实例。
- **Notifier 每种类型仍然只有一个实例**，id 必须等于类型 id。手写的
  `notifier.console@2` 会在启动时被标记为“拒绝加载”，不加载、也不写入
  设置文件；要恢复请从本文件删掉那一行。
- 每个类型最多 **16** 个实例，全局最多 **64** 个。控制面板的“添加实例”
  严格拒绝越界；手写配置超限时**仍按原样加载**并记 Warn（用户可能只是想要
  一个临时配置，宿主不替他删数据）。

#### 自动补实例与 `[removed_types]`

扫描到目录里的 DLL 后，宿主会为**已通过校验、但一个实例都没有、且没有墓碑**
的类型自动补一条 canonical 实例（`id = 类型 id`），并写回本文件。
因此“装一个新插件”不需要编辑任何配置。

反过来，删除某个类型的**最后一个实例**时，宿主写入墓碑：

```toml
[removed_types]
"source.webhook" = true
```

有墓碑时不会自动补实例；再次添加该类型的实例时墓碑会被清除。
没有墓碑的话，用户删掉插件后下次启动它就会被自动复活。

- **本文件不是“已安装插件列表”。**插件列表**永远**由扫描插件目录得到。
- 引用未安装类型、或类型校验失败的实例：跳过并记 Warn，**保留配置行**，
  等 DLL 装回来。
- 未知顶层键、未知实例键：忽略并记 Warn（写回时丢弃未知实例键）。

> **为什么目录里有 DLL 就默认启用**：把插件放进目录是一个明确的“我要用它”
> 的动作。默认不启用会让每个新用户都经历一次“我装好了但什么也没发生”。
> 而 `--safe-mode`（见 [06](../02-宿主设计.md)）提供了相反的入口：
> 出问题时用它启动，所有插件都不加载。

#### v1 → v2 迁移

旧版 `[plugins]` 表会逐项转成 `[[instances]]`：

```toml
# v1
[plugins]
"source.email" = true
"notifier.console" = false
```

变成

```toml
# v2
[[instances]]
id = "source.email"
plugin = "source.email"
name = ""
enabled = true

[[instances]]
id = "notifier.console"
plugin = "notifier.console"
name = ""
enabled = false
```

键名里的点号在 TOML 里**必须加引号**，否则 `source.email = true` 会被解析成
“`source` 表里的 `email` 键”——迁移会看到一个非布尔值，按启用处理并记 Warn。
既有 `plugins/<id>.toml` 设置文件不受迁移影响（它们用独立的版本号空间）。

### 3.3 `[routing]` — 路由覆盖

```toml
[routing]
"notifier.console" = ["sm.host.*"]
"notifier.imgui"   = ["mail.*", "system"]
```

| 项 | 说明 |
|---|---|
| 键 | 插件 id |
| 值 | topic 模式数组 |
| 缺省 | 该 Notifier 用自己元信息里声明的订阅 |
| **空数组** `[]` | 该 Notifier **不再收到任何通知** |
| 非空数组 | **完全覆盖**（不是追加）该 Notifier 声明的订阅 |
| 模式语法 | 点分命名；`"mail.*"` 匹配 `mail` 的**下级**（`mail.inbox`、`mail.inbox.spam`），**不**匹配 `mail` 本身；**不支持正则** |

**本表只影响被列出的插件**，不改变其它 Notifier 的行为。

路由的完整语义（包括一条通知可以命中多个 Notifier、广播而非单播）见
[06](../02-宿主设计.md) 的"路由"一节。

> **为什么值是"覆盖"而不是"追加"**：追加会让人无法判断"这个插件到底订阅了
> 什么" —— 得同时看元信息和配置。覆盖之后，配置里出现即为最终答案，
> 这是排障时唯一好用的语义。

> **为什么需要路由覆盖而不是直接禁用插件**：它们是不同的动作。
> 一个归档 Notifier 在测试期间可能只想收 `sm.host.*`，但它仍然加载着、
> 仍然可以被别的东西引用（例如它注册的 Action 处理器）。用 `[]` 精确地
> 表达"不再收通知"，比"把整个插件关掉"更贴近实际意图。

### 3.4 `[notify_window]` — 通知表面摆在哪

```toml
[notify_window]
monitor = "primary"
position = "bottom_right"
```

| 项 | 允许的值 | 缺省 |
|---|---|---|
| `monitor` | `"primary"`，或某块显示器的**设备名**（形如 `\\.\DISPLAY2`） | `"primary"` |
| `position` | `"top_left"` / `"top_right"` / `"bottom_left"` / `"bottom_right"` | `"bottom_right"` |

- 位置按显示器的**工作区**算 —— 已经扣掉了任务栏以及其它停靠的 AppBar。贴右下角时窗口的右下边贴着工作区的右下边，不会被任务栏压住。
- 窗口与工作区边缘之间固定留 16 像素的缝。
- 窗口的**大小跟随浮层内容**：这两个键决定的是"钉住哪个角"，不是"多大"。浮层内容变化时窗口跟着变。
- **这两个键在控制面板上也能改**（"通知"页顶部的"通知表面"一节，见 [03-控制面板 §4.6](../03-控制面板.md)），改完立即生效并写回本节 —— 不必手工编辑文件再重启。面板上的显示器下拉列的是**当下枚举到的**所有显示器（带工作区坐标）加一项"主屏"；配置里的名字不在列表里时，会额外列出一项"（已断开）<名>"，让"为什么它回到主屏了"直接可见。
- **浮层内容的宽度区间不在这里**，而在插件的设置里（`notifier.imgui` 的 `toast_width_min` / `toast_width_max`，[04-示例插件.md](04-示例插件.md)）。表面尺寸仍由内容决定，本节的两个键只决定"钉在哪个角" —— 宽度是画在表面上的那个插件的事。
- 这是**独立于控制面板的第二扇窗口**（无边框、不抢焦点、不进任务栏/Alt+Tab）。没有浮层的
  内容连续 30 秒后它会自己休眠（隐藏、停止渲染），下一条通知到达时再醒来 —— 见
  [02-宿主设计 §11.6～§11.7](../02-宿主设计.md)。
- 名称写错（系统里没有这块显示器）**不报错**：改用主显示器并记一条 **Warn**，里面带着写错的那个名字。
- 本节的键都会写回文件；缺本节时会被补上，用户不必翻文档才知道有这回事。

> **写法提醒**：设备名里有反斜杠。用**单引号字面量**最省事 —— 双引号里的
> `\D` 是非法转义，TOML 解析器会直接拒绝整个文件：
>
> ```toml
> monitor = '\\.\DISPLAY2'
> ```

> **为什么是设备名而不是"第几块屏幕"**：编号会随插拔顺序与显示设置的变动而变，
> 而设备名是这块屏幕在系统里的身份。代价是它不好看，所以每次启动宿主都会把
> 当前所有显示器连同工作区写进日志：
>
> ```
> [...] 显示器 \\.\DISPLAY1（主） 2560x1440，工作区 2560x1400 于 (0,0)
> [...] 显示器 \\.\DISPLAY2 1920x1080，工作区 1920x1080 于 (2560,0)
> ```

### 3.5 `[rules]` — 规则启用状态

```toml
[rules]
"auto_summary" = true
"drop-verbose" = false
```

- **键是 `rules.toml` 里某条规则的 `id`，值是是否启用。**
- 表里没有的 id **默认启用**；因此新加一条规则不需要先改 `config.toml`。
- 这一节由控制面板的“规则”页写回（防抖写盘），也是规则启用状态的唯一位置
  —— `rules.toml` 本身只描述规则内容，不记录开关。
- 表里存在但 `rules.toml` 里没有的 id：忽略（用户可能只是暂时删了那条规则）。

### 3.6 规则文件 `rules.toml`

完整的字段、表达式语法与两趟语义见本文 **§9**。

## 4. `plugins/<实例id>.toml` 完整参考

```toml
# 文件名必须等于实例 id（不含扩展名）—— 这个文件是 plugins/notifier.console.toml
# 第二个 source.email 实例则是 plugins/source.email@2.toml
schema_version = 1

[settings]
min_level = "warning"
format = "oneline"
include_source = true
```

（每一项的具体含义由插件自己声明，见各自插件的设置表 ——
例如 [04-示例插件.md](04-示例插件.md) 列了六个随仓库发布的插件的全部设置项。）

### 4.1 结构

- 文件名 = **实例 id**，不是插件类型 id。一个类型的多个实例各有自己的文件，
  这样可以给两个邮箱配不同的收件参数，而它们共用同一个 DLL。
- `schema_version` — **独立于 `config.toml` 的版本号空间**，当前为 **1**。
  两个文件升级节奏不同：把 `config.toml` 升到 2（`[[instances]]`）时，
  所有既有的 `plugins/*.toml` 仍然是合法的 1，不会被迁移。
- `[settings]` — **所有设置项都在这一个表里**，不再嵌套。键即
  `SettingDef::name`。
- **文件里除了这两样不应有其他顶层键。**宿主对未知顶层键记 Warn 并忽略。

> **为什么设置项不分组**：插件的设置项上限是 64 个，一个扁平的
> `[settings]` 表在编辑器里完全可以阅读。引入分组意味着设置项 schema
> 要增加"组"的概念，`setting_*()` 的 `name` 也要变成路径 ——
> 复杂度涨了一档，收益只是"看起来整齐一点"。

### 4.2 缺省行为

| 情况 | 处理 |
|---|---|
| **文件不存在** | 按 schema 的默认值生成并写入（**首次运行即自动生成**） |
| 文件存在但缺 `[settings]` | 同上，补写 |
| 缺某个设置项 | 用 schema 的默认值，**立即补写进文件** |
| 多出未知的设置项 | 忽略并记 **Warn**（不删除，因为可能是插件降级后留下的） |
| 类型的值不匹配（如 int 位置写了 string） | 用 schema 默认值，记 Warn |
| 数值超出已声明的范围 | **夹到边界值**，记 Warn（例：`interval_sec = 2` → 10） |
| Enum 的值不在选项列表里 | 用默认值，记 Warn |
| String / Sound 超过 `max_string_bytes` | 截断，记 Warn |

**总结一句：插件设置文件里的任何错误都不会导致加载失败。**
它要么被纠正（夹取/回退/截断），要么被忽略。

> **为什么错误一律不回退到"拒绝加载"**：插件设置是用户手工编辑的，
> 里面有错是常态而不是意外。一个"因为我把 `interval_sec` 写成了 `0`
> 所以整个软件起不来"的行为，会让用户失去一个本可以正常工作的程序。

### 4.3 重置某个实例

删掉它的 `.toml` 文件即可 —— 下次启动会按 schema 的默认值重新生成。
控制面板的插件页也提供"重置为默认值"按钮（内部走同一个路径：
删除文件 + 重新生成）。

注意这**只影响该实例**：`source.email@2` 被重置时，`source.email` 的设置
原封不动。要连实例一起移除，用"删除实例"（会同时删掉这个文件）。

## 5. 解析失败与容错

### 5.1 `config.toml` 解析失败（语法错误 / 文件被截断 / 编码不是 UTF-8）

```
1. 把原文件重命名为 config.toml.corrupt-<时间戳>
2. 用全默认值生成新的 config.toml
3. 记一条 Error 日志，并把这件事作为【结构性事件】通知用户
4. 正常启动（不拒绝）
```

原文件**只重命名、不删除** —— 用户可能手工恢复了很久的设置，
而这个文件里可能还有能救回来的部分。

### 5.2 `config.toml` 部分合法（TOML 语法对，但某几个值非法）

不做整体回退，而是**逐项处理**：

| 情况 | 处理 |
|---|---|
| 类型不匹配、超范围、枚举值非法 | 用默认值，记 Warn |
| 未知的顶层键 / 未知的 `[app]` 键 | 忽略并记 Warn（**不删**） |
| `[[instances]]` 缺 `id`（或 `id` 不是字符串）、id 非法、id 重复 | 跳过该条，记 Warn（写回时丢弃） |
| `[[instances]]` 缺 `plugin` | 按 id 的类型部分补上，记 Warn |
| `[[instances]]` 的 `plugin` 不是字符串或不是合法类型 id | 跳过该条，记 Warn |
| `[[instances]]` 的 `plugin` 与 id 的类型部分不一致 | 跳过该条，记 Warn |
| `instances` 不是数组 | 忽略整节（实例列表为空），记 Warn |
| `[[instances]]` 的 `name` 不是字符串 / 超长 | 按自动命名 / 截断到 96 字节，记 Warn |
| `[[instances]]` 的 `enabled` 不是 bool | 视为 `true`，记 Warn |
| 非 canonical 的 Notifier 实例（`notifier.x@2`） | 保留配置行但标记为拒绝加载，记 Warn |
| `[removed_types]` 里的值不是 bool | **按未删除处理**（不写墓碑），记 Warn |
| `[rules]` 里的值不是 bool | 用"启用"，记 Warn |
| `[routing]` 里的值不是字符串数组 | 忽略该项，记 Warn |

**原则：能读的项都读进来。**一个 `ui_font_size` 写错不该让其它 12 项设置
一起回到默认值。

### 5.3 插件配置解析失败

同 §5.1 的流程，但**只影响该插件**：备份 + 重新生成 + 记日志 + 该插件
按默认值运行。**绝不影响其它插件或宿主的启动。**

### 5.4 编码

**只接受 UTF-8**（允许有 BOM，读入时剥掉）。

- 带 UTF-8 BOM：剥掉 BOM 后正常解析。
- UTF-16 / GBK 等：解析必然失败 → 走 §5.1。
- 写出时**一律不带 BOM**。

> **为什么不接受 GBK**：TOML 规范本身要求 UTF-8，且一个"根据内容猜编码"的
> 读写器会在边界情况上做出难以预测的选择（比如一个短文件既像 GBK 又像
> UTF-8）。插件的设置值里可以有中文，那就用 UTF-8 —— 这是 2020 年代的
> 默认答案。

## 6. 写回机制

### 6.1 触发时机

| 事件 | 是否立即写回 |
|---|---|
| 用户在控制面板改动任一设置 | 否（进防抖队列） |
| 用户在控制面板启用/禁用实例 | 否（进防抖队列） |
| 用户在控制面板**添加/删除实例** | **是**（立即 flush。删除要先落盘再删设置文件） |
| 插件被加载校验拒绝 | 否 |
| 插件因连续失败被自动禁用 | **是**（这是重要状态，立即持久化） |
| 宿主正常退出 | **是**（无条件 flush） |
| 宿主崩溃 / 被强杀 | 否（靠上一次写入的内容） |

### 6.2 防抖

```
改动 → 重置计时器 → 500ms 内无新改动 → 写回
```

理由：用户拖动一个滑块会在 1 秒内产生几十次 `int` 变化。
每次变化都写文件会让磁盘灯常亮，且在资源受限的设备上明显拖慢界面。

**上限**：即使持续有改动，**最多 2 秒**必须写一次。
（否则用户按住一个连发按钮不动，配置永远不会落盘。）

### 6.3 原子替换

```
1. 写 <文件>.tmp       （同目录，保证同文件系统）
2. flush + 关闭
3. 若 <文件> 存在：重命名为 <文件>.bak
4. 把 <文件>.tmp 重命名为 <文件>
```

**为什么必须"同目录 + 重命名"**：跨文件系统的重命名不是原子的（会退化成
拷贝+删除），而"写一半时断电"留下的半截文件正是我们要防的。
`<文件>.bak` **只保留一份**，每次写回时被覆盖。

### 6.4 注释会丢失

运行时写回是**整体重写**（用 toml++ 重新序列化），因此：

- 用户手工写的**注释在第一次写回后消失**。
- 键的顺序可能改变。

**这是刻意的取舍，且必须写进用户可见的文档里。**

> **为什么接受它**：保留注释需要引入一个"格式保留型" TOML 编辑器，
> 它会显著增加体积与复杂度和依赖，与"简洁、资源受限"的诉求直接冲突。
> 而配置被写回的频率并不高（只有用户主动改设置时）。
> 缓解办法是：**默认配置文件里不写注释**，让用户想加注释时自己加，
> 并明确告知他注释会在设置被改动后丢失。

### 6.5 写失败

磁盘满 / 权限不足 / 文件被占用：

- 记 Error 日志（含系统错误码与文本）。
- **重试**：退避 1s / 2s / 4s，最多 3 次。
- 仍失败：在控制面板的"概览"页显示一条醒目提示"配置未能保存"，
  并在宿主退出前再尝试一次。
- **绝不让写失败成为崩溃的原因** —— 配置保存不了是个问题，
  但因为保存不了而崩掉，是更大的问题。

## 7. 手工编辑速查

### 7.1 常见错误

| 症状 | 原因 | 修法 |
|---|---|---|
| 插件设置没生效 | 改错文件了 —— 插件设置在 `plugins/<实例id>.toml`，不是 `config.toml` | 确认路径（见 §1）；注意 `@2` 实例是另一个文件 |
| 改了设置但界面显示旧值 | 宿主正在运行，界面上是内存中的值 | 在界面上改（会立即生效并写回），或退出后改 |
| 启动报错退出 | `schema_version` 比宿主版本大 | 见 §2.2 |
| 某个插件"启动了但没反应" | 该实例在 `[[instances]]` 里是 `enabled = false` | 改成 `true`，或在控制面板里启用 |
| 删掉的实例又回来了 | 删的是 `@2`，类型还有别的实例；或手工删配置行没写 `[removed_types]` | 在控制面板里删；手工删时给该类型写墓碑（§3.2） |
| 加了 `notifier.x@2` 但没加载 | Notifier 只允许一个实例 | 从 `[[instances]]` 删掉该行（§3.2） |
| 两个 Webhook 只有一个在线 | 两个实例绑了同一个端口 | 给每个实例在 `plugins/source.webhook*.toml` 里设不同 `port` |
| 装了新插件但没生效 | DLL 文件名与 `PluginMeta::id` 不一致 | 看日志，加载被拒绝时会写明 |
| 中文显示成乱码 | 文件不是 UTF-8 | 另存为 UTF-8（不带 BOM） |
| `[[instances]]` 报语法错 | 手写时把 `[[instances]]` 写成了 `[instances]` | 数组表必须用双括号；`id`/`plugin` 是字符串要加引号 |

### 7.2 安全编辑流程

```
1. 退出宿主（或确认它在运行时会覆写你的改动）
2. 备份：copy config.toml config.toml.mine
3. 编辑
4. 启动宿主，看日志里有没有 Warn
```

**宿主运行时不要编辑配置文件。**内存中的值会在下一次写回时覆盖磁盘上的
内容 —— 用户会看到"我改的东西自己变回去了"。这是最容易让人困惑的行为，
因此 [07](../03-控制面板.md) 里规定控制面板的"关于"页必须显示配置文件路径，
让用户随时知道该改哪个文件。

## 9. `rules.toml` 完整参考

规则层夹在**通知源**与**通知浮层**之间。它在通知进入历史之前（来源趟）
和每条通知交给某个 Notifier 之前（投递趟）各跑一遍，可以匹配、重写、丢弃。

> **规则内容只在文件里编辑。** 控制面板的“规则”页只允许切换启用状态与
> 重新加载；启用状态写回 `config.toml` 的 `[rules]`（§3.5），宿主**不会**
> 重写 `rules.toml`。

### 9.1 文件结构

```toml
schema_version = 1

[[rules]]
id = "auto_summary"
name = "自动简介"
type = "auto_summary"
from = "content"
max_codepoints = 20
only_if_empty = true

[[rules]]
id = "github-issue"
name = "GitHub issue 标题"
match = 'title =~ "^\[(\w+)\] (.+)$" and topic =~ "^github\."'
case_insensitive = true
[rules.rewrite]
title = "[$title.1] $title.2"
level = "warning"

[[rules]]
id = "drop-healthcheck"
name = "丢弃健康检查"
drop = true
match = 'title =~ "healthcheck"'
[rules.target]
source = ['^source\.webhook$']

[[rules]]
id = "toast-tag"
name = "只在浮层上改标签"
match = 'content =~ "\[(\w+)\]"'
[rules.target]
notifier = ['^notifier\.imgui$']
[rules.rewrite]
content = "标签：$content.1"

[[rules]]
id = "mail-archive"
name = "归档邮件"
match = 'title =~ "^(.*)$" and topic =~ "^mail\."'
[rules.rewrite]
title = "[归档] $title.1"
[rules.save]
enabled = true
path = "notify/{year}/{month}/{ruleid}-{title}.txt"
```

- 顶层只认 `schema_version` 与 `rules`；未知顶层键记 Warn 后忽略。
- `schema_version` 缺失按 1 处理；**大于 1** 时整份文件拒绝加载（规则集为空）。
- `rules` 必须是 `[[rules]]` 数组；最多 **256** 条。超出的条目忽略并记 Warn。
- 每条规则至少要有 `id`（1–64 字节、文件内唯一）。重复 id 的后一条会被跳过。

### 9.2 规则字段

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `id` | string | 必填 | 稳定标识；`config.toml [rules]` 用它 |
| `name` | string | 同 `id` | 规则页显示的名字 |
| `type` | string | `"match"` | `"match"` 或 `"auto_summary"` |
| `target.source` | string 数组 | 空 = 不限 | 来源**实例 id** 的**整串**正则；写类型 id 命中该类型全部实例 |
| `target.notifier` | string 数组 | 空 | Notifier 实例 id 的**整串**正则；非空即投递趟 |
| `match` | string | 空 = 恒真 | 匹配表达式，见 §9.3 |
| `case_insensitive` | bool | `false` | 只作用于 `match` 里的正则，不影响 `target` |
| `rewrite` | table | 无 | `title` / `content` / `summary` / `level` / `importance` / `time` |
| `drop` | bool | `false` | 丢弃并终止当前趟 |
| `handle` | bool | `false` | 本趟后续规则不再执行（匹配后才生效） |
| `save` | table | 无 | 命中后把通知追加写入文件，见 §9.9；只对 `match` 生效 |
| `from` | string | `"content"` | 仅 `auto_summary`；目前只接受 `"content"` |
| `max_codepoints` | int | `20` | 仅 `auto_summary`；上限由规则决定，不夹到 SDK 默认值；小于 1 夹到 1 并记 Warn |
| `only_if_empty` | bool | `true` | 仅 `auto_summary`；summary 非空时不动 |

`target` 省略等价于“全局来源趟”：

```toml
[[rules]]
id = "all-sources"
[rules.rewrite]
level = "warning"
```

- `target.source` 匹配的是**产生这条通知的实例 id**（`source_plugin`），
  也就是 `source.email` 或 `source.email@2`。
- **写类型 id 命中该类型的全部实例。**匹配顺序是：先用完整实例 id 试一遍，
  没命中且实例带 `@N` 时再用去掉 `@N` 的类型 id 试一遍。因此

  | 规则里的模式 | 命中 `source.email` | 命中 `source.email@2` | 命中 `source.emailx` |
  |---|---|---|---|
  | `'^source\.email$'` | 是 | 是 | 否 |
  | `'^source\.email@2$'` | 否 | 是 | 否 |
  | `'^source\.email'` | 是 | 是 | 否 |

  正则仍是**整串**匹配（`regex_match`），回退只发生在“整串不中”时；
  `^`/`$` 的写法不受影响。
- `target.notifier` **不做这个回退**：Notifier 每种类型只有一个实例，
  id 恒等于类型 id，按完整 id 精确匹配即可。
- 只要写了 `target.notifier`，这条规则就变成**投递趟**：它在来源趟不执行，
  而是在每条通知交给每个命中的 Notifier 之前分别执行。
- `auto_summary` 必须有来源趟语义，因此**不允许**写 `notifier` 目标。
- 对 `match` 规则，`drop = true` 与 `rewrite` 同时出现视为配置错误，整条规则跳过。

### 9.3 匹配表达式

```
expr    := or
or      := and ( "or" and )*
and     := not ( "and" not )*
not     := "not" not | primary
primary := "(" or ")" | compare
compare := field ( "=~" | "!~" ) string
field   := "title" | "content" | "summary" | "topic"
```

- `and` 比 `or` 结合得紧；`not` 优先于两者。
- **`=~` 是子串搜索（`regex_search`），不是整串匹配。** 要整串匹配就自己写
  `^...$`。`!~` 是它的否定。
- 正则在表达式里用**双引号**包住，语法为 ECMAScript（与 `source.webhook`
  的 topic 正则同一个引擎）。
- 推荐把整个 `match` 写成 TOML **单引号字面量**，这样反斜杠不用转义：

  ```toml
  match = 'title =~ "^\d+$"'
  ```

  表达式解析器只解释正则字符串里的 `\"` 与 `\`，其余反斜杠原样交给正则引擎。
- **同一个字段在一条规则里最多出现一次正向 `=~`**。这是为了让
  `$field.N` 的组号没有歧义；`!~` 不提供捕获组。
- `match` 为空（或整条省略）表示恒真，适合“只按 target 过滤/重写”。

### 9.4 重写模板

`rewrite.title` / `rewrite.content` / `rewrite.summary` 是字符串模板：

| 写法 | 含义 |
|---|---|
| `$field.N` | 该字段正向 `=~` 的第 N 个捕获组；N 为 0–9，0 是整段匹配 |
| `$$` | 一个字面 `$` |
| 其它字符 | 原样保留 |

- `field` 可用 `title` / `content` / `summary` / `topic`，但**只能引用有正向
  `=~` 的字段**；引用不存在的组号会在加载时让整条规则被跳过。
- 正则在求值时因短路没有执行（例如 `or` 的右侧），对应捕获组视为空串，
  并记一次 Warn。
- 重写后的 `title` / `content` 若为空，**保留原值**并记一次 Warn；`summary`
  允许被写成空串（等于清掉简介）。
- `rewrite.level` 只接受 `"debug"` / `"info"` / `"warning"` / `"error"` /
  `"critical"`。
- `rewrite.importance` 接受任意 32 位整数，写成一个整数（不是字符串）：

  ```toml
  [rules.rewrite]
  importance = 4
  ```

  约定的语义是 `0` = 未指定、`1–5` = 由低到高；宿主原样传给 Notifier，
  不解释、不裁剪。`notifier.imgui` 为 `1–5` 提供单独的驻留时间设置，其它
  数值回退到它的默认时长。
- `rewrite.time` 先按 §9.4.1 的同款模板展开，再把结果解析成 Unix 毫秒：

  ```toml
  [[rules]]
  id = "mail-time"
  match = 'content =~ "发布时间(?:：|:)\s*(\d{4}/\d{1,2}/\d{1,2}\s+\d{1,2}:\d{2}(?::\d{2})?)"'
  [rules.rewrite]
  time = "$content.1"
  ```

  解析失败（或展开为空）时**保留原时间**，并记一次 Warn；规则本身继续生效。
- 重写发生在**内存中的通知上**：来源趟的结果进入历史，投递趟的结果只影响
  那一次 `on_notify` 的视图，历史保持原样。

#### 9.4.1 `rewrite.time` 接受的时间格式

只适配**年在前**的中国习惯格式（`年/月/日`，不接受 `日/月/年`）。解析器会
自动识别分隔符、可选的时分秒与毫秒，不需要额外写 `format`：

| 示例 | 说明 |
|---|---|
| `2026/10/20 12:34:56` | 斜杠分隔，带秒 |
| `2026-10-20 12:34` | 短横线分隔，可省略秒（按 `:00`） |
| `2026.10.20 12:34:56.789` | 点分隔，毫秒可选 |
| `2026年10月20日 12:34:56` | 汉字分隔 |
| `2026年10月20日12时34分56秒` | 汉字时分秒 |
| `2026 10 20 12:34:56` | 纯空白分隔 |
| `2026-10-20` | 只有日期，按本地时间 `00:00:00` |
| `2026-10-20T12:34:56+08:00` | ISO 8601，支持 `Z` / `+08:00` / `+0800` |
| `2026-10-20 12:34:56 北京时间` | 尾部时区名字（目前识别“北京时间”= UTC+8） |
| `20261020` / `20261020123456` | 紧凑日期 / 紧凑日期时间 |
| `1750000000` / `1750000000000` | 纯数字按 Unix 秒 / 毫秒解释 |

- 没有显式时区时按**本机本地时区**解释；带 `Z` 或偏移量时按该时区换算成 UTC。
- 中文标点不会自动转换：正则里匹配全角冒号时不要写进字符类 `[...]`
  （`std::regex` 按字节处理字符类，多字节字符会拆成多个单字节候选）。
  用 `(?:：|:)` 这样的分组写法。
- 时间被改写后，历史列表、"多久以前"、规则保存的 `time` 与路径占位符都会
  使用这个真实时间。**浮层自动消失仍从收到通知的时刻开始计时**，不会因为
  提取出来的是几小时前的存量通知而立刻消失。

### 9.5 顺序与两趟

1. 规则按**文件顺序**执行；每条规则看到的是前面规则改写后的值（累积求值）。
2. 只有**启用**的规则参与；禁用的规则完全跳过。
3. 一条规则匹配后：有 `drop` 就终止当前趟并丢弃；否则执行重写；
   若还有 `handle = true`，当前趟到此为止。
4. `drop` 规则后面的规则不会再执行（无论 `handle` 写没写）。

| 趟 | 何时 | 影响范围 |
|---|---|---|
| 来源趟 | `Admit`，通知进入队列/历史之前 | 改写进入历史；drop 后通知不存在（计入“来源过滤”） |
| 投递趟 | 主线程分发，每个 Notifier 的 `on_notify` 之前 | 只影响该 Notifier 收到的视图；drop 表示这个 Notifier 收不到（计入“投递过滤”） |

### 9.6 自动简介

默认文件里的第一条规则就是它：

```toml
[[rules]]
id = "auto_summary"
name = "自动简介"
type = "auto_summary"
from = "content"
max_codepoints = 20
only_if_empty = true
```

- 它按**顺序**参与来源趟，因此排在它后面的规则可以匹配刚刚生成的 `summary`。
- 把它禁用或删掉，宿主就**不再自动生成简介**：来源没给 `summary` 时它就是空串。
  这就是“summary 生成是规则而不是写死在管线里”的含义。
- `only_if_empty = true` 时，来源已提供的、或前面规则写过的非空 summary 不会被覆盖。
- 生成算法与 SDK 的 `sm::make_summary` 一致（折叠空白、截断加省略号）。
- **`max_codepoints` 没有上限**：写多少就取多少，输出不会长于正文（折叠空白只会
  更短）。`20` 只是省略该键时的默认值。

### 9.7 出错的粒度

| 情况 | 行为 |
|---|---|
| 单条规则字段类型错 / 正则编译失败 / 模板组号越界 / 未知 `type` / 重复 id | **只跳过这一条**，记 Warn，其余规则照常加载 |
| 整个文件 TOML 语法错、`rules` 不是数组、`schema_version > 1` | 启动时规则集为空；**手工重载时保留上一次的规则集** |
| 手动重载成功 | 新规则集替换旧规则集，命中/拦截计数归零 |

`rules.toml` 里的正则与 `target` 模式各限 **1024 字节**；超长视为该条规则错误。

### 9.8 与控制面板的关系

“规则”页列出已加载的规则：`启用 / # / 名称 / 命中·拦截 / 状态`。
勾选启用会立即生效，并写回 `config.toml [rules]`；“重新加载规则”重新读取
`rules.toml`，但**永远不会写它**。选中一行可以查看类型、阶段、目标、匹配
表达式、重写模板、自动简介参数与保存设置（启用状态、路径模板）。

安全模式（`--safe-mode`）下启用开关是灰的：本次运行不会写回配置，也不会
执行任何规则保存。

### 9.9 规则保存与占位符

`[rules.save]` 让规则在命中时把通知的全部细节**追加**写入文件。它只对
`type = "match"` 生效；写在 `auto_summary` 上会 Warn 并忽略。

```toml
[[rules]]
id = "mail-archive"
name = "归档邮件"
match = 'title =~ "^(.*)$" and topic =~ "^mail\."'
[rules.rewrite]
title = "[归档] $title.1"
[rules.save]
enabled = true
path = "notify/{year}/{month}/{ruleid}-{title}.txt"
```

| 键 | 类型 | 缺省 | 说明 |
|---|---|---|---|
| `enabled` | bool | `true`（写了 `[rules.save]` 时） | 显式 `false` 可暂时关闭这条规则的保存 |
| `path` | string | 空 = 默认路径 | 支持 `{name}` 占位符；相对路径相对 `data_dir` |

- `[rules.save]` 必须紧跟它所属的 `[[rules]]`，并在下一条 `[[rules]]` 之前。
  内联写法 `save = { enabled = true, path = "..." }` 也接受。
- **默认路径**是 `data_dir/notify/{ruleid}.txt`。写相对路径时同样相对
  `data_dir`；绝对路径原样使用。
- 写 `enabled = false` 又写 `path` 会 Warn，且不保存。
- 路径模板超过 1024 字节时该规则的保存被关闭（规则本身仍加载）；
  展开后超过 900 字节、没有文件名或含 `.`/`..` 路径段时 Warn 并跳过该次保存。
- 同一路径多次命中是**追加**，文件会持续增长；需要按天/按规则分文件请用占位符。
- **全局许可**：还必须把 `config.toml` 的 `[app] allow_rule_save` 设为 `true`
  （或勾选通知页的开关），否则所有规则都不写文件。开启后不区分来源插件。

#### 触发时机

- **来源趟**：通知一被规则命中就保存，即使它随后被 `drop`、因缺少必填项被
  拒绝或排队时被丢弃，文件里也已经有这一条。此时还没有分配 `seq`，
  文本块里不写 `seq` 行。
- **投递趟**：每条通知、每个命中的 Notifier 都会跑投递规则；同一条规则对
  同一条通知**只保存一次**（取第一个命中的 Notifier）。
- 保存的是**该规则自己的 `rewrite` 生效之后**的字段，不是整趟结束后的最终
  值：同时写了 `rewrite` 与 `save` 的规则不会写出未重写的原文，也不会混入
  同趟后续规则的改写。
- 同一 `(来源, id)` 的原地更新会重新走来源趟并再次追加，因此一条通知
  可能对应多个文本块。

#### 文本块格式

UTF-8、无 BOM、`\n` 换行。单行字段里的换行会被替换成空格，`content`
原样写出：

```
===== SimpleMessage rule save =====
rule: mail-archive (归档邮件)
phase: source
time: 2026-10-18 12:34:56.789
seq: 123
level: warning
importance: 4
source: source.webhook@1
topic: mail.inbox
id: 42
title: [归档] 新邮件
summary: ...
url: ...
icon: ...
actions:
  - open = 打开
content:
<原始正文>
===== end =====
```

`level` 使用稳定 token：`debug` / `info` / `warning` / `error` / `critical`；
`importance` 是重写后的整数（`0` 也会写出）。空的可选字段（`id` / `summary` /
`url` / `icon` / `actions`）会省略；
`seq` 只在大于 0 时写出；投递趟额外写 `notifier:`。

#### 占位符

语法 `{name}`，名字只允许字母、数字、下划线；`{{` 与 `}}` 表示字面花括号。
未知名字原样保留，并在加载 `rules.toml` 时 Warn。日期取通知时间（本地时区；
通知时间为 0 时取保存时刻）。

| 占位符 | 值 |
|---|---|
| `{date}` | `YYYY-MM-DD` |
| `{year}` / `{month}` / `{day}` | `2026` / `10` / `18`（补零） |
| `{hour}` / `{minute}` / `{second}` | 补零的时分秒 |
| `{time}` | `HH-MM-SS` |
| `{datetime}` | `YYYY-MM-DD_HH-MM-SS` |
| `{timestamp}` | Unix 毫秒 |
| `{title}` `{content}` `{summary}` `{topic}` | 通知字段（重写后的值） |
| `{level}` | `debug` / `info` / `warning` / `error` / `critical` |
| `{id}` `{url}` `{icon}` `{source}` `{seq}` | 通知元数据 |
| `{ruleid}` `{rulename}` | 触发保存的规则 |
| `{phase}` | `source` / `delivery` |
| `{notifier}` | 投递趟的 Notifier id；来源趟为空 |

- 只有**替换值**会被清洗：`<>:"/\|?*` 与控制字符换成 `_`，去掉尾部点和空格，
  空值或 `.`/`..` 变成 `_`，规避 Windows 保留设备名（如 `CON.txt`），
  UTF-8 安全截断到 120 字节。
- **模板本身不做清洗**，所以 `/`、`\` 与 `C:` 这类字面量可以正常用于
  建子目录或写绝对路径。
- 不要把 `{content}` 放进路径：它会被清洗并截断，文件名几乎不可读，
  也容易产生大量不同文件。用它记录正文请交给文本块本身。
