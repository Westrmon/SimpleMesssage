# 01 — 架构总览

本篇讲这个程序是怎么搭起来的：有几条线程、调度怎么转、UI 什么时候存在、
插件的生命周期怎么走，以及那些已经定下来的设计决策。

---

## 1. 这是什么

SimpleMessage 是一个常驻后台的通知聚合与投递工具。它自己**不产生**任何信息，
而是提供一套机制，让两类插件协作完成"采集 → 路由 → 呈现"：

```
  ┌──────────────┐   调度循环    ┌───────────┐   队列/路由   ┌───────────────┐
  │ Source 插件  │ ───────────▶ │   宿主     │ ───────────▶ │ Notifier 插件 │
  │ （数据来源）  │   返回通知    │ 调度+路由  │   投递通知    │ （通知出口）    │
  └──────────────┘              └───────────┘               └───────────────┘
                                      ▲
                                      │ 宿主自身也是一个通知来源（日志事件）
                                      │
                                 用户在这里操作控制面板（imgui）
```

典型用法：用一个插件定期检查邮箱、一个插件盯着某个目录、一个插件轮询某个
API；再用一个插件把结果弹成桌面浮层、另一个插件推送到手机、第三个插件
静默归档成文件。这些插件之间互不认识，全部通过宿主中转。

## 2. 术语表

**这份表是全文的权威定义。**同一概念在代码、文档、界面里必须用同一个词；
出现第二个叫法就说明有人在自由发挥，请改回来。

> 文档中出现的规范用语含义固定：
> **必须 / 禁止** = 硬约束，违反会导致崩溃、数据损坏或功能不可用；
> **应当 / 不应当** = 强烈建议，偏离需要有明确理由；
> **可以** = 可选。

| 术语 | 英文/代码名 | 定义 |
|---|---|---|
| **宿主** | host | 本程序的可执行文件本体。负责调度、路由、插件管理、UI 会话、配置、日志。它不是插件，也不通过插件机制加载自己。 |
| **插件** | plugin | 一个 DLL，导出一组固定的 C 符号（见 [01-入门](插件开发/01-入门.md)），实现 `sm::IPlugin`。**一个 DLL 只含一个插件类型**，但可以有多个运行实例（仅 Source）。 |
| **调度子项插件** | Source | `PluginMeta::kind == Source` 的插件。数据来源。由调度循环驱动，每次被调用时返回 0..N 条通知并注册下次调度时刻。 |
| **UI 插件 / 通知器** | Notifier | `PluginMeta::kind == Notifier` 的插件。通知出口。它决定通知怎么呈现（浮层、原生弹窗、写文件、推送到远端……），**不一定要用 imgui**。 |
| **插件类型** | plugin type | 一个 DLL 的加载与校验结果：模块句柄、元信息、导出函数、设置 schema、订阅声明。**一个 DLL 只有一个类型**，与运行实例数无关。 |
| **插件实例** | plugin instance | 一个 `[[instances]]` 行：独立的 `sm_create_plugin` 对象、设置文件、调度槽、日志来源与统计。实例 id 形如 `source.email`（首个）或 `source.email@2`。**多实例只开放给 Source**。 |
| **通知** | Notification | 一条信息。字段见 [02-SDK接口参考](插件开发/02-SDK接口参考.md)。它是两类插件之间唯一的数据形态。可选字段 `icon` 是本地路径或 http(s) 图片地址，由宿主按需加载成纹理。 |
| **主题** | topic | 通知的分类标签，点分命名的小写字符串，如 `mail.inbox`。路由的依据。 |
| **订阅** | subscription | Notifier 声明的它关心的 topic 模式，如 `mail.*`。**声明为空 = 订阅全部**。 |
| **路由** | routing | 把一条通知交给哪些 Notifier 的判定过程。默认由订阅决定，配置可以覆盖。 |
| **调度** | scheduling | 宿主决定"什么时候再调用某个 Source 的 `start()`"的过程。**每个 Source 同时只有一个下次调度时刻**。 |
| **调度循环 / 调度线程** | scheduler / scheduler thread | 宿主内部那条负责在到点时调用 Source 插件的线程。与主线程并列，只有两条线程。 |
| **主线程** | main thread | 宿主内部持有窗口与消息循环的那条线程。所有 UI、以及插件除 `start()` 外的所有回调都在这条线程上。 |
| **UI 会话** | UI session | 一段"imgui 上下文存在、渲染循环在跑"的区间。控制面板、通知表面与每个插件的详情窗口**各有自己的上下文**、各自引用计数：某张表面的引用归零则销毁它的上下文、停止渲染。 |
| **UI 表面** | UI surface | 需要一个 imgui 上下文才能存在的窗口的统称：控制面板、通知表面（浮层画在这扇独立的窗口上）与详情窗口（每个插件最多一扇）。每张活跃的表面持有 UI 会话引用。 |
| **控制面板** | control panel | 宿主自己绘制的配置界面（七页：概览/插件/通知/规则/路由/日志/关于）。**窗口常驻、平时隐藏**；它的 imgui 上下文按需创建、关闭即销毁。 |
| **规则** | rules | 通知源与浮层之间的宿主中间层，配置在 `rules.toml`。用表达式匹配 `title` / `content` / `summary` / `topic`，可改写标题、内容、简介、级别，也可丢弃。分**来源**（入队时，影响存档与所有 Notifier）与**投递**（某个 Notifier 的 `on_notify` 之前，只影响那一次调用）两趟。规则还可选配 `save`：在命中时把通知（含该规则自己重写后的字段）追加写入文件，受 `[app] allow_rule_save` 总开关控制。 |
| **浮层** | toast | Notifier 画在**通知表面**上的临时通知卡片：贴哪个屏幕角由宿主的 `[notify_window]` 配置决定（见 [03-配置格式](插件开发/03-配置格式.md) §3.4、[02-宿主设计](02-宿主设计.md) §11.6）。卡片由 Notifier 自己绘制，承载它的窗口由宿主提供。 |
| **详情视图** | detail view | 由 Action 触发、承载通知完整内容的独立窗口。由 Notifier 绘制，宿主提供窗口。 |
| **动作** | Action | 通知上的一个可点击项，只有 `id` 与 `label`。点击后的处理由 Notifier 决定。 |
| **设置项** | setting | 插件声明的可配置项。声明在 `PluginMeta::settings` 里（schema），值存在 `<实例 id>.toml` 里，界面由宿主自动生成。 |
| **arena** | arena | 宿主在每次插件回调期间提供的一次性分配器。分配的内存随该次回调结束而回收。 |
| **结构性事件** | structural event | 宿主自身产生的、关于系统运行状态的通知：插件崩溃/被禁用、配置损坏、宿主启停。它们**不受** `notify_log_level` 阈值控制。 |
| **内部来源** | internal source | 宿主作为通知来源时的身份，`id` 固定为 `sm.host`。走与插件完全相同的管线。 |
| **保留命名空间** | — | `sm.` 前缀。插件 id 与 topic 都**禁止**使用它；它属于宿主。 |
| **看门狗** | watchdog | 宿主用来发现"插件卡死"的计时机制。它只**标记**、不终止线程 —— 详见 [02-宿主设计](02-宿主设计.md)。 |
| **崩溃屏障** | crash barrier | 宿主包裹每次跨插件调用的 SEH 保护，把访问违例等结构化异常降级为"该插件被禁用"。 |

## 3. 一次通知的完整旅程

用一个具体例子把上面的词串起来。假设 `source.email` 每分钟检查一个目录，
发现了一个新文件：

1. **调度线程**到点，宿主先清空该插件的"下次调度时刻"，然后调用它的 `start()`。
2. 插件扫描目录，在 **arena** 里构造一条 **Notification**，填好 `title`、
   `content`、`topic = "file.new"`、`level`、`time_unix_ms`，以及两个 **Action**
   （`details` 与 `dismiss`），但不填 `summary`（留给宿主生成）。
   它调用 `schedule_next(60000)` 注册**下一次调度**，然后返回 `StartResult::Ok`。
3. 宿主收回 arena 前，把通知**深拷贝**进队列；此时填入 `source_plugin = "source.email"`
   （这个值是**实例 id**，若这是第二个邮箱实例则为 `source.email@2`）
   与一个递增的 `seq`，然后跑**来源阶段的规则**（`rules.toml`）：默认的第一条
   `auto_summary` 规则用 `sm::make_summary()` 生成 `summary`（默认 content 前 20 个码点，可由规则的 `max_codepoints` 改写），
   其它规则可以继续改写字段，也可以在这里把通知**丢弃**。
4. **主线程**从队列取出通知，按**路由**规则找出订阅了 `file.new` 的 Notifier。
   假设命中了 `notifier.imgui` 与 `notifier.console`。
5. 对每个命中的 Notifier，宿主调用它的 `on_notify(notification)`。
   - `notifier.imgui` 把这条排进自己的**浮层**队列，并调用
     `request_ui_surface(5000)` —— 这会**创建 UI 会话**（如果还没有），
     于是 imgui 上下文被建立、渲染循环开始跑。
   - `notifier.console` 按自己的 `min_level` 决定是写一条日志还是忽略。
6. 浮层存活期间，宿主每帧调用 `notifier.imgui` 的 `draw_ui(history)`，
   它用 `imgui_context()` 拿到的上下文画出卡片。
7. 用户点了卡片上的"详情"。插件不能在自己的 `draw_ui` 里直接处理（那会重入），
   于是调用 `host()->invoke_action(n.seq, "details")`。宿主在本帧结束后回调它的
   `on_action(...)`，插件在里面调用 `set_view_title("文件详情")` 与
   `request_ui_surface(0)`（0 = 持续持有）。
8. 宿主发现该插件有了**详情视图**，于是**新建一扇独立的详情窗口**（控制面板
   开不开、在不在前面都不影响它），每帧调用其 `draw_view()`，由插件画出完整
   content。详情窗口里只有这一个插件的视图，不混入控制面板的七页。
9. 用户依次关掉浮层、详情窗口与控制面板后，所有 **UI 表面**消失，引用计数归零，
   宿主销毁 imgui 上下文、停止渲染循环。**CPU 占用回到 0。**

整条链路上没有一个"宿主需要知道插件内部在干什么"的环节 —— 这就是插件机制的
全部价值。

## 4. 既定决策

以下是需求澄清阶段逐轮确认的结论。**这一节是后续所有文档的依据**；
如果某处实现与它冲突，以本节为准，并修改实现。

### 4.1 交付边界

第一轮交付的边界是「只交付**设计文档 + SDK 接口头文件 + 示例插件骨架 +
构建/配置/脚本**，不写宿主实现与插件业务逻辑」—— 该边界已被后续交付取代，
现在的仓库里宿主与插件都已经实现，交付状态见 [docs/README.md](README.md)。
**至今有效**的是文档定位：文档必须翔实到"另一个实现者照着它就能做出完整可
交付的软件"。**为什么不选另一条**：文档先行让后续实现有可验收的施工图；
反过来先写实现再补文档，规格会被实现反向固化。

### 4.2 平台与工具链

优先 **Windows 10/11 x64**，平台相关代码**全部**收敛在 `src/platform/`，
对外只暴露那里的抽象头（`platform.h`、`window.h`、`fs.h`、`system.h`、
`console.h`、`message_window.h`、`dialog.h`、`sound.h`、`image.h`、`tray.h`、
`entry.h`、`utf8.h`），其它地方禁止直接调用平台 API、包含 `<windows.h>` 或写
`#ifdef _WIN32`（`include/sm/export.h` 的导出修饰除外）。
`SM_WIN7_COMPAT` 只提供"静态 CRT + `_WIN32_WINNT=0x0601` + 禁用清单"的
最佳努力配置，**不能**弥补现代工具集已不再保证 Win7 目标这一事实（详见 §6）；
构建用 CMake，imgui 与 toml++ 作为**被跟踪的普通文件**随仓库放在 `external/`
（不是 submodule）。**为什么不选另一条**：真正要支持 Win7 需要换回旧工具集
（v142 及以前）与旧 SDK，且本项目当前无法验证 —— 用现代工具集硬扛只会得到
"编译过、跑不起来"的二进制。

### 4.3 插件模型

一个 DLL 一个插件，四个 `extern "C"` 导出符号，内部是 C++ 纯虚接口；跨边界
**禁止**传 STL 类型、**禁止**抛异常、**禁止**跨模块释放内存、**禁止**跨 DLL
使用 RTTI，**必须**同工具集、同 CRT。两类插件继承**同一个**基类 `sm::IPlugin`，
靠 `PluginMeta::kind` 区分，生命周期为 `initialize / start / stop / exit`
（语义见 [02-SDK接口参考](插件开发/02-SDK接口参考.md)）。发现方式是扫描插件
目录，**先 `LoadLibrary` 读元信息、跑完 12 条校验，才决定是否创建实例**，因此
ABI 不匹配的插件从不曾被执行过一行代码。**为什么不选另一条**：让两类插件各
有一套入口会增大 ABI 面与校验分支，而"一个 DLL 一个插件、`<id>.dll` 文件名校验
一致性、设置项走声明式 schema、启用状态留在宿主 `config.toml` 而不在插件目录"
这几条把宿主与插件之间的一致性压到了最低成本。

### 4.4 调度

宿主拉、插件自报：`schedule_next(ms)` / `schedule_at(unix_ms)` 在 `start()` 内
调用，**每个 Source 实例只有一个下次调度时刻**（同一类型的不同实例各排各的；
插件内部若有多条节奏，自行取最小），
每次 `start()` 之前宿主清空该插件的下次时刻 —— **不注册即休眠**。`start()` 返回
`Ok / Empty / Error / Abort / Cancelled` 五态，**`Error` 不等于禁用**：宿主指数
退避重试（上限 30 分钟），只有连续失败达阈值或 `Abort` 才禁用。**为什么不选另一
条**：per-topic 调度会把调度器从一张表变成两层嵌套表并引入并发触发与重入，而
"一次失败即禁用"会把服务器维护、网络瞬断这类常态故障变成用户手动重启用。

### 4.5 线程与隔离

**两条线程**：主线程（窗口 + 消息循环 + 所有 UI 与插件回调）和调度线程
（串行执行 Source 的 `start()`）。跨插件调用全部包 **SEH 崩溃屏障**；崩溃 →
记日志 → `FreeLibrary` → 禁用 → 持久化。卡死用**看门狗标记 + 协作式取消**
（`is_cancelled()`），**绝不强杀线程**，连续超时达阈值同样禁用并持久化。
**为什么不选另一条**："每插件一个线程"在资源受限场景下是明确的反模式（每条线程
的栈与内核对象开销会很快超过程序其余部分），而强杀超时线程无法安全实现，风险
高于收益。

### 4.6 数据与管线

通知字段为 `id`(可空) / `title` / `content` / `summary` / `time_unix_ms` /
`level` / `topic` / `url` / `actions`，其中 `source_plugin` 与 `seq` 由宿主填，
`summary` 留空时由**默认的 `auto_summary` 规则**用 `sm::make_summary()` 按
**20 个 Unicode 码点**（默认值，可由规则的 `max_codepoints` 覆盖）截断、归一化空白、不切断 UTF-8。**通知只有一条通路：
`start()` 返回**；插件数据通过宿主 **arena** 分配，插件从不释放任何东西。
**一条全局队列**（容量 1000，满了丢最旧并记账），`id` 非空则**原地更新**
而非新增；未匹配任何 Notifier 的通知**丢弃但记 Debug 日志 + 计入统计**，
内存历史保留 200 条、**默认不落盘**（归档由 `notifier.archive` 插件承担，
另有面板导出按钮）。**入队前先跑来源阶段的规则**（`rules.toml`，可改写/
丢弃），**每次 `on_notify` 前跑投递阶段的规则**（只影响那一次调用）。
**为什么不选另一条**：允许"随时推送"会产生第二条投递路径，背压与去重都要
写两遍。

### 4.7 UI

imgui 用于**宿主提供的三类窗口** —— 控制面板、通知表面（浮层画在后者上）与
每个插件至多一扇的详情窗口，插件可以完全不用 imgui，也可以自己开原生窗口。
**UI 会话引用计数**的来源只有三个（面板、浮层、详情视图），并且**按表面分开
算账**：面板表面只要 [面板] 归还，通知表面只要 [浮层] 归还，详情表面要该插件
的 [视图] 归还，每张表面各自还清即销毁它的 imgui 上下文与渲染后端、**并停止
为它出帧**（空闲 CPU = 0）。详情窗口是宿主新建的**独立普通窗口**（可缩放、
有标题栏，标题来自 `set_view_title`），不借控制面板的窗口、也不使用 ImGui
viewport；面板七页为概览 / 插件 / 通知 / 规则 / 路由(只读) / 日志 / 关于，设置**立即
生效**，插件**禁止**缓存任何 imgui 指针或跨帧状态。**为什么不选另一条**：
让上下文常驻与"资源受限、空闲零占用"直接冲突，而用 ImGui viewport 做详情
窗口需要 docking 分支 + 平台窗口管理，跨平台负担重。

### 4.8 配置

`config.toml`（本体 + `[[instances]]` 实例与启用状态 + 路由覆盖）与
`plugins/<实例 id>.toml`（插件设置）分离。两者的 `schema_version` 是
**独立的版本号空间**（当前分别为 2 与 1）：高于本程序认识的版本**拒绝启动**，
低于则走迁移链，解析失败则**备份后用默认配置启动**（绝不因为配置错误拒绝启动）。
写回是防抖批量 + 原子替换 + 写前备份，**接受注释丢失**。**为什么不选另一条**：
保留 TOML 注释需要一个保留格式的解析库，与"简洁"冲突 —— 改用"首次生成带
注释的模板"。

### 4.9 日志

自实现 `LogF(level, fmt, ...)` printf 风格（零 ABI 风险），级别
`Trace/Debug/Info/Warn/Error`，格式 `[时间][级别][插件id][线程] 消息`。互斥锁
保护的有界环形缓冲 + 后台写线程批量落盘，`Warn` 及以上立即 flush，缓冲满则
丢最旧并记账，**永不阻塞调用方**；`main()` 中显式先 `LogInit()`、后
`LogShutdown()`，不依赖静态对象，SEH 崩溃路径强制 flush。**通知不按 Info 级写
日志**（只进 Trace/Debug），避免高频通知淹没日志。**为什么不选另一条**：第三方
日志库会引入工具集/CRT 与 ABI 风险，而"日志最先初始化、最后退出"要求它不能
依赖静态对象的初始化顺序。

### 4.10 宿主自身作为通知来源

宿主是一个**内置虚拟 Source**（`id = "sm.host"`），走完全相同的管线；
**`sm.` 前缀为宿主保留**，插件 id 与 topic 都不得使用。日志 → 通知的桥为
`Error→Error`、`Warn→Warning`、`Info→Info`（`Trace/Debug` 永不转换），阈值
`[app] notify_log_level` 默认 `"error"`，**结构性事件不受阈值控制**。**破环
硬规则**：由通知引发的日志永不参与 log→notify 桥接（不可绕过的来源标记）；
`sm.host.log` 每 10 秒最多 5 条，超出部分合并计数进一条补充通知（复用 `id`
原地更新），结构性事件不限流。**为什么不选另一条**：让宿主绕过管线直发通知会
形成第二条路径，破坏"两类插件之间唯一的数据形态"这条基础设定。

### 4.11 外壳与运维

托盘常驻、**单实例**（第二个实例唤起既有实例的面板后退出）、WINDOWS 子系统 +
`--console` 附加调试控制台；单一中文界面，字符串集中在一个头文件，不做 i18n
框架。**不做**开机自启的内置逻辑，只交付脚本（Windows 写 `HKCU\...\Run`，
Linux 用 `~/.config/autostart/*.desktop`）。CLI 为 `--config-dir` /
`--plugin-dir` / `--console` / `--safe-mode` / `--help` / `--version`，其中
**`--safe-mode` 是必需的逃生通道**；默认目录 exe 同目录优先，不可写时回退
`%APPDATA%\SimpleMessage\`。**为什么不选另一条**：宿主自己写注册表让程序具备了
持久化自己的能力，那是杀软与用户安全直觉会关注的对象，而收益只是"少点一次
脚本"。

### 4.12 界面中未采纳的方案（记录以免反复讨论）

以下都是讨论过并被否决的选项。再次遇到时请先读这一节：

| 被否决的方案 | 否决理由 |
|---|---|
| 每插件一个调度节奏（per-topic 调度） | 把调度器从一张表变成两层嵌套表，还要处理并发触发与重入；收益只是界面好看一点 |
| cron 表达式 | 解析器是纯负担，"每天 9 点"用 `schedule_at` 就够 |
| 通知从任意线程随时推送 | 会产生第二条投递路径，背压与去重都要写两遍 |
| 独立进程托管插件 | 真隔离，但内存与复杂度大幅上升，直接违背资源受限目标 |
| 强杀超时插件的线程 | 做不到安全实现，风险高于收益 |
| 插件跨模块自由 free | 跨模块释放是崩溃高发区；改用 arena 后彻底消失 |
| 保留 TOML 注释 | 需要一个保留格式的 TOML 库，与"简洁"冲突；改用"首次生成带注释的模板" |
| ImGui viewport 做详情窗口 | 需要 docking 分支 + 平台窗口管理，跨平台负担重 |
| 单索引文件列出所有插件 | 插件增删时必然失同步，是经典的运维坑 |
| 通知携带 icon / 富交互 action | 资源与路径解析成本高，没有交互式后端时无意义 |
| `^` / `~` / 通配符版本范围 | 表达力换来的复杂度不值得，且不同实现理解不一致 |

## 5. 进程结构

```
SimpleMessage 进程
├── 主线程 ──────────────────────────────────────────────────────────
│   ├── 窗口 + 消息循环（托盘、单实例唤醒消息）
│   ├── UI 会话管理 → 各张表面各自的 imgui 上下文 + 渲染循环（按需创建）
│   ├── 通知队列的消费端 → 路由 → 调用 Notifier 的 on_notify
│   ├── 主线程任务队列（post_to_main_thread 的消费端）
│   ├── 控制面板绘制 → 七页
│   └── 插件生命周期调用：initialize / stop / exit / on_action /
│                          draw_ui / draw_view
│
├── 调度线程 ────────────────────────────────────────────────────────
│   ├── 最小堆：每个 Source 一个下次调度时刻
│   ├── 可中断等待（IWaiter）→ 到点或被打断即醒
│   ├── 串行执行：逐个数到点的 Source 的 start()
│   └── 看门狗：记录每次 start() 的起止，标记超时
│
├── 日志写线程 ──────────────────────────────────────────────────────
│   └── 从有界环形缓冲批量落盘（见 02-宿主设计.md）
│
└── 图标加载线程（按需、短命）─────────────────────────────────────────
    └── 每条待加载的 Notification::icon 一条 detached 线程：http(s) 下载或读文件
        → WIC 解码；结果交回主线程上传纹理（见 02-宿主设计.md §7.5）

    常驻线程共三条。图标加载线程按需创建、完成即退出，且**不触碰任何插件**。
    插件仍然【不得】假定除主线程与调度线程之外还有任何线程会调用自己的回调。
```

**为什么只有两条业务线程。** "每插件一个线程"在资源受限场景下是明确的反模式：
每条线程要占一份栈（默认 1MB 保留）与一份内核对象，插件数量一多，
光线程开销就超过整个程序的其余部分。而 Source 的采集工作绝大多数是
"发一个请求、等一个结果"，串行执行的吞吐损失远小于它带来的简单性收益。

**由此产生的一条硬约束**：调度线程是共享的，所以**一个 Source 卡住，
所有 Source 都会被推迟**。这是看门狗存在的理由，也是
`start()` 里禁止无超时阻塞 IO 的理由（见 [02-SDK接口参考](插件开发/02-SDK接口参考.md)）。

## 6. 平台支持范围

### 6.1 当前目标

**Windows 10 / 11，x64**。工具链 v145（VS 2026），**C++17**（`cxx_std_17`，
见下面的说明），动态 CRT，Windows SDK 10.0.26100。

> **标准为什么是 C++17 而不是 C++20**：整个构建（SDK、宿主、插件、两个
> 依赖库）统一声明 `cxx_std_17`，实现代码也只用 C++17 的子集 ——
> 这样插件作者的门槛最低，且不会因为工具链的 `-std` 默认值不同而出现
> "我这能编你那不能编"。宿主自身仍然可以在不改 SDK 的前提下用更新的
> 语言特性，但需要同时把这些特性带来的工具链要求写进这里。

### 6.2 Windows 7 的现实

需求里提到"可能出现在早期系统，如 Windows 7"。必须把这件事说清楚，
因为它**不是靠写代码小心就能解决的**：

| 障碍 | 说明 |
|---|---|
| **工具集** | 较新的 VS 版本已不再保证 Win7 目标支持。本项目使用的 v145 完全不适用。 |
| **UCRT** | 用现代 SDK 构建的程序依赖 Universal CRT。Win7 需要先打 KB2999226，否则连启动都做不到。 |
| **清单项** | Windows 10 才认识的清单项（例如 segment heap）在旧系统上行为未定义或导致启动失败。 |
| **API 面** | 一不小心用到 Win8+ 才有的 API，在 Win7 上表现为"导入表里找不到符号，直接无法启动"。 |

因此本项目的策略是 **为切换留门，但不在当前目标上承担 Win7 的承诺**：

1. 平台相关代码**全部**在 `src/platform/` 之下，其它地方禁止调用平台 API。
   将来支持新平台 = 新增一个 `src/platform/<平台>/` 目录。
2. `SM_WIN7_COMPAT=ON` 会把 `_WIN32_WINNT` / `WINVER` / `NTDDI_VERSION`
   拉回 Win7，切静态 CRT、禁用清单。**它的作用是让"用了新 API"在编译期暴露**，
   而不是让现代工具集产出能在 Win7 上跑的二进制。
   静态 CRT 必须**全链路一致**，`external/CMakeLists.txt` 里四处缺一不可：
   自家目标走 `MSVC_RUNTIME_LIBRARY`、GLFW 走 `USE_MSVC_RUNTIME_LIBRARY_DLL=OFF`、
   libcurl 走 `CURL_STATIC_CRT`、imgui 单独补一条。漏掉任何一个的后果不是警告，
   而是链接期一堆 `unresolved external symbol __imp_fread`（静态侧混进动态 CRT 的
   导入符号），或者发布包里凭空多一个"目标机器必须装 VC 运行时"的依赖。
3. 真正的 Win7 支持路径：**装 VS2019 的 v142 工具集 + 配套旧 SDK**，
   用它构建，并接受"无法在本机验证"的现实。

> **给实现者的要求**：不要在代码里写 `#ifdef SM_WIN7_COMPAT` 之外的分支判断。
> 需要区分平台时，加一个 `src/platform/` 下的实现，而不是在业务代码里加 `#ifdef`。

**重新考虑的触发条件**：真的有了必须在 Win7 上跑的部署需求，且愿意为此维护
第二条工具链。

### 6.3 其它平台（POSIX 只有空壳）

`src/platform/posix/` 只有空壳，不提供实现。宿主当前**只支持 Windows 10/11 x64**。

**理由**：需求里的"适配各个系统"与"适配 Win7、资源受限系统"是**两个方向**：
一个要横向铺开，一个要向下兼容。两者都做会让平台层变成一堆
`#ifdef` 与两套未经验证的路径。当前选择是"先把一个平台做扎实"，
并把平台相关的代码全部关进 `src/platform/`（§6）。

**重新考虑的触发条件**：Windows 版本稳定发布之后。
平台层的抽象已经是完整的 —— 一个新平台需要实现的东西恰好就是
`src/platform/` 下各头文件声明的那些：动态库加载、崩溃屏障、可中断等待、
单调时钟、调试输出、单实例锁，以及 `fs.h` / `system.h` / `console.h` /
`message_window.h` / `dialog.h` / `sound.h` / `image.h` / `tray.h` /
`window.h` / `entry.h` 里的一切。工作量是清楚的，不是不可知的。

### 6.4 托盘与窗口也已收进平台层

早先的结论是"不为托盘造跨平台抽象"；本轮改动取代了它：`ITray` / `ITrayHost`
与 `TrayLabels` 已从 `platform/win32/tray.h` 上移到 `src/platform/tray.h`，
和 `window.h` 的 `IWindow` 一样按"抽象接口 + 每平台一份实现"分层。
目前仍然只有 Win32 实现（`src/platform/win32/tray_win32.cpp`），
但接口位置与其余平台层一致，新增平台时不需要再搬一次。

**理由**：托盘与窗口最终是同一类东西 —— 调用点只想知道"有没有托盘、
有没有窗口"，而不想知道外壳是什么。把它们与业务代码隔开之后，
`src/host/` 里不再出现 `HWND` / `HINSTANCE` / `<windows.h>`，
平台差异全部落在 `src/platform/` 的两个目录边界上。

## 7. 调度循环

### 7.1 数据结构

调度器维护一个**最小堆**，元素是 `(下次时刻, 插件)`。每个 Source 在堆里
**最多有一个**条目 —— 这是"每插件只有一个下次调度时刻"的直接体现。

```
        ┌────────────────────────────────────────────┐
        │  最小堆（按 next_due_ms 排序）               │
        ├────────────────────────────────────────────┤
        │  t=1000  source.mail                       │
        │  t=3000  source.email                  │
        │  t=9000  source.weather                    │
        └────────────────────────────────────────────┘
```

### 7.2 循环体

```
调度线程主循环：
  repeat:
    next = 堆顶时刻（堆空则视为"无限远"）
    timeout = next - monotonic_ms()
    woken = waiter.wait(timeout)          ← 可中断等待
    if woken:                             ← 有新任务/新注册/关停信号
        continue（重新评估堆顶）
    if 堆空: continue
    task = 弹出堆顶
    if task 已过期(超过一个宽限期): 记日志并跳到下一次注册
    run_start(task.plugin)                ← 见下一节
```

**必须用单调时钟**（`platform::monotonic_ms()`）而不是墙钟。用户调整系统时间
或 NTP 校时是常事，用墙钟时钟会让"5 分钟后再跑"变成"立刻跑"或"永远不跑"。

### 7.3 一次 `start()` 的执行

```
run_start(plugin):
    arena = 新建本次调用的 arena（上限见 §7.5）
    plugin->下次时刻 = 无            ← 先清空，实现"不注册即休眠"
    record: start_begin = now
    ok = platform::guarded_call(调用 plugin->start, &out, &seh_code)
    record: start_end = now

    if not ok:                       ← 插件崩溃
        写崩溃日志（含插件 id 与异常码）
        禁用该插件（持久化）并卸载
        return

    if (start_end - start_begin) > 看门狗阈值:
        标记该插件"本次超时"，累计计数
        写 Warn 日志
        if 累计连续超时 >= N:
            禁用该插件（持久化）
        （注意：无论超时与否，本次产出的数据仍然正常入队）

    按 out 的结果处理：
        Ok        -> 深拷贝 items 入队（填 source_plugin / seq / summary）
        Empty     -> 什么都不做，按插件注册的时刻继续
        Cancelled -> 什么都不做（不计入失败）
        Error     -> 记录一次失败；若该插件注册的时刻未变，则改为退避时刻
        Abort     -> 立即禁用该插件（持久化）并卸载

    回收 arena
```

### 7.4 退避规则

`Error` 的退避是**乘性**的，属性挂在插件上（不在堆元素上）：

| 连续失败次数 | 下次调度推迟到 |
|---|---|
| 1 | 插件注册时刻 × 2 |
| 2 | × 4 |
| 3 | × 8 |
| … | … |
| 上限 | 30 分钟 |

任何一次 `Ok` / `Empty` **清零**失败计数。达到阈值（默认 5 次连续失败）
则禁用并持久化。

> **为什么 `Error` 不能直接禁用。** 邮件服务器维护、网络瞬断、文件被 Excel
> 独占锁住 —— 这些都是常态。如果一次失败就等于禁用，用户会在一个下午里
> 手动重新启用十几次插件，然后得出"这软件很烂"的结论。

### 7.5 arena 上限

arena 是"每次回调一个"的。宿主必须给它设上限，否则一个失控的插件
（例如在循环里反复 `allocate`）能在几秒内吃掉整个进程的内存。

**建议上限**：单次回调 4 MiB，且单条通知的 content 不超过
`limits::kMaxContentBytes`（64 KiB）。超限时 `allocate()` 返回 `nullptr`；
插件**必须**检查返回值。宿主在 arena 耗尽时记一条 Warn。

## 8. UI 会话与渲染循环

### 8.1 为什么需要"会话"这个概念

需求里有一条看似矛盾的话：*"本体 UI 通常不会显示，所以 ui 部分主要是作为
一个子项调用，关闭后需要立即释放，防止内存占用"*，同时又要求
*"允许插件内部使用 imgui 绘制其他界面"*。

把这两条放在一起，结论是：**imgui 上下文的生存期不能被绑死在"控制面板"
上**。因为插件可能在控制面板关闭之后仍然需要绘制（例如一个还在倒计时的浮层，
或者用户正看着的详情视图）。反过来，也不能让上下文常驻 —— 那与
"资源受限、空闲零占用"直接冲突。

解法是**引用计数**。

### 8.2 引用计数规则

```
界面有【三类表面】，各有自己的窗口、imgui 上下文与渲染后端：
    [面板表面]  面板窗口：控制面板七页
    [通知表面]  第二扇窗口：各 Notifier 画的浮层（浮层不画在面板窗口里）
    [详情表面]  每个插件一扇独立窗口：只画该插件的 draw_view()

引用来源仍然只有三个，只是要按表面分开算账：
    [面板]   控制面板被打开                                      → 面板表面
    [浮层]   Notifier 调用 request_ui_surface(duration > 0) 且未到期 → 通知表面
    [视图]   Notifier 调用了 set_view_title() 且未 close_view()  → 该插件的详情表面

一张表面从空变为非空  →  建出它的窗口（通知与详情按需）、创建 imgui 上下文、
                        加载字体纹理、创建渲染后端、开始为它出帧
一张表面从非空变为空  →  停止为它出帧、销毁渲染后端与字体纹理、
                        销毁 imgui 上下文（面板窗口隐藏而不销毁；详情窗口销毁）
```

几个必须注意的推论：

- **`request_ui_surface` 的效果是"取最长的那个"，不是覆盖。**
  两个 Notifier 各自请求 5 秒与 60 秒，会话至少活 60 秒。
- **`request_ui_surface(0)` 是不能自然到期的**：它表示"我持续需要"，
  只有 `close_view()` 才会归还。这是详情视图的用法。
- **详情窗口不依赖控制面板。** 打开详情不会弹出面板，关掉面板也不会带走详情；
  反之，关掉详情窗口或插件调用 `close_view()` 只销毁该插件自己的那一扇。
- **一张表面销毁后，插件在那张表面上持有的一切 imgui 指针立即失效。**
  这不是"可能会失效"，是"一定失效"。因此插件禁止缓存任何 imgui 状态
  （见 [01-入门](插件开发/01-入门.md)）—— 包括跨表面缓存：`imgui_context()`
  回答的永远是"当前这一帧画在哪张表面上"。
- **渲染循环停止意味着 CPU 占用为 0。** 没有"每帧空转"的后台循环 ——
  这是资源受限目标的核心手段。任何"让程序看起来在运行"的常驻动画，
  都会直接破坏这个目标。通知表面还要再收一层：引用还在、但连续 30 秒
  画出来都是空的（例如只开着一个详情视图、屏幕上没有浮层），它也停止出帧、
  CPU 一并归零（休眠）；下一条通知到达时唤醒，运行时不必重建。

### 8.3 渲染循环的形态

窗口层换成 GLFW 之后，主线程每一轮就是"泵事件 → 每张有引用的表面各画一帧 →
阻塞等待"。三类表面各有自己的 imgui 上下文与渲染后端，而 imgui 的一帧只能装
一个上下文，所以它们不是"同一帧里画完"，而是各画各的：

```
主线程循环：
    platform::window::Pump()             ← 排空本线程所有窗口的事件（面板、通知
                                            表面、各详情窗口、宿主消息窗口），逐个分发
    FrameStep(now):                      ← §8.4 的顺序
        对每张【还有引用】的表面:
            ImGui_ImplGlfw_NewFrame（窗口后端，每张表面各一份）
            渲染后端 NewFrame（DX11 或 OpenGL，跟着启动探测的结论）
            ImGui::NewFrame
            ← 通知表面：调用各 Notifier 的 draw_ui(history)
            ← 面板表面：绘制控制面板七页
            ← 详情表面：调用该插件的 draw_view()
            ImGui::Render
            绑定渲染目标、提交绘制命令、Present（vsync）
    platform::window::Wait(NextWaitMs)   ← 阻塞等待，不空转
```

**没有任何一张表面还有引用时一帧都不画**，主线程完全阻塞在等待上。
某张表面还活着、但画出来是空的（见 §8.4 的休眠）时，也不为它出帧。

### 8.4 顺序约束

在同一帧内，宿主**必须**按下面的顺序调用插件，否则会出现"插件画的东西
比它看到的数据晚一帧"这类难查的问题：

```
1. 消费主线程任务队列（post_to_main_thread 的产物）
2. 消费通知队列 → 路由 → on_notify
3. 处理 invoke_action 排队 → on_action
4. 处理各表面的引用增减（可能创建或销毁某一扇窗口）
5. 对每张还存活的表面各出一帧（见 §8.3）：
       通知表面：NewFrame → draw_ui(history) → Render
       面板表面：NewFrame → 控制面板七页 → Render
       详情表面：NewFrame → draw_view() → Render（每个插件各一扇）
   引用还在、但连续 30 秒画出来都是空的表面不出帧（休眠）
```

## 9. 插件生命周期状态机

```
                （扫描到 DLL，读元信息并校验）
                          │
                          ▼
                    ┌───────────┐
                    │ Discovered│  已发现，未加载
                    └─────┬─────┘
            校验通过且已启用 │            校验失败 / 未启用
                          ▼                    │
                    ┌───────────┐              │
                    │  Loaded   │ FreeLibrary  │
                    │ （已加载） │◀─────────────┘
                    └─────┬─────┘
           initialize() 成功 │       initialize() 失败
                          ▼              │
                    ┌───────────┐        │
              ┌────▶│Initialized│        │
              │     └─────┬─────┘        │
   重新启用    │           │ 开始调度       │
   （再 initialize）       ▼              │
              │     ┌───────────┐        │
              └─────│  Running  │        │
                    └─────┬─────┘        │
            stop() 或崩溃/超时被禁用 / 宿主退出
                          │              │
                          ▼              ▼
                    ┌───────────────────────────┐
                    │  Stopped / Failed / Disabled│
                    └─────────────┬─────────────┘
                       宿主退出或用户卸载
                                  ▼
                            ┌───────────┐
                            │ Unloaded  │  exit() 已调用，FreeLibrary 已完成
                            └───────────┘
```

### 9.1 各转换的精确语义

| 转换 | 触发者 | 调用 | 线程 |
|---|---|---|---|
| Discovered → Loaded | 启动时扫描 / 重新扫描 / 用户启用 | `LoadLibrary` + 校验元信息 | 主线程 |
| Loaded → Initialized | 立即 | `initialize()` | 主线程 |
| Initialized → Running | 第一次调度到点 | `start()` | 调度线程 |
| Running → Stopped | 用户禁用 | `stop()` | 主线程 |
| Stopped → Initialized | 用户重新启用 | `initialize()` | 主线程 |
| 任意 → Disabled | 崩溃 / 连续超时 / `Abort` | `stop()`（若已 Running）→ `exit()` → `FreeLibrary` | 主线程 |
| 任意 → Unloaded | 宿主退出 | `stop()`（若已 Running）→ `exit()` → `FreeLibrary` | 主线程 |

### 9.2 生命周期保证（实现必须遵守）

1. **`initialize()` 必定在第一次 `start()` 之前调用**，且同一次启用期间只调用一次。
2. **`stop()` 对每次启用最多调用一次**，且必定在 `exit()` 之前。
3. **`exit()` 保证被调用**，只要 `sm_create_plugin` 成功过 ——
   即使插件崩溃被禁用，也要在 `FreeLibrary` 之前调用它。这意味着宿主
   要**在崩溃屏障之外**调用 `exit()`，否则崩溃过的插件会走不到清理路径。
   （实际上：SEH 只保护单次调用；`exit()` 是另一次调用，它自己也被屏障保护。）
4. **`exit()` 返回后宿主才会 `FreeLibrary`。** 这是插件销毁自己的线程、
   窗口、句柄的最后机会。
5. 崩溃/超时导致的禁用**持久化到配置**，下次启动不会自动加载。
   这是为了避免"启动即崩"的死循环 —— 详见 [02-宿主设计](02-宿主设计.md)。

## 10. 关键时序

### 10.1 通知从产生到浮层上屏（简版）

```
调度线程                     主线程
   │                            │
   │ start() 返回 N 条通知        │
   ├──────▶ 深拷贝 + 来源阶段规则 + 入队 ──▶│
   │                            │ 从队列取
   │                            │ 路由（按订阅匹配）
   │                            │ 每个 Notifier 前跑投递阶段规则
   │                            ├─▶ on_notify(n)     [notifier.imgui]
   │                            │      └─ request_ui_surface(5000)
   │                            ├─▶ on_notify(n)     [notifier.console]
   │                            │      └─ 写日志
   │                            │
   │                            │ 通知表面引用：空 → 非空
   │                            ├─▶ 建出通知表面（第二扇窗口 + 它自己的 imgui
   │                            │    上下文 + 渲染循环）；这一份按需建
   │                            │
   │                            │ 每帧：
   │                            ├─▶ draw_ui(history)
   │                            │
   │                            │ ... 5 秒后浮层自动消失 ...
   │                            │ request_ui_surface 到期
   │                            │ 通知表面引用：非空 → 空
   │                            └─▶ 销毁上下文，停止渲染循环（CPU → 0）
```

### 10.2 Action 点击（含 `invoke_action` 的绕行）

```
主线程                         主线程
   │
   │ 第 N 帧：draw_ui(history)
   │   └─ 用户点了"详情"按钮
   │        └─ host->invoke_action(n.seq, "details")
   │             （只入队，不在本帧回调）
   │
   │ 第 N 帧结束
   │
   │ 第 N+1 帧开始
   │   └─ 消费 invoke_action 队列 → on_action(n, "details")
   │        ├─ 拷贝一份通知（因为 n 只在本回调期间有效）
   │        ├─ set_view_title("文件详情")
   │        └─ request_ui_surface(0)      ← 持续持有
   │   └─ 会话已有视图引用 → 新建（或更新）该插件的独立详情窗口
   │   └─ draw_view()                      ← 画完整 content
```

> **为什么 `invoke_action` 要绕一圈。** 直接在 `draw_ui` 里处理点击，
> 意味着"点一个按钮"会改变宿主正在遍历的 UI 状态（可能开视图、可能改设置）。
> 推迟到下一帧的开头执行，把这类重入问题一次性消灭。顺带的好处是：
> 无论点击来自宿主画的通知卡片还是插件画的浮层，最终都走同一个
> `on_action` —— 插件不必写两套处理逻辑。

**分发这一步在路由之前先把该通知标为已读**（[02-宿主设计](02-宿主设计.md) §8.5、
[03-控制面板](03-控制面板.md) §4.3）：用户确实点了他屏幕上那张卡片，托盘图标理应对此
有反应 —— 与"哪个 Notifier 会响应这个动作"无关。

### 10.3 关停顺序

关停顺序错了会产生"日志里看不到崩溃原因"或"插件析构时访问已释放的宿主"
这类问题。**必须**按下面的顺序：

```
1. 关闭 UI 会话        各张表面停止渲染循环，销毁各自的 imgui 上下文（详情窗口一并销毁）
2. 停止调度线程        置关停标志 → signal waiter → join
3. 对每个 Running 的插件调用 stop()
4. 对每个已加载的插件调用 exit()      ← 把最后一个日志点留在这里
5. 卸载所有插件（FreeLibrary）
6. 关闭主线程任务队列与通知队列（丢弃未处理项，记日志说明丢弃了多少）
7. 写一份"已退出"的日志
8. LogShutdown()                       ← 日志最后退出
```

第 2 步必须能打断正在执行的 `start()`：宿主置位 `is_cancelled()`，
并给插件一个退出宽限期（建议 5 秒）。超过宽限期仍在执行，就记一条
"某插件未响应退出请求"的日志然后继续 —— **不**强杀线程，
因为强杀会让进程处于未知状态。**代价要说清楚**：这意味着一个卡死的插件
可以让宿主无法干净退出，最终是靠进程终止来收场的。这是"绝不强杀"这个
决定必须付出的代价，也是"看门狗 + 用户手动禁用"这套组合存在的理由。

## 11. 主线程任务队列

`post_to_main_thread()` 是插件从自己的线程回到主线程的唯一通道。

- **有界队列**（建议容量 256）。满了返回 `false`，**调用方必须尊重返回值**。
  不尊重它会得到一个"任务在某个时刻莫名消失"的诡异现象。
- **宿主不提供优先级，也不保证顺序之外的任何事** —— 同一次投递的多个任务
  按投递顺序执行。
- **任务函数 `fn` 自身也受崩溃屏障保护**，因此它在里面崩溃会连累
  **投递它的那个插件**被禁用。这与直接在 `on_notify` 里崩溃等价，
  是刻意的：隔离粒度是"插件"，不是"调用点"。
- **`fn` 禁止阻塞。** 它是主线程。需要慢操作就先投递、再做、再投递回来。

## 12. 启动与关停顺序

顺序是硬约束。尤其是"日志最先初始化、最后退出"与"UI 上下文按需创建"。

### 12.1 启动

```cpp
int wmain(int argc, wchar_t** argv) {
  LogInit();                     // ① 最先：这之后的每一步都可能要写日志
  parse_command_line(argc, argv);  // ② --help/--version 在此直接退出
  resolve_dirs();                // ③ 配置目录 / 数据目录 / 插件目录
  load_config();                 // ④ 失败则备份+默认值（见 插件开发/03-配置格式.md）
  apply_log_settings();          // ⑤ 日志级别等设置项在读到配置后立即生效
  acquire_single_instance();     // ⑥ 已被占用则唤醒它并退出
  init_platform();               // ⑦ 渲染器探测、窗口系统、消息窗口、托盘（不建 imgui 上下文）
  PluginManager::discover();     // ⑧ 扫描目录 + 校验元信息（不加载）
  PluginManager::load_enabled(); // ⑨ 加载已启用的插件并 initialize()
  Scheduler::start();            // ⑩ 启动调度线程
  InternalSource::install();     // ⑪ 宿主自身通知源进入管线
  run_message_loop();            // ⑫ 阻塞在这里，直到用户选择退出
  shutdown();                    // ⑬ 见 12.2
  return exit_code;
}
```

**注意 ⑧ 与 ⑨ 分成两步**：发现是"读取所有 DLL 的元信息"，加载是"真正
`LoadLibrary` 并实例化"。分成两步之后，控制面板可以在**不加载任何插件**的
情况下显示完整的插件列表（包括被拒绝的），而 `--safe-mode` 只需跳过 ⑨。

**⑦ 的顺序内部不能再调**：渲染器的探测必须在窗口系统起来之前（"要不要图形
上下文"是建窗口时的提示），窗口系统必须在任何一扇窗口之前（它一上来就把进程的
DPI 感知定成"每显示器 DPI 感知"，先建出来的窗口会按错误的 DPI 摆放），消息窗口
必须在托盘之前（它先于面板构造、后于面板析构，见 §12.2 与 `message_window.h`）。
这一串在 `app.h` 里以成员声明顺序写死，构造函数按它从上到下跑。

### 12.2 关停

严格按 §10.3 的八步：

```
1. 关闭 UI 会话              各张表面（面板、通知、详情窗口）的渲染循环、后端与 imgui 上下文（[02-宿主设计](02-宿主设计.md) §11.4）
2. 停止调度线程              置标志 → signal waiter → join（宽限期 5s）
3. 对每个 Running 的插件调用 stop()
4. 对每个已加载的插件调用 exit()        ← 最后一个日志点留在这里
5. 卸载所有插件（FreeLibrary）
6. 关闭主线程任务队列与通知队列（丢弃未处理项并记日志说明丢了多少）
7. 写一条"已退出"日志
8. LogShutdown()             ← 日志最后退出
```

**第 3、4 步的调用也要包崩溃屏障**，但屏障的失败处理不同：此时**不能**
禁用插件（配置写回可能已经关了），只记日志然后继续卸载。

## 13. 命令行与退出码

### 13.1 参数

| 参数 | 说明 |
|---|---|
| `--config-dir <路径>` | 覆盖配置目录（见 [03-配置格式](插件开发/03-配置格式.md) §1.1） |
| `--data-dir <路径>` | 覆盖数据目录 |
| `--plugin-dir <路径>` | 覆盖插件目录 |
| `--console` | 跟随附一个控制台窗口，日志同时输出到 stdout |
| `--safe-mode` | **不加载任何插件**，直接打开控制面板 |
| `--renderer <名称>` | 渲染后端：`auto`（默认，硬件 D3D11 可用则用它，否则 OpenGL）、`dx11`、`opengl`；认不出的名称按 `auto` 处理 |
| `--help` / `-h` | 打印帮助后退出（退出码 0） |
| `--version` | 打印版本后退出（退出码 0） |

未知参数：打印一行提示到 stderr 并**继续启动**（不因为参数拼错就拒绝启动）。

### 13.2 退出码

| 码 | 含义 |
|---|---|
| `0` | 正常退出（含"已有实例在运行，本实例退出"） |
| `1` | 未分类的致命错误（初始化失败、无法建立消息循环……） |
| `2` | 配置的 `schema_version` 高于宿主（见 [03-配置格式](插件开发/03-配置格式.md) §2.2） |
| `3` | 平台初始化失败（单实例锁、窗口类、渲染设备） |

### 13.3 Windows 子系统与控制台

`WIN32_EXECUTABLE TRUE` —— 常驻托盘应用不应弹出控制台窗口。

**入口点因此必须是 `WinMain`，不能用 `main` / `wmain`。**
`/SUBSYSTEM:WINDOWS` 要的是 WinMain 系的入口；用 `main` 会得到
`unresolved external symbol WinMain`。（MinGW 的 CRT 会宽容地接受 `main`，
所以这个错误在"我用 MinGW 试过一遍"之后才会在 MSVC 上冒出来。）

参数**不要**用 `WinMain` 收到的 `lpCmdLine` —— 它是 ANSI 的，中文路径会被
本地代码页破坏。一律 `GetCommandLineW()` + `CommandLineToArgvW()` 自己取，
这也是"UTF-8 只在内部流转、只在 Win32 边界做宽窄转换"在进程入口处的落点。

`--console` 的实现：`AttachConsole(ATTACH_PARENT_PROCESS)`，失败则
`AllocConsole()`；随后 `freopen` 把 stdout/stderr 指向 `CONOUT$`。

**日志始终写入 `OutputDebugString`**（Debug 构建下，或用 `--console` 时），
这样在调试器里能直接看到。

> **为什么没有 `--install-autostart`**：自启动**只**通过用户显式运行的脚本
> 注册（`scripts/win/install-autostart.bat` 等）。宿主自己写注册表看起来
> 只是"加一个参数"，但它让一个程序具备了持久化自己的能力 ——
> 这类能力往往是杀软与用户安全直觉关注的对象，而收益只是"少点一次脚本"。

## 14. 安全模型

### N4 — 不做插件沙箱

宿主隔离的是**崩溃**，不是**恶意**。

**现状要说清楚**：一个被安装的插件 DLL 在本进程内拥有完整的权限 ——
它能读写你的所有文件、发起网络请求、调用系统 API。
宿主不拦截、不审计、也不声称能限制它。

**理由**：真正的沙箱需要独立进程 + IPC + 一套权限模型，
那会让"跨边界只传 POD"这条已经足够严格的设计变成整个项目的主线，
并且要求插件作者重新学习一套 API。**那不是这个项目要做的事。**

**所以"安装一个插件"的信任级别应当等同于"运行一个 exe"。**
这句话必须出现在用户可见的文档里（`README`），不能让用户误以为
"这是个有插件系统的程序，所以插件是安全的"。

**重新考虑的触发条件**：插件有了第三方分发渠道、需要从不完全可信的
来源安装插件时。那时正确的方向是"独立的插件宿主进程 + 消息传递"，
而不是在本进程内加检查。

### N5 — 不给插件打开本地文件/目录的能力

`IHostContext` 只提供 `open_url()`，且只接受 `http` / `https` / `mailto`。

**理由**：一个能执行任意字符串的"万能打开器"（`ShellExecute` 的直通），
会让任何一个被安装的插件都具备执行本地命令的能力 ——
`file:///C:/path/to/evil.exe`、自定义协议处理器、甚至
`ShellExecute` 对某些字符串的解析怪癖，都是现成的攻击面。
而插件本来就已经能直接调用平台 API（见 N4），
所以这个接口**只是把能力包装得更方便**，没有增加任何表达力，
却让"这个插件能干什么"这个问题多了一个显眼的答案。

**需要打开本地文件的插件**：自己调 `ShellExecute`。它当然可以，
但那时"这个插件会启动本地程序"这件事在代码里是显式的，
而不是被一个看起来无害的宿主接口隐藏起来的。

### N6 — 不校验通知里的 URL

宿主不检查 `Notification::url` 是不是合法 URL，只在 `open_url()` 时
检查协议。展示层（控制面板）把它当纯文本显示，不自动加载、不预览。

`Notification::icon` 是另一回事：它会被宿主实际加载，因此**在加载那一刻**
校验来源 —— 只接受 http / https、`file://` 与本地路径，其它形式直接判失败。
这个校验不是"URL 合法性检查"，而是"要不要发起这次 I/O"的判定。

**理由**：宿主校验 URL 的合法性需要实现一个 URL 解析器，而它既不能
保证安全性（真正的检查在打开的那一刻），也不能保证正确性
（把合法的怪异 URL 判为非法更糟）。**检查放在真正会产生副作用的那一步。**

### N7 — 不做权限模型与多用户隔离

没有"插件权限"、"管理员模式"、按用户的插件可见性。
配置目录与数据目录按用户隔离（`%APPDATA%`），仅此而已。

**理由**：这是一个单用户桌面工具。引入权限模型的下场是一堆
"要不要再点一次确认"的对话框，而用户对这个程序的期望是
"在后台安静地待着"。

## 15. 明确不做的事

| 编号 | 不做什么 | 为什么 |
|---|---|---|
| N8 | 插件市场 / 在线安装 / 自动更新 | 宿主**不会主动联网**：不检查更新、不下载插件、不上报任何东西。唯一的网络请求来自通知内容本身 —— Notifier 调 `icon_texture()` 时，宿主才会去取那条通知的 `Notification::icon`（只允许 http / https，见 [02-宿主设计](02-宿主设计.md) §7.5）。插件仍由用户自己放进 `plugins/` 目录，这个动作同时也是 N4 里说的"信任决定"。 |
| N9 | 插件的**自动**热重载（文件监视） | 改完源码重新构建出的新 DLL **不会**被自动感知；文件监视引出的问题不少（DLL 被占用无法替换、重载时机与正在执行的 `start()` 冲突、重载失败要不要回滚），收益只是省掉用户点一次鼠标。作为替代，插件页提供 **“重新扫描插件目录”**：用户主动触发，扫描到的新 DLL 先走与启动时相同的校验再登记，校验失败的直接跳过并在列表里标出原因；已加载的类型与运行中的实例保持不变。替换一个正在使用的 DLL 仍然需要先在界面里禁用，或重启宿主。 |
| N10 | 插件之间的直接通信 | 那需要一套注册/发现/生命周期协议，还会让"加载顺序"变成有意义的东西；通知管线已经提供了所需的全部能力 —— 一个 topic + 一个订阅就是一个单向通道（A 产生 `x.y`，B 订阅 `x.y`）。 |
| N11 | 通知的富文本 / Markdown 渲染 | `content` 是纯文本，控制面板与浮层都按纯文本渲染；渲染富文本要引入解析器、布局规则，还会带来一个安全问题（HTML/图片/链接的加载），而通知正文绝大多数是"一段话" —— 需要结构的插件应当用 `title` / `summary` / `actions` 这三个已有的结构位。 |
| N12 | "时刻表"式的调度语法 | `schedule_next(ms)` 与 `schedule_at(unix_ms)` 是全部；调度语法一旦引入，就要处理时区、夏令时、闰秒、"上次没跑要不要补"这些**没有统一正确答案**的问题 —— 推给插件按自己的业务决定更合理。 |
| N13 | 免打扰时段 / 优先级抢占 / 通知聚合 | 这些都是**策略**，应当由 Notifier 插件实现（用户对"静音"的定义各不相同，做进宿主会变成"所有 Notifier 都必须遵守的规则"）。宿主只提供**用户逐条写下的**规则中间层（`rules.toml`）：匹配与改写由用户配置，宿主不预设任何默认过滤策略。另一个例外是 `sm.host.log` 的限速合并 —— 那不是策略而是**保护**，必须由宿主切断"用日志冲垮自己界面"的循环。 |
| N14 | 通知的远端推送 | 不发邮件、不发 webhook、不推送到手机 —— 这是 Notifier 插件的典型用途，宿主只提供"我收到了这条通知"的回调，插件要发到哪里是它自己的事。 |
| N15 | 多语言界面 | 界面语言恒为简体中文（见 [03-控制面板](03-控制面板.md) §11）；字符串**集中在 `src/host/strings.h`** 不是为了"以后能加语言"，而是因为把中文字面量散落在几十个文件里，连"改一个措辞"都要全局搜索。 |
| N16 | 主题 / 皮肤 / 自定义配色 | 只有一套 imgui 默认风格 + 少量级别配色（见 [03-控制面板](03-控制面板.md)）；配色是纯粹的偏好，而实现它需要一套配置 schema、一个实时预览界面、以及"某个主题在某个控件上不可读"的一类 bug。 |
| N17 | 无上限的任何东西 | 队列、历史、字符串、设置项、订阅数、Action 数……全部有硬上限（见 [02-SDK接口参考](插件开发/02-SDK接口参考.md) §3.3）；资源受限是明确的设计约束，没有上限的队列在插件失控时会吃掉整个进程的内存，而"吃掉内存"的表现是整机卡顿。 |
| N18 | 性能剖析 / 遥测 / 崩溃上报 | 宿主不主动联网（唯一的请求是加载通知图标，见 N8）；性能相关的信息以日志形式提供（每次 `start()` 的耗时在 `debug` 级别可见）。 |
| N19 | 用 SEH 之外的任何方式"修复"插件崩溃 | 崩溃过的插件**进程内状态不可信**（见 [02-宿主设计](02-宿主设计.md) §5.2）；重试它等于赌运气，还会把"一个插件崩溃"变成"一个插件反复崩溃" —— 正确的处理是卸载它，并把这件事清楚地告诉用户。 |

### 已知的、刻意的取舍

这些看起来像 bug，但都是决定。列在这里，免得被反复"修好"。

| 现象 | 原因 | 出处 |
|---|---|---|
| 配置文件里的**注释会消失** | 写回是整体重写，不保留格式 | [03-配置格式](插件开发/03-配置格式.md) §6.4 |
| 通知队列满时丢的是**最旧**的，不是拒绝最新的 | 最新的一条通常最重要 | [02-宿主设计](02-宿主设计.md) §7.2 |
| `allocate_string` 可能**切断 UTF-8 序列** | 它按字节截断，是为了零依赖；要按码点截断用 `make_summary` | [02-SDK接口参考](插件开发/02-SDK接口参考.md) §6.3 |
| 默认 `log_level = "info"` 时**看不到通知的详细日志** | 否则高频通知会淹没日志 | [02-宿主设计](02-宿主设计.md) §12.7 |
| 生僻字显示成 `?` | 只用常用简体字集，换取启动时间与显存 | [02-宿主设计](02-宿主设计.md) §13 |
| 插件设置被改动**不会重启插件** | `requires_restart` 只是提示 | [02-SDK接口参考](插件开发/02-SDK接口参考.md) §7.3 |
| 一个卡死的插件会让**宿主无法干净退出** | 绝不强杀线程 | §10.3 |
| 主线程空闲时**每秒被唤醒一次** | 看门狗需要一个观察者 | [02-宿主设计](02-宿主设计.md) §5.4 |
| 关掉控制面板**不会带走详情窗口** | 详情窗口是独立表面，各有各的关闭动作 | [03-控制面板](03-控制面板.md) §1.3 |
| 手写的参数拼错时程序**仍然启动** | 一个拼错的参数不该让程序起不来 | §13.1 |
| 休眠 3 小时后唤醒**不补跑**积压的调度 | 补跑只会产生一批重复通知 | [02-宿主设计](02-宿主设计.md) §6.4 |
| Debug 宿主拒绝加载 Release 插件 | CRT 不匹配会随机崩溃 | [01-入门](插件开发/01-入门.md) §2 |
| 清空历史**不重置** `seq` | 保证"进程内唯一"这条保证 | [03-控制面板](03-控制面板.md) §4.5 |

## 16. 什么时候该重新考虑

上面每条都写了各自的触发条件。除此之外，有三条通用的判断：

1. **如果某个非目标挡住了真实用户的真实任务**，它就不是非目标了 ——
   但先确认"真实任务"是否真的无法用现有能力表达
   （例如 N13 的静音，一个 Notifier 插件就能做）。
2. **如果某个非目标被反复提出**，检查是不是文档没说清"现在怎么做"。
   多数情况下答案是补文档，而不是加功能。
3. **如果加它只需要一个已经存在的机制的复用**，成本可能比看上去低。
   反之，如果它需要一个新的抽象层（沙箱、权限、插件间通信协议），
   成本几乎总是被低估的。
